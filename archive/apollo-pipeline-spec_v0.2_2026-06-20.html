What changed since v0.1

From a single review pipeline to a governed discovery loop.

v0.1 (the "double diamond as a harness") modelled one downstream pipeline: brief → generate → craft gate → parallel review → taste gate → handoff. That architecture survives. v0.2 adds the front of the pipeline — the part that was always the real moat — and tiers the checks so rigor doesn't recreate the slow review it replaces.

Locked 2026-06-20

  • Spec / eval-first is the spine. Success/failure criteria are written as executable checks before design; the criteria become the gates. Verification = enforcement, moved upstream.
  • Intake is an adaptive maturity router, not one flow: seed idea → brainstorm; half-formed → guided JTBD; well-specced → ingest + quiz. All lanes converge on the same criteria contract.
  • Checks are tiered: a few hard objective gates (block), many cheap advisory signals (annotate), a small set of true human taste calls.
  • Generation is multi-solution: N variants on meaningful axes, all run through the objective gates; LLM judging filters the broken, humans + users pick the winner.
  • Constitution pattern adopted (from spec-kit): a root file of non-negotiable principles every phase references — ≈ the gated canon.
  • Editor stays last and bought-in, not built. Generation/editing is commodity (v0, Stitch, Figma Make, Lovable); the moat is upstream.

Overview

The pipeline is a contract, enforced.

Intake adapts to how mature the project is and produces one thing: a criteria / spec contract — the success and failure conditions written as checks. Generation then produces several solutions; the objective gates kill anything that violates the contract; humans and users pick from what survives.

The taste call is made cheap and rare, not absent. Everything around it is computed: the evidence, the diff, the A/B, the pre-rejection of anything failing an objective gate.

Diagram 1 — End-to-end pipeline

Intake router → criteria contract → multi-solution generation → tiered checks → human taste → tuned prototype. Red = human-in-the-loop. Gates withhold "done".

The spine — spec / eval-first

Write the checks before the design.

Borrowed from agentic coding (GitHub spec-kit, eval-driven development): define success and failure as executable checks first. Those checks are the gates every later stage is held to. It is the purest extension of this project's founding principle — verification = enforcement — moved upstream into discovery.

The honest limit: spec/eval-first assumes you already understand the problem. For a genuinely new problem you don't, and writing criteria too early just locks in your first guess. That is exactly why intake is a maturity router with a divergent front-end — the spine governs the objective half (states, a11y, tokens, copy rules); the subjective half is handed to the human taste call.

Constitution (from spec-kit)

A root file of non-negotiable principles every phase references. Structurally ≈ the gated canon: the hard objective rules — brand (angular), contrast, token fidelity, reduced-motion — declared once, referenced by intake, generation and checks alike.

Checks — tiered

A few blocks. Many signals. Rare taste calls.

If every check becomes blocking, you have rebuilt the slow review you set out to kill. Tier them: hard objective gates block, cheap advisory signals annotate, true taste calls stay rare and human.

Harness — the open crux

What is "done" at each tier?

The harness is the contract that says, at each tier: what goes in, what "done" means (which gates), and how tiers compose upward. The component tier is solved. The screen / journey / project tiers are the open work — and the intake lanes above now specify their inputs, so this no longer starts cold.

Guardrails

Three rules that keep the moat the moat.

01
Automate around taste, not taste itself
Compute the evidence, render the diff, line up the A/B, pre-reject anything failing an objective gate — then hand the human a ~20-second decision. Make the taste call cheap and rare, never absent.
02
Tier the gates
A few hard objective gates block; many cheap advisory signals annotate; a small set of true taste calls. Resist gate sprawl — if everything blocks, you've rebuilt the slow review.
03
Editor last, and bought-in
Generation/editing is commodity (v0, Stitch, Figma Make, Lovable). Don't build a bespoke editor; wrap one. Spend the scarce effort on the differentiated front of the pipeline.

Proof project

Prove the method on the payments journey — backwards.

Define just enough target to run one real proof, then let the first project refine the rest. The chosen proof: run the payments journey — tech-first, slow, contested, no real discovery — backwards through the loop. Reconstruct the criteria, the riskiest assumptions and the gates it skipped, then produce a "what would have bitten us after go-live" gap report.

Why retrofit, not a speculative PRD: it uses a real project, the ground truth is observable (the pain already exists), it needs no fabricated research, and it speaks directly to the failure being feared. A PRD with no research is confident fiction — and you can't validate a discovery tool against an imaginary project.

v1 prune commitment

A lot of artifacts were produced fast. Naming the prune now so it isn't optional: at v1, everything in knowledge/_demo/, the two intake instruments, and the deferred harness work each get an explicit keep / promote / delete decision. Artifact volume is not proof — the demo and instruments are only validated once the colleague chat and a live showing actually happen.
