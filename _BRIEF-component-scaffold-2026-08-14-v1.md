## 1. What we are trying to do, in plain words

We have spent a lot of sessions building the machinery around components — the gates, the token
store, the theme cascade, the showroom — and almost none building components. The point of this
brief is to start that again, deliberately, with one component, so that the *route* a component
takes from nothing to gated-and-visible gets walked end to end by somebody who writes down where it
hurt. Dave's own words for the goal are simply that **component creation resumes at the weekend or
next week**. So the deliverable of the next build session is a real, finished, reviewable component
sitting in the showroom for Dave to look at — plus an honest note of every place the route made the
builder guess, dig or improvise. That note is what earns us the right to automate the route later.
We are not automating it first. We build the component first, and let the friction we actually
observe decide what, if anything, gets built to smooth it.

## 2. What "the scaffold" actually is — verified state, #173

⚠ **First, a correction to the inherited premise.** The #172 plan (`_PLAN-172-back-on-track-2026-08-14-v1.md`,
lane B item 4) describes the component-scaffold path as a thing to be *built*: *"a thin `atoms-first`
scaffold: pick component → resolve tokens → meta.schema entry → per-theme render-proof harness."*
Read as "there is no scaffold yet", that is **wrong**. Most of that path already exists, is written
down, and is gated. What does not exist is a *scaffolder* — a command that creates the skeleton for
you. The distinction matters, because it changes the next window from an infrastructure build into a
content build with a friction log. [[premise-ages-faster-than-rule]]

Everything below was verified by reading the files in the repo at HEAD `e5ab8ee` on 2026-08-14.
⚠ **Nothing here was verified by RUNNING a gate.** No validator, generator or build step was executed
while writing this brief. Treat every "the gate does X" statement as *read from the source*, not
*observed firing*, and re-verify at build time.

### 2.2 The other registries a new component must be joined to

These are the places a new component has to be *registered*, not just authored. Missing one is the
classic way a build looks green and is not.

- **`knowledge/gen_showroom.py` → `CATEGORIES`** (line 127) — the showroom index. Six categories.
- **`knowledge/_validate_radius.py` → `MIGRATED_SNIPPETS`** (line 46) — the radius ratchet. Its own
  docstring is explicit: *"rebinding a snippet's radius onto the token (CSS + manifest + theme-block
  declarations) and adding it here is ONE change."* A new snippet built radius-correct from the start
  belongs in this set.
- **`knowledge/component-types.json` → `$members`** — ADR-0013's component-type tier. ⛔ **Only join a
  family if the duplication is OBSERVED, never speculated** (ADR-0013 ruling 3). If the new component
  carries press-physics, `button-family` is its home and it must then carry the `AUTO-PARTIAL`
  markers, the required vars and the `$manifestBinds` bindings, or `gen_component_partials.py --check`
  fails the build.
- **Type composites** — `.t-cm-*` / `.t-ed-*` are mandatory (Dave, firm). The ratchet baseline in
  `knowledge/_type_ratchet.json` is **1101 and may only SHRINK**. A new component that adds raw type
  declarations instead of composites raises the count and fails the ratchet.

### 2.3 What does NOT exist (be honest about this)

- **No scaffolder.** There is no `new-component` command, no template generator, no skeleton writer.
  The snippet is authored by hand from the runbook. This is the gap the #172 plan was pointing at.
- **No standard per-theme render-proof harness.** What exists is a set of **one-off, per-component
  scripts** — `knowledge/_render_button_responsive.py`, `_render_tags.py`, `_render_links.py`,
  `_render_notif.py`, `_render_journey.py`, `_render_sme.py`, `_render_smej.py`. Each was written for
  its own moment. There is no shared "render this snippet × 4 themes × light/dark" entry point.
- **No index or checklist over the component metas.** Carried openly in the queue (§C·1(e), the
  component-spec-KG remedy): the `knowledge/components/*.meta.json` files are *in no index and in no
  checklist*. Nothing tells you a meta is missing a field until a gate happens to catch it.

## 3. The first component — a RECOMMENDATION

⛔ **This is Dave's choice. What follows is a recommendation with reasons, and he may override it
with any component he likes.** It is presented as a recommendation precisely because picking from an
incomplete set reads as a ruling if it is not said plainly.

### Recommended: **Progress bar — determinate, linear and circular**

**Why it:**

1. **It is a genuine remaining gap, verified.** There is no `Progress-bar.reference.html`.
   `Loading-indicator` is a spinner only (its markup carries just `.loader` and `.spinner`).
   `Progress-tracker` is a step display. `role="progressbar"` currently appears in three snippets —
   `Progress-tracker`, `File-upload` and `Stepper` — which means **three components have each
   improvised their own progress bar**. That is observed duplication, and observed duplication is
   exactly what ADR-0013's component-type tier is for. Building the atom gives that duplication a
   legitimate home instead of a speculative one.
2. **It is an ATOM, so it respects the ATOMISE ordering** (atoms → molecules → organisms, Dave
   2026-07-14). It depends on no unbuilt atom. The `P-rolled-up` pitfall — building a molecule before
   its atoms and recreating the debt ATOMISE exists to stop — does not apply.
3. **It is small enough to finish, and wide enough to prove the route.** It exercises every seam that
   matters: token resolution light+dark, all four themes, a contrast pair (fill vs track vs page),
   `role="progressbar"` + `aria-valuenow/min/max` + accessible name, a `prefers-reduced-motion` block
   for the fill transition, and the type-composite rule on its label. It does not drag in keyboard
   interaction models, focus management, overlay/portal behaviour or date logic.
4. **It does not touch anything Dave has parked.** It needs no ruling on `tooltip.tip`, no ruling on
   base red 30, and no palette reshape. Its colours come from the primary/neutral surfaces that are
   already green. That means the weekend's Dave's-eye day and this build do not collide.
5. **It unblocks two fintech gaps by composition.** The itinerary's **Coverage / runway bar** (P2) and
   **Limits meter** (P3) are both a progress bar with a domain label. Building the atom first is the
   cheapest route to both.

**Scope fence to carry into the build:** **determinate only.** An indeterminate variant overlaps
`Loading-indicator` and would need a ruling on which component owns it — that is a Dave question, and
Gate 3 below asks it rather than assuming.

**Alternatives, honestly stated, in case Dave prefers one:**

| Alternative | Case for | Case against |
|---|---|---|
| **Avatar group** | Smallest possible build; pure atom-on-atom over the existing `Avatar`. | Very low value; proves little about the route because it barely touches tokens or a11y. |
| **Combobox / autocomplete** | High real value; `Dropdown` + `Input-fields` atoms already exist so it is legal under ATOMISE. | A molecule with a heavy interaction and ARIA model. Likely spills a window and buries the friction log under implementation. |
| **Timeline / activity feed** | Directly useful for the fintech transaction story. | A molecule; also overlaps `List-items` in a way that needs a scoping call from Dave first. |
| **Footer / doormat** | Layer-2 shell work, which is the load-bearing gap long-term. | Blocked in practice by the Brand mark / logo P1 asset gap. |

## 5. CONSEQUENCES AND PITFALLS — mandatory section

*(Dave ruled #165: every proposal and every sub brief replays the known consequences. These are the
ones that have actually bitten this repo, not hypotheticals.)*

**Absolute prohibitions**

- ⛔ **Do NOT run or touch `knowledge/_build_all.py`.** A single-process run is sandbox-impossible
  (~49s against the ~45s call kill), and **any partial run strands the tree in a documented mid-build
  intermediate** — step 1 rewrites wholesale and is healed only by a complete pass. CI delivers the
  single-process verdict on push. Also: the `#166` label strings in its route table are **join keys** —
  ⛔ never edit them, not even cosmetically.
- ⛔ **`set_content()` is BANNED in render-proofs.** It silently drops `type.css` (14px→16px) and
  `document.fonts.check` passes anyway, so the proof lies. Use `goto("file://…")`. Measured, #29.
- ⛔ **Never hand-edit a generated surface** — `canon/canon.css` between the AUTO markers,
  `showroom/*.html`, the token blocks. Edit the source and regenerate. [[no-gate-parses-the-artefact]]
- ⛔ **Do not write `GOOD-MORNING.md`, `_LIVE-STATE.md`, `_FUTURE-STATE.md` or
  `knowledge/_rulings.json`.** Rulings are Dave's and are inscribed by the conductor.
- ⛔ **Do not commit.** Hand files up to the conductor.

**Environmental potholes, all previously observed**

- The **render sandbox is fresh every session** — budget ~4 calls just to stand it up, and price it.
  `pip install tiktoken --break-system-packages` first, or the gauge refuses loud and named.
  `LD_LIBRARY_PATH` chromelibs. Full recipe: `knowledge/_RUNBOOK-render-verify.md`.
- **ENOSPC masquerades as "Download failure, code=1"** — three observed occurrences. Check
  `df -h $HOME` *before* diagnosing the network; set `PLAYWRIGHT_BROWSERS_PATH=/var/tmp/pw-browsers-<session>`
  and `pip install --target /var/tmp/pylibs`.
- **`/tmp` and `/sessions` are SHARED across sessions.** A pre-existing artefact there is FOREIGN —
  reading it will serve you another session's traceback as if it were your run's evidence. Use a
  unique log path under `$HOME`.
- **Nothing survives a tool-call boundary**, and builds over ~45s wall get killed. Chunk with
  `--range` / `--resume`.

**Failure classes this build is specifically exposed to**

- **P-theme — a single-theme green is not a green.** Four themes means four proofs per surface.
  Console and Supercharge render as Mono where their override sets are empty; that is *labelled*, not
  a pass by default.
- **P-address — a token name is not an address.** The `--pri-hover` fork was measured at #108: the
  same token name resolves differently per theme. Consult the fork ledger; never assume.
- **P-rolled-up — building a molecule before its atoms** recreates exactly the debt ATOMISE exists to
  stop. This is the main argument for the recommended pick.
- **P-scope — the scaffold is wiring, not new design law.** Any new token or tier this build appears
  to need goes to `knowledge/_DS-IMPROVEMENTS.md` as a proposal. **Promotion is Dave's, always.**
  Token proposals live in `knowledge/tokens/_proposals/`, OUTSIDE the resolving stores, until Dave
  physically moves them in — the store boundary is the fence, a `$confidence` tag is not.
- **The registry-miss class.** A snippet can be authored, gated and still invisible, because
  `CATEGORIES` was not updated. Step 5 exists for this.
- **The ratchet class.** `_type_ratchet.json` baseline 1101 **may only shrink**. Raw type declarations
  instead of `.t-cm-*` composites will raise it and fail the gate.
- **The unrun-gate class.** A gate you did not run cannot fail, and reporting it as passing is the
  worst failure mode in this repo. **Declare what you could not run and why.**
  [[instrument-without-a-consumer]] · [[unrun-search-is-not-an-absence]]

## 6. BOUNDED VERIFICATION — the appetite clause

*(Ruled `s172-D3`, Dave #172. Full body: `knowledge/_RUNBOOK-parallel-conductor.md` § BOUNDED
VERIFICATION — read it. ⛔ Read the fence first, because it is Dave's condition and not a caveat:
**"careful of externalities, I don't want to fix something only to break other constituent parts."**
This section governs THE APPETITE FOR BUILDING NEW INSTRUMENTS AND NOTHING ELSE. **IT RETIRES
NOTHING.** No existing gate, law, runbook clause or ruling may be removed, relaxed, skipped, narrowed
or "simplified" by citing it. A brief that cites it to justify not running something is misusing it.)*

**(a) Scope block, near-verbatim, and it applies to this build:**

> *"Use the minimum complexity that solves the current task. No abstractions for hypothetical future
> needs. No defensive code for scenarios that cannot occur here. Make the changes requested and those
> clearly necessary to them — nothing else."*

**(b) Verification is TARGETED.** Prove **the seam this deliverable creates** — named per step in §4.
⛔ Not "verify everything you touch": that instruction has no edge, spends the whole window, and still
cannot say what it proved. For this build the seams that must be proven are: the **component seam**
(the snippet renders correctly in all four themes, light and dark), the **contrast seam** (declared
pairs actually pass), and the **registry seam** (the component appears in the showroom index and
regenerates byte-identically).

**(c) DEPTH CAP — one level.** If this build creates any new check at all, it is driven to a **named
refusal once**, with a passing control. ⛔ No checkers checking checkers beyond that.

**(d) MACHINERY PRICE LINE.** The build sub's report declares **instrument-lines vs feature-lines**,
e.g. `machinery: 0 instrument / 240 feature`. It is a reported measurement, not a threshold — nothing
fails for a bad ratio. It exists so the ratio is visible at the moment it is chosen.

**(e) OBSERVED-FAILURE RULE.** A new test must cite **the failure class it guards** or **the ruling it
enforces**. A check with neither is speculative: it **QUEUES as a proposal for Dave** and is **never
built in the same breath as the thing it would watch**. ★ **This is why the friction log (step 9) is a
deliverable and a scaffolder is not.** We do not build the scaffolder until we have observed, in
writing, what it would have saved.

## 7. DAVE-GATES — the decisions this brief leaves to him

Each is a plain question with a recommendation attached. None of them is settled.

**Gate 1 — Which component goes first?**
*Recommendation:* **Progress bar, determinate, linear and circular.** It is a real remaining gap, it
is an atom so it respects ATOMISE, three existing snippets have each improvised their own version of
it, and it touches nothing you have parked for the weekend. Alternatives with their trade-offs are in

**Gate 2 — Does the next window build the component, or build a scaffolder first?**
*Recommendation:* **Build the component, and keep a friction log.** The route already exists as a
written runbook plus a gate chain; what is missing is convenience, not capability. Under the
observed-failure rule a scaffolder built now would be a speculative instrument. Build one component,
write down where it hurt, then decide.

**Gate 3 — Does the progress bar include an INDETERMINATE variant, or is it determinate-only?**
*Recommendation:* **Determinate-only for v1.** Indeterminate overlaps `Loading-indicator`, and which
component owns that state is a scoping decision, not a build decision.

**Gate 4 — Should the new component join a `component-type` family in `component-types.json`?**
*Recommendation:* **No, not for a determinate progress bar** — ADR-0013 ruling 3 says groups accrete
from OBSERVED duplication only. The three improvised progress bars in `Progress-tracker`, `File-upload`
and `Stepper` *are* observed duplication, so a `progress-family` becomes arguable — but arguable is
not the same as ruled, so it queues as a proposal rather than being minted in this build.

**Gate 5 — Do the stale inventory documents get corrected, and when?**
*Recommendation:* **Yes, but as a separate small lane, not inside this build.**
`knowledge/_COMPONENT-LIBRARY-TARGET.md` (says ~38 components, ~20 P1 gaps; reality is 75 and
essentially one) and `reviews/ITINERARY-2026-07-14-apollo-component-library.html` (86 stale Gap/Partial
rows) both misstate where we are. They are load-bearing for any "what next" conversation, so leaving
them wrong is a live risk — but rewriting them mid-build would bury the build.

**Gate 6 — Who is the build sub, and how much of the window does it get?**
*Recommendation:* **One Opus sub, one window, priced at ~110–130K real tokens** per §4. ⛔ No Sonnet
subs. Quota is cheap this week; the window is what binds.
