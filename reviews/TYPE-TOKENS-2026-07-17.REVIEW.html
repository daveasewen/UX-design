00What the Figma file gives us

One responsive scale of a fully tokenised type system — no hardcoded values, which is exactly the foundation we want.

The node is titled scale-1, which strongly implies there are sibling scales (scale-2, scale-3) for the other breakpoints — matching the "three responsive scales" the project has been anticipating. Everything on the specimen is driven by variables, layered like this:

Primitivesthe raw values
font family, font weights (named → numeric), and per-size font-size / line-height / letter-spacing / paragraph-spacing.
Composite styleswhat a designer applies
named text styles that combine the primitives — e.g. font-1/regular, font-5/link, Call-to-actions/default.

So the good news up front: the source is already primitive-driven. Our job is to decide how to name and arrange it, and to add the second (interface / cropped) expression you want.

03The composite styles

Each size ships several ready-made text styles. There are three "columns" on the specimen, plus role styles at the small sizes.

1 · Weight-named

font-N/light · font-N/regular · font-N/medium — the plain "pick a weight" styles.

2 · Default → highlight

A two-weight pairing: default for the run of text and highlight for the emphasised words inside it (the "quick brown fox" bolding on the specimen). At large sizes default is the lighter weight and highlight a step up.

3 · V2

The same default/highlight pairing bumped up one weight step — a heavier alternative (likely for lower-contrast surfaces or a slightly bolder aesthetic).

Role styles (small sizes)

At font-5/6/7 the system adds purpose-named styles: link tooltip superscript alternative, plus Call-to-actions/default (font-5) and Call-to-actions/small (font-6).

04Your two sets — editorial vs interface

This is the heart of what you asked for. The key point: both sets share the same primitives. The only real difference is the box / line-height treatment.

Editorialtype as-is
Full line-height baked in (the values in §02). Leading gives vertical rhythm and breathing room — for prose, headings, marketing and content. Matches your earlier ruling that headings and body are excluded from the crop.
Interfaceline-height crop
Same primitives, but the visual box is cropped to cap-height→baseline (text-box-trim / leading-trim). Lets component text — labels, buttons, inputs, table cells — sit exactly on the 4px grid without the half-leading padding above and below. Matches "text-box-trim for labels, metric-aware".

So structurally I'd expect one primitive tier feeding two composite tiers, not two duplicated scales. That's decision D2 below.

05Decisions to make

Six open calls. Each has my recommendation marked; the "Your call" line is yours to answer (pin a comment on it or use Export).

Decision · D1 — how to name the size scale Keep font-00…font-7, or rename?

The font-N names don't say how big a step is or what it's for, and (per §02) they don't even sort by size. Three common approaches:

A · Keep font-N — 1:1 with Figma, easy to trace back; but opaque, and keeps the out-of-order oddity.
B · Role names — display · heading-xl · heading · body · caption · label. Readable, says what to use it for (what Material / Polaris / Carbon do); needs a lookup back to Figma.
C · Numeric ladder — size-900…size-100 or by px. Always sorts correctly, fixes the font-2 oddity; but doesn't say what it's for.
Recommend D · Two-tier — C underneath, B on top. A clean ordered primitive scale (unambiguous), with role aliases layered over it. This is what mature systems actually do — you get traceability and readability, and nobody argues whether "font-4" is a heading or a caption. Keep a note mapping each back to its font-N source.

Your call: A / B / C / D — or your own scheme. If D, do you want the primitive scale numbered by rank (100–900) or by px?

Decision · D2 — how to structure editorial vs interface How should the two sets sit in the token tree?
Recommend A · One primitive tier, two composite tiers. Shared size/weight/family primitives; editorial/* and interface/* reference them; the crop lives only in interface. Least duplication, standard shape, easiest for another designer/dev to pick up.
B · Two parallel trees — fully separate editorial and interface trees. Each is independently portable, but you maintain everything twice.
C · One set + crop modifier — a single tree where interface is editorial plus a boolean crop flag. Leanest, but couples the two so a change to one leaks into the other.

Your call: A / B / C.

Decision · D3 — how you picture the two sets in Figma Two style folders, or "the same thing, tightened"?

This is the one I genuinely need your mental model on, because it changes how the role layer is named. When you imagine a designer working: do they see two separate style folders ("Editorial" and "Interface") and pick from the right one — or one set where interface is understood as "the editorial style, cropped for components"?

Your call: folders-of-styles / one-set-tightened / something else — tell me how you see it.

Decision · D4 — the font-2 value Is font-2 = 43px correct, or a bug?

Flagged in §02. I don't want to bake in a value that's out of order with the rest of the scale without you confirming it against the source.

Your call: 43 is right / it's a bug (should be ~__) / I'll check the Figma and confirm.

Decision · D5 — default / highlight / V2 naming Keep the default · highlight · -V2 vocabulary, or rename?

highlight reads a bit ambiguously (it's inline emphasis, not a highlighter), and -V2 doesn't say what the variant is for. Options: keep as-is for continuity; or rename to something like body / emphasis and a purpose name for the heavier set.

Lean Keep default/highlight for continuity with the existing file, but give -V2 a real name once we know what it's for (accessibility? a bolder brand register?).

Your call: keep / rename (to what?).

Decision · D6 — where the role styles live link · tooltip · superscript · CTA · alternative — editorial, interface, or both?

These are inherently component-ish. My instinct is they belong in the interface set (cropped), with editorial carrying only the reading styles.

Recommend Role styles → interface set. Editorial = headings + body only.

Your call: interface / both / split differently.

If you took every "recommend" above, the system would look like this:

Primitivesordered, unambiguous
Numeric size scale + weights + family + the four per-size metrics. font-2 fixed. Each maps back to its font-N source in a note.

display · heading · body … — reading styles only, natural line-height.

Three responsive scales (scale-1/2/3) sit under all of it as a mode, once we bring in scale-2 and scale-3.
