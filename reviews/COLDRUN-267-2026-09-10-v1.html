Findings

Seven, each with the file that proves it

Finding 1 · blocking for a consumer

canon.css and the snippets have diverged. Two components ship markup that canon.css cannot style.

The skill's rule 2 says copy the snippet; step 3 says link canon.css. Do both, exactly, and the sidebar navigation and the filter toolbar come out unstyled — because the class names in the snippets' markup are not in canon.css at all. They live only inside each snippet's own private <style> block, which rule 3 never tells you to copy.

$ grep -c "nv-item" knowledge/canon/canon.css → 0 $ sed -n '39,265p' knowledge/snippets/Sidebar-nav.reference.html | grep -c nv-item → 18 canon.css's .cn-sidebar-nav scope carries .sn-link / .si / .si svg (an OLDER vocabulary) the snippet's markup carries .nv-item / .nv-ic / .nv-label / .nv-count / .nv-chev $ grep -c "ftb-primary" knowledge/canon/canon.css → 0 (also 0: ftb-trailing, ftb-ctl, ftb-context, ftb-status, ftb-hint, ftb-clear, th-in) canon.css's .cn-filter-toolbar-bar scope carries .ftb-row / .ftb-view / .ftb-filter

This is what took rich from 3 to 2, and it is what makes the dropdown menus pointer-dead (they are not positioned, so a live region in normal flow sits over them). The skill's own claim — "canon.css (all tokens, aliases, utilities and all 135 components)" — is not true of these two.

Finding 2 · blocking for a consumer

The released ZIP cannot pass its own two gates, because the receipt minter is not in it.

Step 5 says: mint the receipt first with gen_provenance_receipt.py --mint, then run _validate_receipt.py. That file is in three release zips zero times. Without it the receipt gate stops at FAIL:NO-RECEIPT and never inspects the page — so every later check (behaviour loaded, no demo chrome copied) never runs either, exactly as the skill warns.

v1.0.7.zip · v1.0.8.zip · v1.0.9.zip grep -c gen_provenance_receipt.py → 0 0 0 repo tree knowledge/gen_provenance_receipt.py → present knowledge/gen_*.py in the zip → gen_snippet_tokens.py (that is the whole list) also absent from the zip: gen_component_partials.py — which 30+ snippet comments tell you to run

Cold run 5 passed both gates because it ran against the tree. This is the first run against the artefact a customer receives, and it is why the gate column flipped.

Finding 3 · the good news

The chart engine works, and it closes cold run 5's F03.

C5's third finding was "rule 2 cannot be obeyed for a data-driven chart" — every chart snippet was baked SVG, so a moving chart had to be hand-drawn. In v1.0.9 a blind build wrote three data specs and three dvRender() calls and drew no geometry at all. Six rects, five polylines and seven arcs all came from the library, all re-render on a filter, and the table lockup is rewritten from the same numbers.

dv-render.js:1 "THE DATA-DRIVEN CHART ENGINE, core (s249-D4, built #259)" dv-render.js:25 "It REPLACES rule 18 of ADS-generate-from-canon" all six engine files inlined byte-identical (sha256 table above)

Finding 4 · discoverability

Rule 18 of the skill still teaches the interim recipe the engine replaced.

The rule reads "A library engine replaces this in v1.0.9; until then, author the geometry yourself" and then gives a 15-line renderBars() to copy. It is v1.0.9 now. The engine's own header says it replaces that rule. A blind consumer who reads the skill top to bottom — the intended path — hand-authors arithmetic the library owns. This build only found the engine by opening the last script in Chart-bar.reference.html.

skills/generate-from-canon/SKILL.md rule 18 — unedited interim recipe, still present knowledge/canon/dv-render.js:25 — "It REPLACES rule 18" Two files in the same pack disagree about which is the current instruction.

Finding 5 · gate quality

The pack's own engine trips the pack's own icon gate.

The single icon-source: ❌ 1 UNKNOWN on the screen gate is not authored markup. It is the string ' d="' + arc(cx, cy, ro, ri, a1, a2) + '"' at dv-render-donut.js:113 — the donut engine building a path at run time. The gate reads inlined JavaScript as if it were an icon in the document.

$ grep -n 'arc(cx, cy, ro, ri' knowledge/canon/dv-render-donut.js → 70, 113 A page carrying the engine verbatim, as rule 2a asks, is refused by the icon gate for doing so.

Finding 6 · composition

Chart chrome needs a second nested scope inside a bento tile, and nothing says so.

.cn-template-dashboard-bento carries dv-head · dv-title · dv-stage · dv-chart-area · dv-svg · dv-grid · dv-series — but not .dv-tbl, .dv-tablepanel, .dv-controls, .dv-label or .dv-legend. So a chart in a bento tile that wants its table lockup, its sort control or its axis labels has to be wrapped in a second .cn-chart-* scope inside the tile. Trap (a) in rule 18 warns you the wrapper matters; it does not say you will need two.

grep -o "\.cn-template-dashboard-bento[^{,]*" canon.css | sort -u → 196 selectors, none .dv-tbl Consequence seen in the render: the donut, authored WITHOUT a details.dv-tbl lockup, shows the engine-written <table class="dv-table"> as bare rows under the ring.

Finding 7 · retrieval

Eight of eleven chart types, and both facility components, unused again.

Sixth run running. The brief says corporate international banking; the page carries a committed facility at 18% drawn as a sentence of plain text, while limits-meter and runway-bar sit in the index unused. The bento template's own specimen writes that line as plain text, and rule 2 says copy the specimen — so the specimen, not the index, decided what got used.

showroom/index.json — 145 entries. Used: 15. Dashboard-set available and unused: 22. Unused chart types: pie · sparkline · combo · scatter · stacked-area · bullet · histogram · boxplot · butterfly-h · butterfly-v · candlestick

For Dave

Ruling-shaped questions

Not answered here. Each one is a decision only you can make, and each has a fact above attached to it.

RSQ-1. Does v1.0.9 ship tomorrow with a released pack that cannot pass its own two gates?

Finding 2. The fix is a packaging line, not a code change — gen_provenance_receipt.py (and probably gen_component_partials.py) into the zip. It has been missing since v1.0.7, so it is not a v1.0.9 regression; it is a v1.0.9 opportunity.

RSQ-2. Is canon.css's divergence from the Sidebar-nav and Filter-toolbar-bar snippets a release blocker, or a known-issue note?

Finding 1. It is the only reason a score moved down. A demo that shows a side navigation will show this.

RSQ-3. Should rule 18 of ADS-generate-from-canon be cut to a pointer at dvRender before the demo, or after it?

Finding 4. It is a documentation edit with no code risk, and it is the difference between the engine being found and being found by accident.

RSQ-4. Should the icon gate skip <script> content, or should the engine be linked rather than inlined?

Finding 5. Two different answers, one of which changes the "single self-contained file" output rule.

RSQ-5. Should a chart inside a bento tile need two nested .cn-* scopes — or should the template scope carry the dv chrome?

Finding 6. This is a canon shape question, not a lane's.

RSQ-6. F01 and F02 were both fixed in prose and neither is gated. Is that enough, or does each want a check?

Both are gone in this run, which is the evidence that prose works when it is read. It is also the evidence that nothing catches a consumer who does not read it.

Recommendation

Ship v1.0.9 with a caveat.

SHIP-WITH-CAVEAT. The thing v1.0.9 was cut for works: a blind build wrote three data specs, drew no geometry, and got three live charts that re-render on every filter — with all six engine files byte-identical to the pack (sha256 table above) and zero console errors across the drive. Both of cold run 5's live defects are gone under a playwright assertion.

The caveat is two lines long and neither is about the engine: the released zip is missing gen_provenance_receipt.py, so no consumer of the pack can pass either gate; and canon.css cannot style the Sidebar-nav or Filter-toolbar-bar markup it ships, which is the one thing in the render that looks broken. Both are one-line facts with named files, and both are yours to rule.

A recommendation, not a ruling.
