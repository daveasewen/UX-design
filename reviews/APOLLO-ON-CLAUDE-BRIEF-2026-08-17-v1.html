Claude is the interface.

Three layers, nothing dumbed down, nothing locked in.

The engine runs as an MCP server we own — the repo's existing Python is the implementation, not a rewrite. Working judgment ships as plugin skills. The visible surface renders as live artifacts. If Claude ever stops being the right front door, the same server fronts a standalone app. Market context: the plugin marketplace is live at scale, Skills 2.0 ships executable scripts, and no shipped design plugin enforces a design system with gates. That is the gap.

01
The engine

An MCP server we own

Owns store access, ruling reads, gate execution, theme and token generation, and render proofs. Ruling writes stay behind the existing single writer — unchanged. The server is a thin tool surface over the scripts that already exist.

Versioned as releases, with the same discipline as the designer-skills packs: a release is explicit and deliberate, never an auto-sync of live repo state.

02
The judgment

Skills in a plugin

Discover, Create, Craft, Dispatch as skills — plus the capture ritual and the review-presentation conventions: live variant spreads, light and dark, responsive, decision controllers. Skills call the engine's tools and hold no state of their own.

03
The surface

Live artifacts

Progress dashboards, variant spreads, review overlays, live tuners — persistent HTML views that call the engine on load. The review layer is already ruled a product feature; this is its delivery vehicle.

"Design is just the interface" holds in both senses: the visual layer is a thin skin over the engine, and Claude's surface is a thin skin over Apollo.

Positioning

Every shipped design skill nudges. Apollo enforces.

The most-installed design skill sells escape from average output — better taste through better prompting. Apollo's pitch is the enforced upgrade of that premise: ruled decisions, with gates that check output rather than hope for it. Public copy stays abstract — it sells the sensation, never the mechanics.

Existing design plugins

One-shot generators and token-syncers. Output is nudged by instructions; nothing verifies the result against a system.

Apollo on Claude

A design system with teeth: output checked against ruled decisions by the same gates that govern the repo today.

Consequences and pitfalls

A

A writing tool is a new inscription path

If any MCP tool ever writes rulings or store rows, the existing single writers must remain underneath — or the invariant silently dies. Read-only first is the fence.

B

Quota inversion applies

Users' quota pays for inference. Gates run server-side and return verdicts; streaming gate internals through the model costs five to ten times more.

C

A plugin release is a generator

Auto-syncing repo state into a released pack recreates the exact class the packs-are-releases rule fences. Release is explicit, versioned, and on Dave's word.

D

Artifacts cache their reads

A stale-looking dashboard becomes a support question, not a bug report. Every artifact shows its data's as-of.

E

This brief itself can rot

Its market premises age faster than its rules. Re-verify marketplace mechanics and Skills 2.0 behaviour at build time, not from here.

—
