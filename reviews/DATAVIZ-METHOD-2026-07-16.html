01The approach — custom SVG + token layer (to ratify)

Recommended in the desk research; restated here as the thing you're signing.

Charts are semantic SVG in the DOM, styled entirely by tokens, animated entirely by CSS, described by a real table. The stack:

Data a real <table> in the markup (visually hidden when a visual chart is shown)Doubles as the KB's required tabular alternative (dv-005) AND the screen-reader surface — one artefact, two obligations. For simple types the table IS the source the geometry reads from (the Charts.css idea, without adopting Charts.css).
Geometry small JS: data → x/y/arc coordinates, writes SVG elements + CSS custom propertiesBehaviour-only per rule 14 — JS positions things and wires toggles/tooltips; it never styles. Hard maths (nice ticks, time scales, stack layouts) via a scale helper — see decision 6 on hand-rolled vs vendored d3-scale.
Skeleton one SVG skeleton per chart type, classed .dv-*, variants via data-*The masthead move applied to charts: one skeleton, N variants by attribute, N brands by token mode. No per-brand chart forks — Apollo mono / HSBC / Apollo UI are token cascades (rule 15).
Style 100% tokens: --data-series-N fills, grey building blocks, spacing/border tokensFlat fills only (dv-009); fills bind to the V7 assignment; axes/labels/gridlines bind to mode-aware greys at ≥3:1 (dv-016). DEF-004 no-hardcode applies in full.
Motion CSS keyframes/transitions only: bars grow, lines draw, donuts sweepDEF-003-clean; honours prefers-reduced-motion; motion clarifies change, never decorates.
A11y accessible name + description on the SVG; letters A·B·C on elements; aria-live="polite" for updating values; decorative ticks hiddenColour is never alone (dv-011): letter + marker shape + position + direct label are the redundant channels.

Canvas is rejected — it forfeits token styling, per-element CSS motion, DOM inspectability (which is what makes charts gate-able), and the accessible tree. A canvas chart would be invisible to every gate we have.

Why this is the Apollo-shaped answer: the KB's chart rules are mostly statements about markup and computed style (gaps, fills, baselines, slice counts, contrast). SVG-in-DOM makes every one of them statically or render-checkable with the machinery we already run; the token layer makes the "one skeleton, N modes" factory thesis extend to charts for free.

02The vocabulary model

Axes for the machine, recipes for the designer — the anti-god-chart guardrail.

The model is a three-rung ladder: intent family (the KB's four: comparison-over-time · distribution · composition · relationship, plus the KPI/indicator family banking actually leads with) → type (line, bar, donut…) → variant (stacked, diverging, butterfly…). A variant is a data-* reconfiguration of its type's skeleton, not a new component — exactly the masthead's reveal-mode move.

Designers pick recipes, not variants: "Balance trend" (line), "Spend by category" (donut or stacked column), "Budget vs cap" (progress/bullet), "This year vs last" (grouped column), "KPI with delta" (stat card + spark). Recipe names stay simple + descriptive + channel-neutral, per the masthead naming ruling. The recipe table grows in the component catalog as types build out.

04Your four rulings, enacted

Quoted back for confirmation before they enter canon (nothing recorded as FIRM until you nod).

1 · Gain/loss — use the convention, override the rule consciously

Ruling (2026-07-16): the never-red/green orthodoxy is overblown — use the gain/loss convention, paired with sign/arrow/position.

Enactment: delta indicators may carry gain/loss colour, with +/− sign and ▲/▼ arrow always present (colour never alone, dv-011), zero-baseline position carrying the meaning where applicable. Two colour options rendered on the decision sheet (§05). Proposed override wording (records the conscious exception you asked for):

Draft override — for your sign-off, verbatim or edited "OVERRIDE (RULED Dave 2026-07-16, scoped): gain/loss DELTA INDICATORS (text, arrows, spark end-values, RAG-style cells) may use red/green semantic colour in data visualisations, as a conscious exception to col26-012 (no HSBC Red alongside the supporting palette in charts) and to the red-reserved-for-primary-action rule — DELTAS ARE DATA SEMANTICS, NOT ACTIONS, and do not count against red-once-per-screen. SERIES FILLS remain supporting-palette only (dv-017). Sign + arrow are mandatory companions (dv-011)."
Note the second rule this touches: the 07-14 red rule (red = primary-action accent, once per screen). If a screen has a red CTA and three negative deltas, the once-per-screen count must exclude deltas — that's what the wording above pins.

2 · Texture — sparingly and stylishly

Ruling (2026-07-16): one chevron-style pattern max per chart, still flat — not a zoo of hatchings.

Enactment: one SVG <pattern> (chevron) in the kit's defs, flat two-tone from the series' own token (no gradient, dv-009). Usable on at most ONE series per chart — the gate counts pattern references (§06). Round-one includes it on the stacked column as the proof; decision 7 covers whether it ships in R1 or waits.

3 · Legends — colour + letter + name

Ruling (2026-07-16): legends are fine, with an alphabetic signifier; letters repeat on the elements.

Enactment: every multi-series chart labels elements A·B·C·D·E and its legend rows read [swatch] [letter] · [name]. The letter is the colour-independent channel; line charts additionally keep per-series marker shapes (dv-line-002). Rendered live across the whole decision sheet. Becomes a kit rule + a gate check (letters present when series ≥2).

4 · Variant-complete inventory

Ruling (2026-07-16): enumerate ALL sub-variants — butterfly/tornado, segmented, waterfall, the lot.

Enactment: §03 above — 41 items, tiered, each tagged by intent family. Feeds the itinerary as the DataViz section (the itinerary's 124 items pre-date this enumeration; reconcile on next itinerary refresh).

5 · Avoid vibrating boundaries (added from your article, 2026-07-16)

Ruling (2026-07-16): avoid the vibrating-boundaries effect — adjacent, highly saturated, near-complementary colours at near-equal value shimmer at the edge; an accessibility hazard (astigmatism, sensory processing) that you confirmed live on the D2 dark red/green pair ("they dance a little"). Source: Tuts+ "Vibrating boundaries: making colors pop" (MacDonald, 2024) — an Apollo-added rule, not an ingested HSBC one.

Enactment: the risk is quantifiable — all three legs together: pair value-ratio <1.25 + hue separation ≥135° + both HSL saturations ≥0.5; breaking any one leg kills the shimmer. Rolled in three places: (1) receipts — every candidate set, delta pair and suggestion range on the render sheet now carries adjacent-pair vibration receipts, and the tokens holding pen records the worst level per range; (2) fixes applied — D2/D1 delta pairs value-split in both modes (the receipts caught light mode too, not just the dark pair you saw); suggestion ranges rebuilt across the palette's step-ramps so adjacent picks are value-stepped; (3) gate — an advisory adjacent-pair check joins _validate_dataviz.py (thresholds tunable, promote after bite-test). Structural note: the dv-004 ≥2px surface-coloured gap is itself the classic defence — a neutral boundary between fills; the check protects the gapless surfaces (legends, adjacent text, touching edges).

08Open decisions — the markup list

  1. Ratify the approach (§01): semantic SVG + tokens + CSS motion + table-as-a11y-spine; canvas rejected.
  2. Series assignment (render sheet): A / B / C, or a marked-up mix.
  3. Delta treatment (render sheet + §04.1): Option 1 RAG tokens + the drafted override wording, or Option 2 in-palette pair. Confirm or edit the override text verbatim.
  4. Scope of dv-014 consistency: within-mode only (A/B) or across the theme switch (C). Record either way.
  5. Inventory tiers (§03): confirm the R1/R2/M/X boundaries, or move items.
  6. Maths helper: hand-rolled scale/ticks first (zero dependencies, portability-friendly) vs vendoring d3-scale now. Recommendation: hand-rolled until a type actually needs more (time scales will likely be that moment).
  7. Chevron texture: prove it in R1 on the stacked column (recommended — it's the ruling's testbed) or defer to R2.
  8. Gate plan (§06): approve advisory-first set + the blocking set, and that _validate_dataviz.py lands with the first chart.
