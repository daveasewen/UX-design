Amount entry (itinerary row 17) — the Input-fields boxed chrome given a money contract. It consumes the display primitive's conventions: code before value, typographic minus, grouped thousands, tabular figures.

Every pane below is the real gated snippet markup, copied verbatim and rendered through the generated canon.css — not a redraw. Four Apollo themes, each light and dark. It was built, gated and generated on 2026-07-22 (Phase-2 wave 1) and has a snippet, a meta, a .cn- canon partial and a showroom page. The itinerary row is stale by five weeks. Nothing was rebuilt here; what was missing was this — a four-theme surface for your eye. Correcting the itinerary is yours, not a sub's.

Open — the standard amount field is 39px tall, in every theme, at every width. Measured in a real browser: the standard .ai-box renders 39px high at both 1180px and 480px — 5px under the ruled 44px minimum hit area. The display variant is 75px and is fine. This is the field a customer taps to enter money on a phone, so it is the one that matters most. No gate enforces the 44px minimum today (the token exists at base tier but nothing reads it), which is why a gated component has carried this since 2026-07-22 without anything going red.

PROPOSED #203, your eye owed: lift the box padding from 8px 16px to 10px 16px (43px) or 11px 16px (45px) — the second clears the minimum, the first does not, and the choice changes the field's proportion against the label, so it is a look decision, not a maths one. Yours. Separately, a hit-area gate is the durable fix and is proposed to the conductor for _DS-IMPROVEMENTS.md.

What you are looking at is missing two dark-mode rules — and the screenshot is how we found out. In the dark panes above, the error roundel renders red. In the gated snippet it is ruled white shape with a black mark ("policy dark"), and the dark error border is ruled to go full red. Neither rule reaches canon.css.

Cause, quoted: gen_canon_components.py drops any rule whose selector startswith("[data-theme"). That is right for the harness variable blocks ([data-theme="light"]{--page:#FFF}) and wrong for a component rule that merely happens to be dark-scoped ([data-theme="dark"] .se-msg .ic{color:#FFFFFF}). The very next function in that file already has commented machinery for keeping a leading root-ancestor at the front and scoping the descendant after it — the drop test just fires first, so that machinery never sees these rules.

It is not this component. Probed across the library: 33 rules in 19 of 76 snippets are silently absent from canon.css the same way — Notifications (4), Form-layout (3), Input-fields (3), the date/time pickers, Textarea, Stepper, four charts. Every gate is green on all of it, because no gate compares the snippet to the partial generated from it. PROPOSED #203 to the conductor for _DS-IMPROVEMENTS.md: discriminate the drop (no descendant = var block, drop; has a descendant = scope it), plus a gate that parses the generated partial in its own grammar. Neither is a sub's to make — this lane may not touch a shared generator.
