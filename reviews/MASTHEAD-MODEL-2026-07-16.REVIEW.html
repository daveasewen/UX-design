The Masthead — one switchable pattern

The global header and the content-heavy masthead are not two components. They are one masthead pattern that reconfigures by intent — and the thing that felt tangled is that three separate layers were being decided as one. This is the model, its labels, and how it maps onto what we already built.

Synthesised 2026-07-16, built collaboratively with Dave, from a research pass across Nielsen Norman Group, IBM Carbon, Shopify Polaris, USWDS, and Material 3. Status: labels signed off 2026-07-16 (Dave) — Layer-1 name = Shell (+ optional footer); recipes named; mode labels kept provisionally pending user feedback. See §06 for the resolved decisions. 00What was tangled

Three different questions, at three different layers, were being answered as if they were one.

The knot was that these got bundled together:

  • Does the masthead show its links flat, or hide them behind a mega? — a property of the masthead.
  • Is there also a side nav, or in-page links? — a property of the page, driven by how deep the information architecture is.
  • What is each of those regions actually for? — a role, not a component.
Dave's own examples split cleanly along these lines. "A flat menu — top level exposed, no mega — might be used in isolation, or with a side menu, or with an in-page links list." That is one axis (flat) crossed with another (what else is on the page). "Some might use a mega paired with another type — it all depends on depth of the IA, future scaling, or designer preference." Depth drives the pairing; the masthead's own behaviour is separate.

Untangle those three and the god-component risk disappears: the masthead owns only the first question. The rest lives one layer up.

02The masthead's own axes

Not granular parameterisation — a small closed set, categorised by intent. The reveal mode is a ladder of increasing IA depth.

minimal
Brand + utility only. No primary nav in the bar — it lives elsewhere (side nav / in-page) or the context is a focused app. Precedent: Polaris Frame (nav in the sidebar).
exposed
L1 links inline, no panels. Shallow, stable IA — roughly ≤6 top items, one level. Show it all. Precedent: USWDS basic header. Evidence: exposed beats hidden by a wide margin (NN/g).
exposed-mega
L1 links inline, each opens a mega. Broad and deep — show the top level, reveal the rest on demand. This is your "exposed header that also invokes a mega." Precedent: USWDS mega header.
trigger
One door opens a panel holding the nav. Deepest / most flexible — carries the modifiers below. Precedent: content-heavy masthead; our current .mm-masthead.

The trigger modifiers

Everything that felt like "more modes" is actually variation inside trigger. This is where depth and emphasis live.

Prominence
primary (nav is the star — brand-led / marketing) or index (deliberately tucked, low-frequency — the well-configured dashboard where nav is an occasional index). Index is a subset of trigger, not a peer — prominence only means something once the nav is behind a door.
Affordance
burger (plain menu control) or menu+search (a combined control that opens a panel leading with search, then browse — the common mobile pattern). Pairs especially well with index, where search is often the fastest way in.
Panel layout
cols (1 level) · featured (+ journeys rail) · tabbed-vertical (L1 tabs → L2 columns → L3 links = 3 levels) · tabbed-horizontal. This sub-axis is what carries IA depth — a 3-level structure lives here, not in a new top-level mode.
Tuck-by-intent ≠ collapse-by-necessity. The index prominence tucks the nav at all widths because it is incidental. That is different from the automatic responsive collapse to a drawer at narrow widths, which happens under every mode because there is no room. Same drawer, different reason — keep them distinct.

05The search rule

Search can appear in the bar and inside the mega/panel. Here is when that is fine and when it is redundant.

Both global?
Fine. Two entry points to the same global search is acceptable — in trigger/index modes the bar is stripped down (brand + door), so the bar-search and the panel-search never sit inches apart competing.
The finesse
(Dave)
The masthead search icon disappears when the panel/mega search is present or open — so you never see two global searches at once. This is the clean resolution of the redundancy worry.
Combined control
The menu+search affordance folds the two together into one door — the search is the top of the opened panel. Most natural in the index recipe.
Accessibility
Two search fields = two landmarks. Either give each a distinct accessible name ("Search", "Search menu"), or expose only one to the accessibility tree. Do not ship two unlabelled, identical search landmarks.
Scope note (settled as "same global" for now): if a future context wants the panel search scoped to that section (e.g. "Search payments") while the bar stays global, that is a legitimate variant — but it must be labelled to show the difference, or it reads as a duplicate. Parked, not adopted.

07What this unlocks

Beyond tidying the component — this is a proof and a seed.

One component, many use-cases factory proof

A single .masthead skeleton that reconfigures across five real intents via a data-mode attribute + a small prop set is the pro-forma programme thesis made visible. It is a strong artefact for the "one skeleton, N modes" story — the switch UI reconfigures one live instance across use-cases.

The component API falls out of the model build

Reveal mode → data-mode (declarative, CSS-driven). Prominence / affordance / panel-layout → modifier classes or props. Utilities → boolean toggles. Motion stays CSS-only; JS only for disclosure open/close, focus, keyboard. The recipes become documented presets.
