Hierarchical component libraries a machine can compose from

1Atomic-design tier models — who still uses it, what replaced it

What the practice isBrad Frost's 2013 atoms/molecules/organisms/templates/pages model is still the shared vocabulary everyone learned from, but almost no large production system enforces its strict five-level tree today. Systems instead use a shallower, looser hierarchy: components + patterns (composed groups) + sometimes templates, with the deeper structure captured in relationships/graphs rather than a fixed level number. Atlassian has explicitly said its "neat three-tier model" now behaves more like a constellation — a web of interconnected decisions that designers, engineers and AI navigate as a decision tree, not a rigid ladder. IBM Carbon keeps a plain two-tier split: Components, then Patterns (named, reusable combinations of components + templates solving a user goal), plus a separate closed/open "Pattern Asset Library" for cross-component product patterns. Shopify Polaris references Frost's atoms-to-organisms analogy in its own writing but organises its actual library as Foundations / Components / Patterns, not four strict tiers. USWDS and Material 3 both use component + pattern/template layers without adopting atomic-design naming at all — Material 3 instead layers reference tokens → semantic/system tokens → component tokens, which is a token hierarchy, not a component hierarchy.

Fit for Apollo — the meta.json knowledge graph is closer to Atlassian's "context engine / constellation" model than to a rigid four-tier tree; keep atoms/molecules/organisms as optional human-readable labels on graph nodes, never as the structural spine.

2Slot mechanisms — modelling "patterns with injected contents"

What the practice isFigma announced Slots at Schema 2025 (November 2025), rolling out as open beta from March 2026: a slot is a placeholder container inside a component that lets you add, remove or swap content in an instance without detaching it, and — critically — a slot can be constrained to only accept specific instances/types, enforcing design-system compliance at the injection point. Figma is explicit that this is a different axis from variants: variants describe component STATE (open/closed, active/inactive); slots describe what CONTENT can be inserted. On the code side, the same idea has two mainstream implementations: the web-platform native `` (Shadow DOM, named slots) and the React convention of `children` plus the Radix UI `Slot`/`asChild` pattern, where a component supplies behaviour and the consumer supplies the actual rendered element — true composition rather than a fixed prop surface. Figma's older "component properties" (instance-swap, boolean, text, variant properties) remain the finer-grained single-value mechanism and predate Slots; Slots is for whole regions of repeating or free-form content (task lists, tabs, card bodies, modal contents).

3Embedded contextual variants — one component, many contexts

What the practice isThe 2025 consensus mechanism for "a component behaves differently depending on where it sits" is CSS container queries plus style queries, now supported across all evergreen browsers: a component (e.g. a card) reads its own container's size or a custom-property "mode" set by an ancestor, and adapts layout or token values automatically — no JavaScript, no forked markup. Style queries specifically let a parent set a custom property (e.g. `--surface: card`) that descendant components query to resolve which token alias to use, which is effectively contextual re-theming through the cascade. On the Figma side, the equivalent is Variables with multiple modes (light/dark/high-contrast, and now nested per-frame mode overrides) plus aliasing, so a component references a semantic variable and the surrounding frame's mode decides the resolved value. Material 3 formalises the same idea in its token model: component tokens alias semantic tokens rather than literal values, so a single Button component resolves differently depending on which semantic context it's placed in, without being a different component. The industry's practical ruling on "is a button-in-a-card the same button": yes — re-skin via token alias/container query; forking into "CardButton" is treated as design debt, not a pattern.

4Generative composition — pattern lexicons a machine can build from

What the practice isThe W3C Design Tokens Community Group's Design Tokens Format Module reached its first stable release, 2025.10, on 28 October 2025 — a vendor-neutral JSON format for design tokens, with theming and modern-colour-space support, backed by Adobe, Amazon, Google, Meta, Microsoft, Salesforce and Figma. It is a Candidate Recommendation, not a full W3C Standard, but it is now the de facto interchange format tools are converging on. Separately, current AI component-generation systems (surveyed across the "awesome-generative-ui" corpus and vendor write-ups) have converged on constrained/declarative generation: agents emit output drawn from an allow-listed grammar of approved primitives/components rather than freeform code, precisely because unconstrained generation breaks brand and accessibility consistency. The clearest prior art for a "pattern lexicon" that tooling can generate FROM is Pattern Lab (Brad Frost & Dave Olsen, from 2013) — a static-site generator that assembled pages from a declared library of atoms/molecules/organisms via includes, the direct ancestor of today's Storybook-based component-driven development. Academic work (e.g. SpecifyUI, arXiv 2509.07334) is now formalising "structured specification + generative AI" as a research topic, confirming this is an active, not solved, frontier.
