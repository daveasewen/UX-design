Four repairs, as pixels

#228 · L8 the straight underline · s227-D7 the concentric thumb · the library icon on the FAB face · the hot-corner reveal — all four live, none previously rendered

Page chrome
Corner

What is being asked. Nothing on this page is a proposal. All four are already in canon; the question is only whether they look right. Say so per row, and say plainly if one does not.

  1. The underline stays straight. The radius now lives on the boxed variant only. In console — the one rounded theme — the box takes a corner and the underline keeps its ends.
  2. The thumb is concentric at m and l. Console only. The other three themes are square at every scale, on purpose.
  3. The FAB wears a library icon, not a hand-drawn gear.
  4. The FAB hides until you go to the corner. That is now the default everywhere.

One thing to know before you touch the FAB. Its Theme buttons write data-apollo-theme onto this page's <html> — that is the overlay working correctly. But canon has no mono block (mono is the base), so a theme set at the root inherits down into the four pinned columns below and will round corners that are meant to be square. That is canon's cascade, not a defect in the spread. Reset page attributes puts it back, and the measured table at the foot of each specimen always tells you the truth about what is actually resolving.

Specimen 1 · L8 · #228

The underline stays straight; only the box takes a corner

Two search fields, the same component, side by side in every theme and both modes. Top: the boxed variant. Below it: the plain underline. The radius binding is unchanged — --border-radius-control still resolves per theme on this component — it is now only consumed by .search.boxed: :where(.cn-search-field) .search.boxed{border-radius:var(--border-radius-control)}. The base .search rule declares no radius at all.

#227's canon-gap B5 had put the radius on the base rule, following Dropdown's .trigger and Input-fields' .uctrl input. Dave overruled that precedent on the eye: an underline is a straight line, and rounding its ends bends the stroke and nothing else. Console is the only theme where the difference is visible, because it is the only theme with a non-zero control radius — that column is the one to look at.

Measured, live, from this page

getComputedStyle().borderTopLeftRadius on each field as it is actually rendering right now. Expected from canon: the underline is 0px in every theme; the box is 0px except console, where it is 8px. If a number disagrees, the number is the fact.

Specimen 2 · s227-D7 · #228

The sliding thumb is concentric with its track at every scale

All four minted scales — xs 24 · s 36 · m 44 · l 48 — in all four themes and both modes. Console at m and l is the new thing: --border-radius-segmented-thumb-m: 8px and -l: 8px, which is each track's own radius minus its inset padding (10 − 2 and 12 − 4). Before the repair both were 0 and the thumb sat square inside a rounded track.

Mono, Legacy and Supercharge are square at every scale, by ruling (s201-D5): the concentric pair is minted under [data-apollo-theme="console"] only. If you see a rounded thumb in any column but console, that is a fault — say so, and it gets fixed at source rather than on this page. Click a segment: the thumb slides, and the corner travels with it.

Measured, live, from this page

Track radius and thumb radius per scale, as rendered. Expected from canon: console 6/8/10/12 outside and 4/6/8/8 inside; every other theme 0 on both, at every scale.

Specimens 3 & 4 · #228

The overlay: what is on its face, and how it arrives

Both panes below load the same real file, knowledge/_render/apollo-fab.js. Nothing is excerpted or re-drawn. Each pane is the FAB's container, so its "corner" is that box's bottom-right rather than the window's — on a real page the layer is fixed and the corner is the viewport's.

Both panes hold a copy of the same two reference components, so the FAB's Inspect switch has something real to name when you hover it.

Specimen 3 — the library icon on the face

The button is visible in this pane and nowhere else. Reveal is forced to always here, purely so the face can be looked at without hunting for it; the shipped default is the pane on the right.

The glyph is knowledge/assets/icons/global-controls/settings.svg, copied byte for byte from the library — its 18×18 viewBox, its single evenodd path, its currentColor fill, scaled into the 24 px box by the overlay's own CSS. What it replaced was a hand-drawn gear nobody had reviewed, in a pack whose first rule is never to invent an icon. Zoom in on it; that is the whole question.

The disc itself is button/primary/background/default of whatever theme the host page is wearing — ink here, because this page is mono and mono's primary action is ink, not red. Switch the FAB's own Theme to Common and it goes red. That is the overlay inheriting the page, not a colour choice made in the overlay.

Bottom-right, always present.

Specimen 4 — the hot-corner reveal (the default)

Move your mouse into the bottom-right corner of this pane. Nothing is drawn until the pointer enters a 72 px × 72 px zone there; then the button fades in. Move away and it fades out again. On a touch screen there is no hover, so a tap in that same corner reveals it.

This pane is mounted with no reveal option at all, so it is showing the file's own defaults: REVEAL_DEFAULT='hotcorner' (it was always) and CORNER_DEFAULT=72. Those live values are read back in the strip below. Show the 72 px zone in the top bar draws the corner so you can see where it is. The zone is measured from pointer coordinates, never a hit-testing box, so nothing sitting under that corner is ever intercepted.
