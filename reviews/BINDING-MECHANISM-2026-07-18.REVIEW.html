CORRECTION

Option (a) is structurally larger than “add a class”.

.t-cm-button sets only font-size, font-weight, min-height. The cap-trim machinery — the thing that actually seats text in the 4px slot — lives on .t-cm and on a .txt child:

.t-cm{display:inline-flex;align-items:center;}
.t-cm > .txt{line-height:1; text-box:trim-both cap alphabetic;}

So a correct Component binding is not one class. It is:

<button class="btn t-cm t-cm-button"><span class="txt">Confirm payment</span></button>

Why it matters: Two classes plus an inserted element, per text-bearing node, in the files that are the visual reference. And display:inline-flex on a button that was previously inline-block is a layout change, not a type change — it will move things. Editorial (.t-ed-*) has no such structure and is genuinely one class. The two tiers are not equally cheap, which is your D2/D3 ruling showing up again in the plumbing.

(a) — markup class

Add .t-cm + .t-cm-* + a .txt child to every Component text node; .t-ed-* to every Editorial one.

Impact: Most legible option — you can read a component's type off its markup, which is the best possible answer to “retrieval, not recall”. But binding becomes welded to markup, and the three libraries are supposed to be one skeleton with token overrides. The moment a mode wants different type structure, markup diverges — and divergent markup is the first step of the fork the architecture forbids. Leaves the 152 canon.css violations entirely unaddressed.

(b) — CSS composition via custom properties

Components keep their selectors and pull values: font-size:var(--t-cm-button-size). Precedent exists — .cn-button .btn{font:var(--weight) var(--fs)/1 var(--font)} already does this.

Impact — and the finding that decides it: Custom properties carry values. Cap-trim is not a value, it is a pseudo-element pair and a required child. No custom property can deliver text-box:trim-both to a child that doesn't exist. So (b) cannot express the Component tier at all — it would work for Editorial and silently drop the trim on everything else, which is precisely the class of failure DEF-006 was written to catch. It also requires rewriting type.css from a class library into a property library, i.e. throwing away the composites you signed off on 07-17.

My read: this one is dead as a whole answer. Its flexibility is real but it cannot carry the tier that matters most.

(c) — build-time inlining

The canon.css generator folds composite declarations into component rules at build time.

Impact: A generator can only fold into what it generates. It covers the .cn-* region and not the hand-authored .c-* composition layer — which is where 152 of the violations live — and not the 630-odd in hand-authored snippet and tranche <style> blocks, which nothing generates. It also costs you traceability: devtools shows font-size:16px, not .t-cm-button, so the composite name survives only in the generator. That is a direct trade of auditability for tidiness.

(d) — generated selector-list extension — not on your original list

A mapping file (knowledge/canon/type-bindings.json) names which component selectors bind to which composite. A generator appends them to the composite's own rule as a selector list:

/* generated from type-bindings.json */
.t-ed-body, .c-summary__k, .cn-list-items .row .desc { font-size:16px; line-height:24px; font-weight:400; }
.t-cm-button, .cn-button .btn { font-size:16px; font-weight:500; min-height:20px; }

Robust: one source of truth, and the mapping is a small machine-readable file a gate can check exhaustively — “every text-bearing selector in the corpus appears in the map exactly once” is a checkable claim, which is more than (a), (b) or (c) can offer. It also makes orphans visible: a component nobody bound shows up as a missing key rather than as silence.

Flexible: rebinding a component is one line of JSON. No markup churn, no CSS churn, no re-inline sweep of hand-authored files. Adding a mode is adding an override block, same as today.

Standards: plain CSS selector lists — no preprocessor, no @extend, nothing a browser or a new starter has to be taught.

The costs, stated honestly:
— Cap-trim still needs the .txt child. (d) solves values and sizes everywhere, but the Component tier's trim structure is markup, and no CSS mechanism removes that. So (d) does not eliminate the markup pass — it shrinks it from ~230 nodes to only those Component nodes that need trim, and defers the rest. That must be measured before you commit, not asserted.
— Cascade order becomes load-bearing. Composite rules live in type.css; component rules that must still win need to come after, or need the map to own them too.
— type.css becomes genuinely generated, which fixes the false header in §1 but means the hand-authored composites move to a source file. That is a real change to a file you reviewed and signed off nine days ago.
