Why this is text, not fill — one line

In the fills, meaning is carried by the label and the roundel glyph, so fill contrast is a salience lever, not a legibility requirement (R-D6). On the amount-display numeral, meaning is carried by the sign — U+2212 minus for negative, no sign for positive/zero — so colour there is also salience, not the only channel. But text carries a second obligation fills do not: it must be readable (WCAG 1.4.3), independent of what it means. That is the only reason these four values must clear 4.5:1 — and, as of v2, clear it on the ground it will actually sit on, not just on pure white.

#FFFFFF — page ground, light #1A1A1A — page ground, dark ("digital black")

A mode-invariant AA-text value is arithmetically impossible for either hue: text on white needs relative luminance L ≤ —; text on #1A1A1A needs L ≥ —. This bound is about the two PURE page extremes and is independent of the ground selector below — it is why the tool tunes four values, not two. Colour model

HSB is primary — Dave's words, the Figma convention. OKLCH drives saturation via chroma and brightness via lightness instead; the repo's own colour notes are already written in OKLCH (knowledge/tokens/semantic-colour.json $note fields). Hue stays locked either way. Correction from v1's framing, found while driving this build's own hue-drift readout: v1 described the two models' hue readings as differing "by a fraction of a degree" when the other model drives — measured live, that holds for red but green's HSB-reconciled seed reads ≈3.1° away from the locked OKLCH hue when read in OKLCH terms, which is not a fraction of a degree. That gap is a structural property of reconciling in one hue space and measuring in the other (HSB-hue and OKLCH-hue are different constructions, not perfectly interconvertible) — it is present even with zero gamut clipping, so the hue-drift alarm below is keyed only to whichever model is currently driving, never to the other model's cross-read.

Method: WCAG 2.x relative-luminance/contrast formula, read from rendered getComputedStyle colour for the foreground text, never a hard-coded ratio; ground hexes are parsed directly (they are literal #RRGGBB constants with no CSS indirection, so a DOM round-trip adds nothing). OKLCH via Björn Ottosson's public sRGB↔OKLab↔OKLCh coefficients (same matrix as v1 / reviews/_rag_colours_calc.py). Gamut guard: chroma is clamped to the largest value that keeps oklab2rgb(L,C,H) in [0,1] per channel at the CURRENT lightness and the LOCKED hue, found by binary search (28 iterations, ~2×10⁻⁹ resolution) — the CSS Color 4 "reduce chroma toward the achromatic axis" gamut-mapping strategy — so hue is a constant of the search, never an output of it. Worst-ground reading recomputes the same formula against every ENABLED ground's hex for the cell's own mode (light cells against light grounds, dark against dark) and reports the minimum. CVD preview via Machado/Oliveira/Fairchild (2009) dichromacy matrices, SVG feColorMatrix in linearRGB — an approximation for information, not a clinical tool.
