type.css line 180 — the dark-mode background — which shade should win?

Rolled from #106 (declined blind) to #107. This page does not pick a side — Option A and Option B are both shown live below; you rule by eye. Radios are unselected on purpose.

Every dark-mode screen in Apollo is meant to use one near-black shade: #1A1A1A. Right now it doesn't. One styling rule inside type.css is written more strongly than the rule that carries the correct colour, so every dark pane actually renders a different shade: #111. The two shades sit nine steps apart on a 0–255 scale — close enough that no one sentence can settle it. That's why this is a specimen and not a written description.

Both shades here are pure grey. Red, green and blue are equal in each one — there is no hue anywhere on this page. Your usual caution about red and amber shifting unstably on screen does not apply here; this is a lightness call only.

Left = Option A, today's actual render. Right = Option B, the declared token value. The two panes are pushed edge-to-edge on purpose: a nine-step difference is easiest to catch exactly where the two backgrounds touch, in the middle.

Which shade should the dark background be?

Technical detail — the rules, the measurement, and what the #106 record got right and loose

Confirmed against the live file (knowledge/canon/type.css, read 2026-08-06):

LineRuleSpecificity
180[data-theme="dark"]{background:#111;color:#fff;}0-1-0 (one attribute selector)

This matches the #106 record exactly: value, line number, and specificity all check out.

One thing the record's shorthand doesn't quite say: there is no literal body{background:var(--page)} line inside type.css itself. That exact pattern — body{margin:0;padding:2.5rem;…background:var(--page);color:var(--text);…} at specificity 0-0-1 — lives in every consuming snippet's own local stylesheet (e.g. knowledge/snippets/Account-card.reference.html:32, the file this specimen uses). Each snippet also declares its own local [data-theme="dark"]{--page:#1A1A1A;…} block that sets the custom property (not background directly). So the cascade fight is real and produces exactly the outcome #106 recorded — the record's phrasing just names the generic pattern rather than a single line inside type.css. Independently, canon's own token chain agrees on the value: canon.css:568 --background-default:var(--surface-digital-black) → canon.css:742 --surface-digital-black:#1A1A1A. Three independent sources (the record, every snippet's local token, and canon's token chain) agree the intended dark background is #1A1A1A; only type.css:180's literal #111 disagrees.

A second, currently-silent instance of the same defect: line 180 also sets color:#fff at 0-1-0, beating each snippet's own color:var(--text) at 0-0-1. Today this is invisible because every snippet's dark --text also resolves to white — but it's the same literal-over-token pattern ADR-0014 flags, just with no visible consequence yet. Worth knowing regardless of how the background is ruled.

Not the same bug, don't conflate: line 177's .spec-h{…color:var(--text,#111);} also contains the string #111, but that's an unrelated var() fallback (used only if --text is undefined) — it plays no part in this cascade fight.

How Option B was built for this specimen: a scratch copy of type.css (reviews/_assets/type-css-180-specimen/type-fixed.css, NOT canon, never loaded by anything else) with line 180's value changed from background:#111 to background:var(--page) — same selector, same specificity, only the value swapped to reference the token instead of the literal. That is one possible mechanical fix among others (raising the specificity of the token-carrying rule instead is another); this specimen shows the resulting colour only, not a prescribed code change — which mechanism ships is a separate, later decision.
