EXISTENCE QUESTION 1 OF 2 — NOTHING BELOW IS DECIDED

Is the product’s statement a LIST or a LEDGER?

#204 Lane N ruled itinerary row 91 (“Transaction / ledger row”) a DUPLICATE and built nothing: list-items.meta.json build.$status reads, verbatim, “PROMOTED 2026-06-22 (Dave) — TRANSACTION row brought to the Tabs-bar standard”. #209 Lane A built only the form that adjudication does not cover — the ledger: an ordered statement with a running balance, column heads and a closing total. The tappable transaction row was not re-drawn.

  • If you rule LIST — transaction-row should not exist. Row 91 is marked Duplicate pointing at List-items, and the new snippet and meta go. Nothing registers them (they are absent from gen_showroom CATEGORIES), so removing the pair costs nothing downstream.
  • If you rule LEDGER — transaction-row stands as a SECOND component alongside List-items, and the boundary between them — tappable list row vs ordered statement — becomes a thing the library states. Row 91 stops being a duplicate.
  • Any third answer is yours to name — Nothing on this page proposes one, and nothing here is decided.

EXISTENCE QUESTION 2 OF 2 — NOTHING BELOW IS DECIDED

Keep limits-meter as its own component, or fold it in?

progress-bar.meta.json relationships.commonPatterns already names the use, verbatim: [… "savings goal / limits meter" …]. Progress-bar’s third specimen is already a non-percentage determinate bar (“Savings goal · 1,450 of 2,000”) carrying its domain units in aria-valuetext. The new component’s bar is Progress-bar’s, copied byte-for-byte; what it adds around the bar is the limit framing — cap, reset, remaining, and a within-limit / approaching / at-limit status vocabulary.

  • If you KEEP it — The library carries a limits meter as its own row, and the overlap with Progress-bar is a stated boundary rather than an accident.
  • If you FOLD it into Progress-bar — The component goes and the pattern is served by a Progress-bar with a domain aria-valuetext — which is what its meta already claims.
  • If you MERGE it with Runway-bar — It becomes a parameterised “allowance” mode of that component. ⚠ Limits-meter vs Runway-bar is a SEPARATE open question (receipt Q9) and is not put on this page: a runway’s ceiling is a fact about your money, a limit’s ceiling is a rule about your permission.

How the specimens are loaded, stated plainly. Each pane’s <iframe src> is a relative path to the real snippet in knowledge/snippets/. In light, that live file is what you see. Switching to dark sets data-theme="dark" on the specimen’s <body> directly when the browser permits it (it does over http://). Opened straight off disk over file://, Chromium gives every file its own opaque origin and returns null for the frame’s document — measured, not assumed — so the page falls back to re-serving the byte-exact bytes of the same file, embedded at build time, with exactly two mechanical substitutions: the <body> theme attribute, and href="../canon/type.css" rewritten to href="../knowledge/canon/type.css" (a srcdoc inherits this page’s base URL, and without the rewrite the shared type stylesheet drops silently).
