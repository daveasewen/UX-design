08 · Data believability

Plausible corporate international banking, not placeholder. Five named legal entities with countries and BICs; 12 accounts with IBAN-shaped identifiers across GBP/EUR/USD/SGD/HKD/JPY; 50 payment instructions naming Siemens Energy, Maersk Line, PSA Corporation, Li & Fung, ADP, HMRC and four intercompany sweeps; eleven corridors; five statuses; four real channels (SWIFT gpi, SEPA, Fedwire, CHATS, FAST, ACH, CHAPS). Mid-market rates and a prior month drive a real FX move column.

One believability wobble, and it is arithmetic, not content: "Payments out +497.6% up" and "Group cash position −53.6% down". The prior-period comparator is the same-length window immediately before, and the ledger thins out beyond 30 days, so short windows produce violent deltas. A real product would compare like for like or suppress the delta below a row-count floor. Called out rather than hidden.

10 · Findings

  1. s258-D3 fixed the snippets and left canon.css behind — --demo-width still governs 28 component widths.

    knowledge/snippets/Data-grid.reference.html:125 now reads .dg{width:100%; max-width:var(--dg-max, 760px);} with a comment naming s258-D3. knowledge/canon/canon.css:10341 still reads :where(.cn-data-grid) .dg{width:var(--demo-width, 760px); max-width:100%;}. git show --stat 5c241f7 touches 55 snippet files, the skill and the receipt gate — and not canon.css; git log -L 10341,10341:knowledge/canon/canon.css dates that line to 0272996, 22 August, #215.

    The consequence is not academic. Skill step 3 tells the builder to drop a component in as "its scope class + the snippet's own markup" — i.e. to link canon and wear cn-data-grid. A page that does exactly that inherits the demo dial: the grid sat at 760.00px inside a 1,311.98px content box, 552px of dead band, Amount column clipped, and the author's --dg-max:100% override computed correctly and changed nothing because the binding declaration is width, not max-width. grep -c demo-width knowledge/canon/canon.css = 36, of which 28 are width:var(--demo-width, …) on a component wrapper.

  2. The Filter-toolbar-bar's open-state contract is invisible to a blind builder, and three filters died on it.

    Canon binds the menu to .menu[data-open="true"] (canon.css:11710). The snippet's own script sets that attribute (Filter-toolbar-bar.reference.html:415). The builder read the snippet's markup range, found no script there, wrote #behaviour-manifest saying "script": null — and wired .open on the wrapper instead. Measured result: aria-expanded="true", opacity: 0, pointer-events: none, elementFromPoint returns the toolbar. Three listboxes, all dead.

    Two things are true at once. The builder should have read filter-toolbar-bar.meta.json's behaviour.script address, which names the script exactly. And nothing in the skill's procedure sends it there: step 2 says read the contract for "variants, states, antiPatterns, relationships" — it does not mention behaviour, which is where rule 2a's address lives. Rule 2a assumes the builder already found the script.

  3. s258-D3's new refusal cannot fire on the population it was built for.

    Driven, not read. The frozen page and a mutant with one harness-bar fence pasted back in were both put through _validate_receipt.py. Without a receipt, both return the same thing: FAIL:NO-RECEIPT, verdict identical, the fence never looked at. After gen_provenance_receipt.py --mint: clean → PASS, mutant → FAIL:DEMO-CHROME-COPIED.

    So the clause works, and a first-run generated page can never reach it, because ADS-generate-from-canon never tells the builder to mint a receipt — rule 2a says "carry that address into the page's receipt" as though the receipt already exists.

  4. The compose gate fails a page for copying the Data-grid snippet exactly as rule 2 instructs.

    compose: ❌ 2 native radio/checkbox not composed from .cn-selection-controls (.radio/.box). Both are the Data-grid's own .cbx checkbox markup, carried byte-for-byte from Data-grid.reference.html as rule 2 requires. Rule 2 and the gate disagree about the same bytes, and the builder is told to obey both.

  5. The screen gate wrote into the repo and then refused because of what it wrote.

    python3 knowledge/_validate_screen.py <page> emitted knowledge/_screen-gate/coldrun258v3.canon.md and then exited 1 with ⛔ SCREEN-GATE INDEX REFUSED — untracked subject. There is no flag in the runner's help to send the ledger elsewhere. Any consumer gating a page that lives outside the repo's tracked set hits this on their first run; the useful output (the four gate verdicts) is only in the file the gate objects to.

  6. Ten of eleven chart types shipped and unreachable; the fullness ceiling is unmoved since #246.

    The template carries one column chart. Nothing in the skill routes a second chart type off the brief — no rule, no index query, no example — so a blind build lands on one chart in every run: #246, v1, v2 and v3 alike. chart-line, chart-donut, chart-stacked-area and eight others are stable, gated and never chosen.

  7. Two nav destinations render the same wall.

    The view router shows and hides bento groups, and Liquidity and FX resolve to overlapping group sets, so nav:fx changed only the title and the URL — the groups snapshot was identical to Liquidity's (drive.json, nav:fx → changed: [title, url]). Honest reporting of a thin spot: the skill's rule 14 says "nav switches the view" and a group-visibility router satisfies the letter of it while leaving two destinations nearly indistinguishable.

For Dave. Not answered here.

  1. Does s258-D3 count as enacted while canon.css still carries 28 --demo-width width rules? The snippets are fenced and the gate refuses copied fences; the generated-page symptom the ruling was written against still reproduces through the canon route.
  2. Which route is the sanctioned one — link canon.css and wear the cn-* scope, or inline the snippet's own <style>? v2 did the second and drew 262 hex; v3 did the first and drew none. Step 3 reads as the first; rule 2 reads as the second. Only one can be the answer the gates are calibrated for.
  3. Should ADS-generate-from-canon step 2 name behaviour as a thing to read? Rule 2a's script address lives there, and the one control family that died in this run died because the procedure never pointed at it.
  4. Should the skill's procedure mint a provenance receipt? Without one, s258-D3's FAIL:DEMO-CHROME-COPIED is unreachable for every first-run page.
  5. Is a native <input type="checkbox"> inside a copied Data-grid a defect? If not, the compose gate needs an exemption for snippet-carried controls; if so, the Data-grid snippet itself needs changing.
