Key-filter + control-lockup molecules — the #66 decision pack (v2)

In one breath: the clickable chart key that dims a series on and off already exists as a reusable piece — bar and donut use it. Scatter never got connected to it, a checking tool wrongly said scatter had no key at all, and one chart (sparkline) is carrying a copy of the key machinery it can never use. The chart header — title, "View as table", the controls — is repeated by hand in every chart and could become a reusable piece too. Four decisions below sort all of this. Each one: plain description first, machinery in the fold.

What went wrong with scatter's key (fixed tonight, one part left for you)

Scatter's key looks like the others but is only a picture — clicking does nothing, which is what you found. It was built before the clickable key existed and never upgraded. Worse, the tool whose job is to catch exactly this looked at scatter's key and reported "no key here", so the gap sat invisible. That tool is fixed tonight and now points at scatter loudly; it will keep complaining, on purpose, until you decide scatter's key's fate in D3.

Technical detail

Scatter carries the dead static model (ul.dv-legend, snippet ~line 261) — no .dv-legrow rows, no data-series-toggle hooks. The registry (component-types.json) subscribes scatter to dv-behaviour only, so the dv-legend partial is never injected. _check_legend_migration.py matched only .dv-legrow or the dead hook; a static ul matched neither and fell through to "no legend — nothing to migrate" (the matched-grep-≠-presence class). Fix (sub-built, conductor-replayed): total partition over a derived legend vocabulary (\bdv-leg[a-z-]*\b), new loud finding "static legend present but not migrated and not subscribed", exit 1 extended to cover it, mutation-tested in three directions. Known consequence, declared: dv-behaviour.js:148's "Authorised by … exit 0" citation is stale until D3 enacts.

The four decisions

D1 — Make the sharing rule permanent?

There's a rule that decides which reusable pieces each chart receives: a chart can declare exactly what it uses, and anything with no declaration gets everything. You approved it provisionally in July. It has behaved well since — including refusing several kinds of mistake we deliberately threw at it — so the question is whether it graduates from provisional to permanent, and if so whether "no declaration = everything" stays, or every chart must declare explicitly.

Technical detail

ADR-0015-A2 (TENTATIVE, yours, 2026-07-28): universal-default consumes-manifest — "consumes": [...] narrows injection; absent key = all group partials. Since ruled: scatter's own narrow declaration enacted #27 (dv-legend's 16,271 B refused entry, build 72/72 exit 0); mutation control refuses in four directions (unknown name, empty list, declared-away markers present, declaration deleted). The unpredicted safety property, observed not inferred: deleting a declaration makes the member universal, which demands markers it doesn't carry ⇒ non-conforming — a declaration cannot be silently dropped. Flipping the default to fail-loud matches house style but costs an explicit declaration on every current member.

D2 — Let sparkline drop the dead weight?

Sparkline has no key — nothing to click, nothing to filter. But because it never declared what it uses, the "everything" rule hands it a full copy of the key machinery anyway: about seventeen thousand characters of code riding along in every copy of that chart, doing nothing. One line of declaration sheds it.

Technical detail

Measured tonight: sparkline's injected dv-legend block = 16,661 B (the record's "15.6KB", re-measured on the artefact). Remedy: "consumes": ["dv-behaviour"] on the sparkline registry entry, then regenerate — the exact move ADR-0015-A2 predicted "when ruled". This is that ruling. Post-shed the build's declared-away marker check enforces the block's removal from the snippet.

D3 — Scatter's key: connect it, or remove it?

Two honest options. Connect it: rebuild scatter's key in the working format and subscribe it to the machinery — clicking then filters the segments, same as bar and donut. Remove it: argue scatter never needed a key, because every point already carries its segment's shape and letter (circles/A, squares/B, diamonds/C) — the key would be decoration. Connecting is what you asked for when you reported the fault; removal is listed because it's cheaper and defensible, not because I recommend it.

Technical detail

Migrate = markup (static ul → .dv-legrow rows) + registry (consumes: ["dv-behaviour","dv-legend"]). Budgets, measured: scatter page 13,346 + 16,661 = 30,007 B vs 32,768 group cap ✓; dv-legend.js (54 B free) needs zero new bytes if init-discovery covers scatter's markers — they already carry data-series-group. That zero is a reading of the init loop, proven only at enact by the build gate; if it's wrong the job STOPS and re-prices (the ceiling is absolute). Delete = drop the ul, scatter joins sparkline as legendless-by-design; dv-011 already guarantees colour is never the only channel.

D4 — Make the chart header a reusable piece?

Every chart hand-builds its own header — title, the "View as table" button, theme and replay controls where present — and the copies have drifted apart. The proposal: one reusable header piece that each chart configures (which title, which controls, how aligned), same discipline as the key. Tonight's question is only whether the idea is the right cut — look at the three headers in the spread below and judge by eye. Building it is next session's work, sized and priced then.

Technical detail

New ADR-0013 partial (working name dv-lockup), parameterised by data-attributes, registry-gated, riding the existing partial machinery (gen_component_partials.py) — no new architecture. Scope risk to price at build: the lockup touches every chart snippet (7 pro-formas), so it lands as its own wave with the ratchet, not a drive-by. Interaction with the behaviour-page budgets is markup-side only (partials inject markup+CSS here, not JS), but that claim gets measured at scoping, not assumed.
