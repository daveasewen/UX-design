# #259 lane F — COMBO type partial · subreport

**`dvRender.types.combo` is built, driven and green on every gate that owns it — and the
`Chart-combo` PAGE is RED on the s250-D1 byte budget by 8,702 code-only bytes, which is REPORTED,
not worked around.** The red was known at launch (35,414 with five stubs in place); it is worse now
because the two partials the combo COMPOSES both landed real. The floor is the point: **with the
combo partial deleted entirely the page is still 3,504 bytes over.** No literal was touched, no
partial was stripped from the registry, and nothing was minified.

## What the partial is

`combo` **draws nothing itself** — not one rect, not one polyline. It is a COMPOSER:

1. splits `spec.series` on `kind: "column" | "line"` (absent ⇒ series 0 is the column, the rest
   are lines), keeping each series' SPEC INDEX, which is its palette slot and its legend number;
2. builds a **prototype-linked sub-ctx** per group (`Object.create(ctx)`) — the same `push`, the
   same `out` array, the same plot frame, the same `cats`/`GAP`/`HIT` — with only the series, the
   palette mapping, the formatter and (for the line) the value scale exchanged. A delegate cannot
   tell it is drawing half a chart;
3. calls `dvRender.types.column` (dv-render-bar) and then `dvRender.types.line` (dv-render-line);
4. **re-keys** what each delegate pushed: a delegate numbers its marks 1..n *within its own group*
   and dv-render-bar omits `data-series-group` altogether for a single series, but dv-legend filters
   on the SPEC's series number. The line delegate's repeat of the category labels is dropped in the
   same pass — the column delegate already wrote them on the same band centres;
5. authors the only two things that belong to neither delegate: the **secondary axis furniture**
   and the optional **target rule**.

The lane's one lucky break is lane B's header: *"THE CATEGORY BAND IS THE COLUMN'S… that is the
whole reason a COMBO can hand this function a ctx and overlay a line on its own columns."* It is
true, and it is why step 3 is three lines and not a re-implementation. **Measured, not assumed:**
bar centres `[89.0, 174.7, 260.5, 346.5, 432.2]` vs polyline point x `[89.0, 174.8, 260.5, 346.5,
432.3]` — the same band axis to a tenth of a pixel, and still the same after a resize
(`[70.6, 119.7, 168.9, 218.1]` vs `[70.6, 119.8, 168.9, 218.1]`).

### The spec extension (everything else is the core's contract, unchanged)

| field | what |
|---|---|
| `series[i].kind` | `"column"` \| `"line"`. Absent ⇒ series 0 columns, rest lines. |
| `series[i].unit` / `.format` | per-series, because **one `spec.unit` cannot say "£000" and "%" at once** — which is the entire premise of dv-line-006's dual axis. |
| `spec.sharedScale` | `true` ⇒ ONE value axis for both groups, no right-edge rule (the same-unit combo). |
| `spec.target` / `.targetLabel` | a number on the SECONDARY scale ⇒ the `[data-dv-view="target"]` group dv-behaviour's segmented toggle shows and hides. |

### The two axes

- **PRIMARY** — `combo.domain` returns the COLUMN series' range only, floored at zero
  (**dv-bar-009**, blocking). Without it the core would scale the bars against the line's numbers;
  a percentage and a payment volume share a band axis, never a value axis. So the core's
  gridlines, left tick labels and ink baseline are the BARS' scale — bars own the plot floor and
  own the grid (DV-D07).
- **SECONDARY** — the line's, computed here with the core's own exported `nice()` and deliberately
  **not** floored at zero (**dv-line-001**: zero is optional where floating aids interpretation).
  Drawn as a right-edge rule in the quieter `--data-axis` role plus a full **suffixed** tick run,
  which is what keeps a floating floor explicit instead of silent. Driven: primary ticks
  `0 · 250 · 500 · 750 · 1000`, secondary `88% · 90% · 92% · 94% · 96%`.

### The casing — the combo's intersection mechanism, kept

ds-026's categorical palette is **isoluminant by design**, so a line crossing a bar sits at about
1.04:1 against it and no pair of series colours can ever separate that crossing. The snippet's
2026-07-24 answer was a page-colour casing under the line; the engine keeps it, and keeps it
*honestly*: the casing is **the line delegate's own polyline, restroked** (class swapped to
`dv-casing`, presentation `stroke` dropped so `polyline.dv-casing{stroke:var(--page)}` wins,
width 2.5 → 6.5), so the two can never come to describe different geometry. Driven: 1 casing,
computed stroke `rgb(255,255,255)` on mono/light.

## What I could NOT do — first obstacle, named

1. **`gen_component_partials.py` red: `Chart-combo: required declaration 'data-dv-type="line"'
   missing`.** `dv-render-line`'s registry entry sets `requires.declarations:
   ["data-dv-type=\"line\""]`, and `Chart-combo` consumes `dv-render-line` — so the contract asks a
   COMBO figure to declare itself a LINE. It is not, and writing `data-dv-type="line"` on it would
   be a lie to `_validate_dataviz.py` as well. **The fix is one character of the registry
   (`knowledge/component-types.json`), which the brief fences.** Core request, verbatim, below.
2. **The page budget cannot be met from inside this lane** — see the table above. Reported, not
   worked around.
3. **`gen_showroom.py` not regenerated** (6 stale pages, none chart-related, chart-combo not among
   them). `_validate_screen.py` not run (fenced).
4. **DV-D10's axis-proximate lockups still not enacted** — the snippet's header says they ride the
   O1 build and the ledger is narrower than the divvy. Unchanged by this lane, deliberately.

## Core requests — verbatim

1. **`knowledge/component-types.json`, `$behaviour.dv-render-line.requires.declarations`:** change
   `["data-dv-type=\"line\""]` to `[]`, or to a form that a *consumer* of the line partial can
   satisfy without claiming to be a line. Every composing type (combo today; candlestick,
   bullet, stacked-area tomorrow) will trip the same clause. A type partial's registry contract
   should require what the PARTIAL needs, not what its own type's figure happens to say.
   *Suggested replacement:* drop the declaration entirely — `dv-render.js`'s own
   `data-dv-type="…"` requirement already proves the member is a chart, and `dvRender`'s "no type
   partial registered for X" error is the loud one if a name is genuinely unclaimed.
2. **`knowledge/canon/dv-render-bar.js`:** emit `data-series-group` on every `rect.dv-series`, not
   only when `ns > 1`. A single-series column inside a MULTI-series composition still needs its
   legend key, and today the combo has to patch the attribute in after the fact. ~20 bytes there
   replaces a string-rewriting pass here. (Not urgent — the pass is written and driven — but it is
   the honest home for the rule.)
3. **`knowledge/canon/dv-render.js`, the table spine:** `writeTable` suffixes every column header
   with the single `spec.unit`. A dual-axis chart has two units, so this lane put them in the
   series NAMES instead. If `series[i].unit` becomes canon (it is already canon in this partial),
   the core's header line should prefer it.
4. Lane B's core request stands and is seconded from here: **`if (lo > 0) { lo = 0; }` in
   `dv-render.js` fires for every type and cannot be escaped by `fn.domain`, because the clamp runs
   after the domain call.** This lane worked around it by computing the SECONDARY scale itself, in
   the partial, which is why the combo's floating line axis exists at all. A `fn.zeroBase = false`
   opt-out would let the composer stop carrying its own scale arithmetic.

## RULING-SHAPED — Dave's word, not a lane's

1. **The `Chart-combo` page is 8,702 code-only bytes over `PAGE_BYTES` 34,816, and it is over by
   3,504 with the combo partial DELETED.** s250-D1's words are *"`MAX_BYTES` 16,384 and
   `PAGE_BYTES` 34,816 are UNMOVED; the unit is code-only bytes"*, and ADR-0015 A1 line 90 calls
   exactly this *"the forcing function working, not a defect."* Lane A raised it at 112 bytes of
   headroom; the combo is the case that proves the arithmetic does not close, because a COMPOSING
   type necessarily carries **three** type partials (its own, the column's, the line's) on top of
   the core, dv-behaviour and dv-legend. Four shapes, none of them a lane's:
   (a) re-dial `PAGE_BYTES` — Amendment 1's own caution is *"a cap that moves once moves again"*,
   and it has moved once (32→34 KB, #96-D5);
   (b) drop `dv-legend` from Chart-combo's `consumes` — **does not fit either** (35,784, still 968
   over), and the combo's legend is its DV-D11 dual-gesture control, so this costs a real feature
   for a red that stays red;
   (c) **price the engine CORE once per page rather than once per member** — dv-render is a SHARED
   payload, the same 9,309 bytes whether one member or eleven load it, and this is the only option
   measured to fit (34,209, 607 spare) while keeping every feature;
   (d) rule that a composing type is a legitimate exception and waive it for `combo`.
   **Not decided here. Nothing was raised, stripped or minified.**
2. **`behaviour.partial` on `chart-combo.meta.json` lists SIX names** (`dv-behaviour, dv-legend,
   dv-render, dv-render-bar, dv-render-line, dv-render-combo`) — the `consumes` list verbatim, as
   briefed, and the schema's own wording is *"the AUTO-BEHAVIOUR name(s) … that the snippet
   carries"*. **`chart-bar.meta.json` omits `dv-legend`** on the narrower s245-D2 reading. Two
   metas in the same wave now read the same field two ways. One of them is wrong and it is not a
   lane's call which. Flagged in the meta's own `$note`, not silently reconciled.
3. **A composing type has no home in the registry's `requires.declarations` model.** Obstacle 1 is
   the first instance; it is the same shape as lane A's *"no gate parses the artefact"*, one level
   up — a contract that describes what a partial's OWN figure looks like cannot describe a figure
   that borrows the partial. Worth a ruling before the next composing type (candlestick, bullet)
   arrives, not after.
4. **`spec.sharedScale` and `series[i].unit` are NEW spec fields**, minted here because dv-line-006
   is unstateable without them. They extend the shape Dave ruled at s249-D4. Minted and reported,
   in the ADR-0017 by-addition posture — but they are his to keep or rename.
