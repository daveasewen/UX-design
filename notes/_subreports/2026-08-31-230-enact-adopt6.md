### T4 · Chart tooltip re-homed into its chart — **ENACTED**, eyed · `P3`

**Source changed:** `knowledge/canon/dv-behaviour.js` (one function).

Canon's component layer scopes every snippet rule to `.cn-<slug>`, so all 28 `.dv-tip`
declarations read `:where(.cn-chart-*) .dv-tip{…}`. The tip was created on `<body>`, outside
every one of those scopes, so **nothing matched** — not the ground, not the border, not
`position:fixed`. The showroom hid it for months because each snippet keeps an unscoped copy
that composed pages never load.

Written from the mechanism, not from GPT's diff: `tipAt` gained a `src` argument and re-homes
the tip under `src.closest('[class*=cn-chart-]')` (falling back to `<body>`) **before** writing
the text — an `aria-live` region must be in place when its content changes. `position:fixed` is
viewport-relative, so the move changes which rules match and never where the tip lands.

**Driven, not inferred:**

## 7 · RULING-SHAPED QUESTIONS

Three. None blocked an item — all five enactable items landed without one.

**RSQ-A · The dataviz behaviour budget is full. Raise it, split it, or spend it down?**
ADR-0015 caps a behaviour GROUP at 34,816 bytes for page weight. The dataviz group is now at
**34,816 of 34,816 — zero headroom** (§2 has the arithmetic). Two consequences worth Dave's
word: (1) the T4 fix ships with a one-line comment where canon's house style would explain it
properly, and an under-commented structural fix is the kind that gets lost; (2) the next dataviz
change of any size fails the gate before it starts. Three shapes, no recommendation smuggled in:
raise the group number (it is a picked constant, not a derived one); split dataviz into two
groups (⛔ the gate's own docstring says splitting a source must not buy headroom, so this needs
his word, not a workaround); or **spend it down by landing T4's permanent half** — one unscoped
canon `.dv-tip` rule retiring the 28 scoped copies would let this JS shrink back and buys the
comment room at the same time. ⚠ Not urgent before the demo; urgent before the next dataviz lane.

**RSQ-B · In light mode the tooltip has no visible keyline. Intended?**
Measured on the render: light `border: 1px solid rgba(255, 255, 255, 0)` — `--pop-border`
resolves **transparent** — against dark's `rgb(128, 128, 128)`. So in light the pill is a white
box on a near-white tile held apart by the drop shadow alone, and in dark it has a grey outline.
It reads acceptably in `t4-tip-light.png` and `t4-bento-light.png`, and this is **pre-existing,
not something T4 introduced** — it was simply invisible while the tip matched no rules at all.
It is a look, not a bug, so it is his call: keep the shadow-only light pill, or give
`--pop-border` a visible light value to mirror dark. ⛔ Untouched pending his eye.

**RSQ-C · T5's record shape — confirm per-subject files.**
Genuinely unruled (the triage searched: nothing on `_validate_screen.py` or the screen-gate
file). I built the triage's recommendation — `knowledge/_screen-gate/<subject>.md` per subject
plus a directory-rebuilt index — because it follows from ADR-0017's write-once principle, and
because append (the cheap alternative) re-creates the same defect slowly. It is enacted and
driven, so this is a **confirm-or-redirect**, not a blocker. Reversible in one file if he wants
a different shape.
