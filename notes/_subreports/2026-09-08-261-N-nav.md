# #261 N — the nav family design pass

Dave's ask, verbatim: **"tackle the nav design"**. No reference ("we'll prompt this"), so this is
designed by judgment. Everything below is PROPOSED, nothing is ruled.

## What was built

`sidebar-nav`, `navigations`, `tab-bar` — redesigned as ONE family, not three files that agree.

**The family claim is mechanical, not rhetorical.** Two blocks are pasted identically into all
three snippets: a NAV FAMILY TOKEN SET block (17 colour vars + 4 geometry vars) and a SHARED ITEM
block (`.nv-item / .nv-ic / .nv-label / .nv-count / .nv-chev`, plus hover / `:active` /
`:focus-visible` / `[aria-current=page]` / `[aria-disabled=true]`). The item block is byte-identical
in all three. The token block is byte-identical in two and extended in Navigations by EXACTLY TWO
vars (`--field-border`, `--field-active`) for the search field it alone contains — that exception is
stated in every file rather than papered over, because "byte-identical in all three" would have been
a claim a diff could falsify. If the surfaces drift, the blocks stop matching and it shows in a diff.

**THE INDICATOR RULE, new and shared:** the 3px current-location bar sits on the edge the nav
touches the content. Sidebar `inline-start`, masthead `block-end`, tab bar `block-start`, masthead
compact drawer `inline-start`. The rule is what the three share, not the pixel. Measured in all 24
driven probes: 0 geometry mismatches.

Per surface:

- **Sidebar** — counts, a stated disabled row, a product lockup slot (masterbrand SVG per #230), a
  user/account slot at the bottom, tokenised widths (248 / 64), and an **overlay** mode below 768px.
  That overlay ANSWERS the deferral #203 left open ("below the desktop breakpoint the correct answer
  is almost certainly a Drawer, not a rail. NOT specified here"). The **rail tooltip** closes #203's
  other open finding without composing Tooltip in: the same visually-hidden `.nv-label` is re-shown
  in place on `:hover` and `:focus-visible`, so the mouse user and the screen-reader user are told
  the same word and no `aria-label` restates anything.
- **Top nav** — the primary row is literally the sidebar's row laid horizontally. Adds counts, a
  notifications action, a signed-in account trigger, a stated disabled destination, and a real 768px
  collapse: REPLACEMENT by hamburger + stacked panel, not a shrink. Drawer and primary row share ONE
  selection scope, so `aria-current` can never disagree between them.
- **Tab bar** — adopts the family token set and anatomy. Counts ride the GLYPH so the columns stay
  equal; disabled is stated; the 3px bar joins the filled-glyph swap as a second shape carrier.
  Variant B's sliding island now uses one rAF-debounced resize listener (ADR-0015).

Metas: `$navFamily` in all three (members, grade, shared anatomy, shared tokens, indicator rule,
carriers, open items, driven receipt), a typed `edges.groupsWith` on `navigations` ONLY — one
direction, because s251-D6 makes reciprocals derived — new props/variants/accessibility keys, a
`responsive` block each, and `provenance.$261`.

## Two ruling-shaped items

1. **Tab bar means the bottom bar, not section tabs — KEEP or RENAME?** The lane brief described
   Tab-bar as in-page section tabs with overflow fade and underline; that is the gated **Tabs**
   component, and Tab-bar's own meta has said "app-level BOTTOM navigation, NOT the in-page Tabs
   component" since it was surfaced. Redefining it would make two components mean one thing and
   leave the mobile bottom bar homeless. Built to the canon meaning; the section-tab reading is
   drawn on these same tokens inside the review page's app frame. **Recommend KEEP.**
2. **Supercharge dark has no legal current-location colour — SHAPE or TOKEN?** Measured 3.89 / 2.73
   against 4.58 / 3.01 elsewhere. **Recommend SHAPE**: stop treating the bar's colour as a carrier
   at all — the shape and `aria-current` already carry it in every theme. TOKEN (a Supercharge-only
   current-location value) costs a new token and a fresh four-theme measurement.
