## ① THE FROZEN-RELEASE GATE — and how it was made to bite

The ledger (`_frozen-releases.json`) is **seeded by measurement, never typed**: `--seed` walks each
release's surface at a named commit and records `path <blob-sha>` lines hashed to one sha256.

```
designer-skills-v1   version v1          6 file(s)  b83d048483b7
designer-skills-v2   version v2        849 file(s)  e1d8019b97cc
designer-skills-v3   version v3.0.0      0 file(s)  e3b0c44298fc
```

v3's frozen surface is **`designer-skills-v3/dist/` and nothing else**, deliberately: the build
script, the ci-template and R3's skills are the machinery that *cuts* the next release, and
freezing them would freeze the next cut before it was made.

**Three arms, each able to fail alone:**

1. **Surface** — recorded hash vs measured hash at the commit, every differing path named.
2. **Working tree** — `git status --porcelain --untracked-files=all` over the same prefixes, so
   the same edit is caught one step *before* it is a commit (and so a zip appearing in a frozen
   `dist/` is reported rather than ignored).
3. **Laundering** — the arm that stops the ledger being a rubber stamp. A ledger you can re-seed
   at will is not a freeze: edit v2, re-seed, and arm 1 goes green having recorded the edit as the
   new truth. So the gate reads the ledger **at the parent commit** and refuses a row whose
   `content_sha256`/`baseline_commit` moved while its `version` stayed the same.

## ② THE TWO SHIP-LIST AUDITS

**`--check` (BLOCKING)** rebuilds the manifest from the generator at the manifest's *own* recorded
commit, using the stored probe, and compares **byte for byte**. The defect class is in the v2
receipt's own words: *"v1's copy-list had gone stale — never shipped canon/type.css nor
tokens/themes/"*. A generated ship list is only better than a typed one while something
re-generates it and compares. Verdict today:

```
PASS — the manifest at knowledge/_release/_v3_manifest.json is byte-identical to a fresh
generation at 71bb2f77ff59 (1590 files, sha256 ad0d985534457a1b)
```

When it goes red it names *what* differs — groups gained/lost, paths gained/lost — because a diff
of two 1,500-path JSON files is not a remedy.

**`--pack` (BLOCKING, resting state = refusal)**. If a zip is in `designer-skills-v3/dist/` it is
checked against the manifest and the commit's own blobs. If none is, the arm returns
**COULD-NOT-ASK (77)** naming the reason: nothing is baked, because the release is Dave's word and
the manifest reads PROPOSED. The survey counts 77 as the third verdict and excludes it from its
exit code — which is how this can be BLOCKING today without being born red.

Its happy path is **not** left unproven. A `--dry-run` bake was cut to `/var/tmp` and checked:

```
CHECK GREEN — /var/tmp/r2/bake/Apollo-designer-skills-v3.0.0.zip matches the manifest at 71bb2f77ff59
sha256: 5288358d07aa8945c2ea75d8f18cf017c5e1a20d11f10df64b1edeaae187bc07
```

That sha is **identical to the one R1 measured**, which independently re-proves R1's determinism
claim and proves my generator edits are byte-neutral end to end.

**`--drift` (ADVISORY)** reports how far behind HEAD the ship list has fallen. Non-zero when
behind, `continue-on-error` in CI, ADVISORY in `_build_all` — because *whether to re-cut* is
⬛ Dave's (`s219-D4(2)`), and blocking on it would be a gate making his release decision for him.

## ③ THE PACK-SIDE TEMPLATE

- **`gates.yml`** — two jobs. `gates` runs the 36 plain-python gates and installs **nothing**

  reading it."*

## FINDINGS

1. **A rule with no gate, for 105 sessions.** `s114-D4` was enforced by habit. It is now enforced
   by machine, and the enforcement includes the escape hatch (bump the version) so that the rule
   is followable rather than merely blocking.
2. **The pack ships FOUR gates that are RED at bake.** Measured by running them from an extracted
   pack: `_validate_evidence.py` (exit **2** — it needs a `<rows.jsonl>` argument), and
   `_validate_token_forks.py` (3 forks not in the ledger), `_validate_type_blast_radius.py`
   (`.search input` escaped its radius), `_validate_type_composites.py` (664 violations in the
   pack; 1,091 in this repo). R1's probe already recorded each as *"a live red, not a packaging
   fence"* — so the fact is in the manifest. What is NOT anywhere is the consequence: **a
   designer's first CI run is red, for reasons that have nothing to do with their work.** That is
   the born-red disease at pack scale, and it is question 1 below.
3. **`_validate_evidence.py` cannot pass as invoked.** Exit 2 is bad arguments, not a verdict.
   R1's probe schema carries an `invocation` field for every gate and it is empty for all 47 —
   this is the gate that needs one, or exclusion. (R1's classifier reads a clean non-zero as a
   verdict, which is right in general and wrong for rc=2.)
4. **cwd makes no difference to those four.** They were re-run with cwd *inside* the pack: same
   four reds, same messages. So the runner runs from the designer's project root, which is what a
   designer expects, and the reds are content, not invocation.
5. **A seventh manifest group would have invalidated R1's manifest and Dave's page.**
   `build_manifest` emits an entry for every group in the table, so a new `ci-template` group
   would have added an empty card, changed the manifest's bytes, and forced a regeneration of the
   go/no-go page mid-review. Instead the ci-template paths are folded into the **gates** group —
   *a workflow that runs the gates is not a seventh thing to explain*. At `71bb2f77ff59` the files
   are untracked, so the rule is a **no-op and the manifest is byte-identical** (proved); at a
   synthetic landing commit the ship list carries **1,593** paths, the gates card reads **57**,
   and Dave's page renders a CI-template line (proved by rendering it). The manifest was **not**
   hand-edited and **not** regenerated.
6. **`build-designer-pack.sh --dry-run` writes into `reviews/`.** Its last step folds the measured
   zip size back into Dave's page — correct behaviour, and a side effect nobody would predict from
   the word "dry run". It cost me the two `rv-*` meta stamps that `_make_review.py` injects into
   the source; restored by re-running `_make_review.py`, both files back to their exact byte sizes
   (116,129 / 142,375). Anyone running a dry-run bake dirties `reviews/` and should re-run the
   review-maker after.
7. **R3's store row cites generator LINE NUMBERS** (`_gen_v3_manifest.py:284`, `:1251`, `:722`,
   `:194/:899`) for the skills repoint. My three additions shifted them. Line numbers in a store
   row rot the moment anyone else edits the file — the repoint should be re-derived by name.
8. **R3's skill and this template agree exactly.** `check-with-gates/SKILL.md` cites
   `ci-template/run-gates.py --list`, `--browser`, `ci-template/gates.yml` and
   `ci-template/README.md`, and states the delete-the-step rule. All four exist and behave as
   described. Verified by reading their file, not by assuming.
9. **A bare CI `run:` cannot tell 77 from 1** — the #193 disease one level down. The release
   steps capture the code, print the refusal, and pass only on 77.
10. **The baseline is a ratchet, not a mute, and it is mutation-proven.** On a three-gate fixture
