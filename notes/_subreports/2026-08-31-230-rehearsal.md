### F1 ⛔ SHARPEST — the design contract is in no file a cold Copilot seat auto-loads

`README.md` says `.github/copilot-instructions.md` "is loaded automatically". That file contains
**zero** of: *declare the lane* · *grill first* · *dashboards are bento-first* · *copy the markup
from `knowledge/snippets/`*. The merged projection that does carry them sits at
`cold-start/projections/.github/copilot-instructions.md`, and `gen_projections.py` says in its own
docstring: *"THE PROJECTIONS ARE TEMPLATES, NOT PLACEMENT … Getting them to the paths above in a
designer's own project is a separate step."*

The pack's own checker agrees, unprompted:

```
$ python3 cold-start/verify_placement.py
  NO RULES   CLAUDE.md                       Claude — no file at this path
  NO RULES   AGENTS.md                       AGENTS.md agent hosts — no file at this path
  NO RULES   .github/copilot-instructions.md GitHub Copilot — the file exists but the design contract is not in it
```

**…and it exits 0.** It warns; it does not block, and nothing in the install path runs it.

**Consequence:** on a pristine v1.0.5 unzip opened in VS Code, beats 1, 2 and 5 have no
instruction to fire from. This is the single thing most likely to sink the demo.

**Fix tonight, cheap:** merge the projection into the pack's own
`.github/copilot-instructions.md` so the shipped pack is contract-carrying out of the box, or add
the merge as step 1 of the install instructions and have `verify_placement.py` exit non-zero.

### F2 — the bento question is never asked, by anything

Dave's condition is *"it would use the dashboard bento **or** it will ask if that is right."* Only
the first arm is built, and only in the contract. `grep -c -i "bento-first"`: contract `1` ·
projection `1` · **auto-loaded copilot file `0`** · **`generate-from-canon/SKILL.md` `0`**. The
skill's rule 7 says "layout comes from the rails" and points at
`knowledge/_render/_bento_edit_rails.json`, which the contract calls "the dial vocabulary … not a
layout" — it never says *dashboards are bento-first*. So even a seat that opens the right skill is
not told to go bento-first. **If the demo wants the OR's second arm, it does not exist and must be
written.**

### F3 — THE LOGO (Dave's priority beat)

**What a cold builder does: it ships a text wordmark, silently, and never asks.**

`knowledge/snippets/App-shell-top-nav.reference.html` and `Navigations.reference.html` both carry
the mark as literal text:

```html
<span class="sh-logo t-ed-heading-4" aria-label="HSBC">HSBC</span>
```

The twelve official masterbrand SVGs **do** ship — `knowledge/assets/logos/`
(`masterbrand-*`, `masterbrand-identifier-*`, `hexagon-*`, each light/dark × colour/mono) — and
**nothing binds them.** The snippet says so in its own header comment: *"⚠ SEE $decision-2: the
OFFICIAL masterbrand assets exist and NOTHING binds them."* The component meta is just as plain —
`"use": "the masthead identity. ⚠ CURRENTLY A STAND-IN — see $finding-brand-mark"`, and
`$decisionsForDave[2]`: *"THE BRAND MARK. Twelve official SVGs exist and nothing binds them; zero
of 108 pre-existing snippets reference `knowledge/assets/logos/`."*

Two shipped guidelines contradict the stand-in, and **both are ADVISORY, so no gate catches it**:
- `va25-015` — *"the Masterbrand logo appears in ALL digital mastheads"*
- `va25-016` — *"Never-rules: no new lock-ups from text …"*

**And the reference render settles it:** Dave's own artefact carries **the hexagon mark**. So the
contract's "copy the markup" rule, obeyed exactly, produces the one thing his target does not
have. `foundation-logos` is a display-only foundation page — browsing it is the only route to the
real assets, and nothing points a builder there during a build.

**This is a canon gap to close in the components, not a freestyle fix:** bind the masterbrand
asset to a brand-mark component (itinerary row 86, P1) and re-point the shell/masthead snippets at
it. Until then, every dashboard the pack builds says "HSBC" in type.

### F4 — there is no bento snippet

`knowledge/snippets/` holds 137 files and **zero** contain `.c-bento`. The contract's own two
rules therefore cannot both be obeyed for a dashboard: *"Copy the markup. Component HTML comes
from `knowledge/snippets/`"* and *"Dashboards are bento-first."* The bento vocabulary is
well-formed and well-commented in `knowledge/canon/canon.css` (`.c-bento`, `.c-bento__grid`,
`.c-bento__tile[data-c|data-r]`, `.c-bento__caption`) and demonstrated in
`showroom/_foundations/bento.html` — but a builder holding the "never invent / stop and name the
gap" rule tightly should **stall here**. This one stalls the priority beat.

### F5 — the pack's only page-scale dashboard reference is not bento

`Template-dashboard.reference.html` uses `.l-grid` / `.l-row` / `.l-split` / `.l-stack` and
contains **zero** `.c-bento`. It is also the artefact a builder is most likely to reach for on
"build me a dashboard". So the most authoritative dashboard example in the pack contradicts the
bento-first rule.

### F6 ⛔ DEMO HAZARD — the contract's own final check is RED on a clean pack

The contract's beat-5 rule ends: *"it ends in `python3 ci-template/run-gates.py`, and reading the
file is not running it."* Run on the pristine pack:

```
37 pass · 1 FAIL · 0 could-not-ask      →  exit 1
  === _validate_wiring.py ===
    ⛔ ORPHAN: _validate_grid.py exists on disk and NOTHING RUNS IT …   (×23 gates)
    ⛔ DANGLING EXEMPTION: _gate_pack_imports.py is exempt but not on disk.
    ⛔ DANGLING ARM: _gate_harness_stubs.py is declared an arm of _test_git_commit.py but is not on disk.
```

`_validate_wiring.py` checks **source-repo wiring** (`_build_all.py` STEPS, `_git_commit.sh`,
`gates.yml`) that a pack install does not have — the `#173` "gate that cannot pass in one
environment" class, shipped as RUNNABLE rather than REPO-BOUND. `--baseline` exists for exactly
this, but **no baseline file ships**, and a cold seat will not know to write one.

**If Dave runs "check before you show" live, the demo prints FAIL** — on the pack, not on his
dashboard. Reclassify the gate REPO-BOUND, or ship a baseline.

### F7 — the app-shell snippet is a specimen card, not a page frame

`.sh{ min-height:560px; border:1px solid var(--rule); border-radius:…; overflow:hidden }`. A
builder copying the shell to get "the correct navigation bar" inherits a **560px empty bordered
box** under the masthead. Cost one full fettling round. The right move is `.cn-navigations` +
`<header class="masthead">`, but nothing says so — the shell is what `app-shell-top-nav`'s blurb
("a masthead band carrying the brand…") points you at.

### F8 — chart data is baked geometry, with no generator

`dv-series` rect `x/y/width/height` are mint-time values. Nothing in the pack turns data into
chart SVG (`grep -rn "dv-series" --include="*.py" knowledge/` hits only `_validate_a11y.py` test
fixtures). An FX-exposure chart with real FX numbers therefore requires hand-computed
coordinates — which "never invent" forbids and nothing supplies. The build shipped the specimen's
spend-by-category data under an FX heading, which is the honest outcome and a visible wrong.

### F9 — no `@font-face`, and no web font ships

`canon.css` declares `--font: "Univers Next for HSBC","Helvetica Neue",Arial,…` with **no**
`@font-face` anywhere, and the pack carries only `knowledge/assets/fonts/_desktop/` TTF/OTF — no
woff2. A composed screen falls back to Helvetica/Arial unless the HSBC desktop fonts are
installed on the machine. Likely fine on Dave's laptop; worth knowing before a stakeholder opens
the file.

### F10 ✅ — the screen gate is the strongest link, and it should be demoed

`_validate_screen.py` caught the first build's `.c-bento__grid` redefinition immediately and named
the class. That is precisely the "you have left canon" moment the system exists to produce, it
cost one small fix, and it is a good thing to show live.

### F11 — minor: no `briefs/` ships

Both the contract and grill-me say "look in `briefs/`". Its absence is the correct trigger to run
the grill, so this is benign — but grill-me has to create it, and nothing pre-creates it.
