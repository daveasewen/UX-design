## WHAT / WHY / RECEIPT

### 1 · Rules are read WITH their band conditions (`all_rules`, `_conds`, `band_applies`, `cascade`)

**WHAT** every rule in the page's `<style>` is collected as `(conds, selector, declarations, pos)`,
`@container` blocks included and carrying their own query; `pos` is the absolute offset so source
order is comparable across the top level and every band block. `cascade(el, rules, width)` picks the
winner by (specificity, source order) among rules whose selector matches and whose query holds at
that band. `bands()` now carries each band's evaluation width (`None` = the base band, wider than
every declared band), so `(max-width:1100px)` holds at 1100/820/520 and not at base, and
`(min-width:821px)` holds at base/1100 and not below.
**WHY** both ruled declarations are ordinary CSS: one is a property on a scoped selector, the other
is a property inside a band. Nothing can see them without a cascade that knows about bands.
**RECEIPT** the matcher is not new code: `match_selector()` is `gutter_of()`'s own walk, extracted
verbatim, and `gutter_of` now calls it — the C1 gutter arms (M3–M6, K1, K2) are unchanged and green,
which is the probe that the extraction was faithful.

### 2 · A column count written as a literal `repeat(<n>,…)` IS the count (`grid_cols_at`) — rule 10a

**WHAT** the winning `grid-template-columns` for a grid at a band is read; if its `repeat()` count is
an integer **literal**, that is the grid's column count at that band. If the count comes through a
`var()`, it is canon's band machinery and the band's own count stands.
**WHY** `s247-D3`/`s251-D1` pin the lead grid at four across at every band, and rule 10a's own
comment says why the literal is on the property rather than on `--bento-cols-now`. The literal/var
split is the artefact's own distinction, not a name: canon's base rule
(`repeat(var(--bento-cols-now),…)`) and rule 6b(ii) (`repeat(var(--bento-columns),…)`) both stay
band-driven; only a literal opts out.
**RECEIPT** the gate now prints what it found, and it is one selector, unnamed by any list in the code:
```

```

### 3 · `grid-column: 1 / -1` is the whole row (`tile_span_at`) — rule 6b(i)

**WHAT** a tile's span is cascaded from the page's own `grid-column` rules: `1 / -1` → the grid's
column count at that band, `span N` → N, otherwise the tile's `data-c`; always clamped to the column
count, which is what a browser does with a span wider than the explicit grid. The old hand-rolled
clamp-table regex in `bands()` is gone — canon's band clamps are now read as the ordinary rules they
are, by the same cascade.
**WHY** `s248-D1` re-flows the context rail to a full row at ≤1100px, and the snippet's rule 6b
comment says in as many words that C9 "reads only canon-shaped clamps, so it does not see (i)".
**RECEIPT**
