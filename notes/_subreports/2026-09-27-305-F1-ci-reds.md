## RED 1 — [145], [146], release step 7: an enacted ruling read as "not ratified"

**Cause (P1's, confirmed).** `ratification_status()` in `knowledge/_release/_gen_pack_manifest.py` returned RATIFIED only when the keyed ruling's status was exactly `"ruled"`. The stamps commit `21c9b7f4` moved s305-D2 to `"enacted #305 2026-09-27 - the cut is built …"`, so a fresh generation derived PROPOSED against the committed RATIFIED manifest. That one status line was the whole difference.

**Change.** A module-level `_RATIFYING_STATUS = re.compile(r"(ruled|enacted)(\s|$)", re.IGNORECASE)` and the loop now matches the status's first word against it. The RATIFIED sentence is unchanged byte for byte, which is why the manifest regenerates identical. The PROPOSED sentence now says "not 'ruled' or 'enacted'". The rule is not version-specific, so any earlier release whose ruling is later stamped `enacted …` stays ratified. Superseded, standing, proposed, and anything that is not the whole word (e.g. `enactedX`) still derive PROPOSED. ⚠ Declared: case-insensitive, so `RULED` / `ENACTED` also count; the store uses both casings for the same states (145 `RULED`, 210 `ENACTED`), and a case-exact match would re-open this red the first time a stamp is upper-cased. If the conductor wants lower-case only, drop `re.IGNORECASE`; nothing else moves.

**Driven** (`notes/_lanes/305/F1/drive-ratification.log`, fixture copies of the store, the live store never written):
- live store (enacted) → RATIFIED · superseded → PROPOSED · standing → PROPOSED · proposed → PROPOSED · `enactedX` → PROPOSED · restored → RATIFIED · `ruled` → RATIFIED.
- an earlier release, v1.0.13 / s268-D3: stamped `enacted #306 …` → RATIFIED; `superseded` → PROPOSED.

## RED 2 — [133] and [134]: `ast.unparse` changed between Python 3.10 and 3.12

**Cause.** Not a file, path, gitignore or line-ending difference: `git --no-optional-locks diff HEAD -- memento-package/` is empty, so H2's port is committed exactly as the seat has it. The CI log's finding is a different one from the seat's pre-H2 drift: `SHIM BODIES: a DECLARED-DIFFERENCE rule no longer applies for 'measure_tokens' … expected 1x, found 0x (quoted source text: "try:\n (n, how) = gauge.count(text) …")`. `_validate_package_delta.py` normalises function bodies through `ast.unparse` and compares against quoted text. Python 3.10 (the seat) unparses a tuple assignment target as `(n, how) = …`; 3.11+ (CI runs 3.12) writes `n, how = …`. The quote was typed at the seat, so it matched there and matched 0x in CI. The same cause turned [134]'s ARM2(f) red in CI (the rule failed before the drift it looks for could be seen). H2's green was real at the seat, and it could not have seen this.

**Reproduced at the seat.** With a uv-installed Python 3.12.14 in `/var/tmp`, the unfixed HEAD gives exactly CI's two findings, and [134] red on "real repo" and ARM2(f) (`clean-control-head.log`).

**Change.** In `knowledge/_validate_package_delta.py`, after the two quotes: `_TUPLE_UNPACK = ast.unparse(ast.parse("(n, how) = gauge.count(text)"))`, and that one line in `_REAL_TIER_SOURCE` and `_REAL_TIER_SHIM` is replaced with the running interpreter's own rendering. Each rule still has to apply exactly its declared number of times. Under 3.12 the selftest's mutation arms still catch the failures they are built for: ARM2(f) (an edit inside the allowance fails as DRIFTED), ARM2(g) (a stale rule fails loud) and ARM2(h) (control) all pass (`clean-py312-134-full.log`).
