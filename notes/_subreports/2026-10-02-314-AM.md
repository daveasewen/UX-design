## 1. The account menu (call 3)

**Cause: a wrong class on the page.** On `dashboards/international-banking-dashboard.canon.html` the two account-menu items were `<button class="opt t-cm-label" role="menuitem">`. `opt` is the dropdown's option class, and canon only styles it inside `.cn-cards` (`.card.opt`) and the dropdown listbox. Inside `.cn-navigations` it matches nothing, so the browser drew its own grey button with an outset border. The top nav's account menu in `knowledge/snippets/Navigations.reference.html` uses `nv-item` with the label in `<span class="nv-label">`, and canon styles that (`:where(.cn-navigations) .nav-menu .nv-item`).

**The page is its own source.** No generator builds it. The #230 triage calls it "(Dave's)", the #227 regen built a separate `regen-v1.html` beside it, and nothing under `knowledge/` writes `dashboards/international-banking-dashboard.canon.html` (I searched the .py, .sh and .js files). `gen_bento_matrix_217.py` is the canon cascade reader and does not build this page. So the fix is in the page.

**Changed (one file, 4 edits):**
- Both items: `class="opt t-cm-label"` became `class="nv-item t-cm-label"`, and the label is wrapped in `<span class="nv-label">`, matching the reference.
- Page script: the theme toggle now sets the text of `#themeToggle .nv-label`. Before, it set the button's `textContent`, which would have wiped the span.
- Page script: "Secure session" now marks itself with `aria-disabled="true"` instead of `disabled`, because canon styles `.nv-item[aria-disabled="true"]` and has no `.nv-item:disabled` rule.

**Export CSV was not broken.** It is `btn tertiary` inside `.cn-page-header-lockup`, and it already draws as the outlined tertiary button in all eight renders (computed border is 1px solid ink). AC1's shot shows it because it sits just below the menu. I did not change it.

**Checked:** I opened the menu with a mouse click in four themes × light/dark, before and after. Before: grey native buttons 17.6px tall with a 2px outset border, in all eight. After: transparent rows 44px tall with no border, the same as the top nav's menu. The first item takes focus when the menu opens, but `:focus-visible` is false, so no ring shows. The menu keeps its edge: invisible in light, grey in dark (s313-D58). One caveat: the label reads "Switch to dark theme" in the dark shots because the harness sets dark mode directly; the page's own toggle rewrites the label.

## 2. Focus ring only by tabbing (call 1, s313-D71)

**State of the ruling.** s313-D71 is still `ruled`, not `enacted`, in `_rulings.json`. The brief's other citation, s313-D44, is about the evidence folder and has nothing to do with focus. The showroom bar's fix is s313-D45 (`gen_showroom.py`): the ring sits on `:focus-visible`, and a pointer flag turns it off after a click. The components already have the same agreed pattern, used by Input-fields and twelve other fields:
- the ring on `:focus-visible`;
- `:root[data-modality="pointer"] … {outline:none}`;
- a small script that sets `data-modality` to "pointer" on mousedown or touchstart, and back to "keyboard" on Tab.

The pointer flag is needed for text fields and selects because the browser counts a click into them as `:focus-visible`.

**Static sweep.** I searched every snippet and the canon sources (`canon.css`, `type.css`, `gen_canon_components.py`). Every bare `:focus` rule either removes the outline (`outline:none`), sits inside `:not(:focus)`, or is a field's active state: a border colour or the 4px bar. No snippet draws a ring on bare `:focus`. Static reading could not find the real defects. A click test could.

**Click test (new instrument, not committed).** `/home/claude/lanes/314/AM/click_sweep.py` loads all 137 showroom pages over `file://` in cloud Chromium. For every focusable part in the component frame it clicks with the mouse, then records any outline that is present after the click but absent on hover.
- Before: **199 rings on click across 16 pages.**
- After the fixes, with canon and the showroom regenerated in a scratch worktree: **0.**
- On the tabs page, one part was not measured: the tab panel, which is hidden once another tab is chosen.

**Defects found, and fixed at the part:**
1. **Combobox, Multi-select, Tags-input.** Each snippet had the pointer-flag CSS rule but no script to set the flag. The rule could never fire, so a click into the field drew the 2px focus ring. Fix: added the same four-line modality listener the Input-fields snippet carries, wrapped in a block so its `root` name cannot collide.
   - `knowledge/snippets/Combobox.reference.html` (+6 lines)
   - `knowledge/snippets/Multi-select.reference.html` (+6)
   - `knowledge/snippets/Tags-input.reference.html` (+6)
2. **Data-grid, the rows-per-page select.** The ring was on `.dg-pp select:focus-visible`, and the browser counts a clicked select as focus-visible. Fix in `knowledge/snippets/Data-grid.reference.html` (+6 lines):
   - added `:root[data-modality="pointer"] .dg-pp select:focus-visible{outline:none;}`;
   - added the modality listener at the end of the component's script, outside the demo harness.
3. **All 14 charts.** The marks (bars, slices, points, candles, markers) carry `tabindex="0"`, and the authored ring is already on `:focus-visible`. But the browser's own ring for focused SVG elements fires on a plain `:focus`, so a click on a bar drew a dark 5px ring. Fix: one line after each chart's mark-focus rule:
   `svg [tabindex]:focus:not(:focus-visible){outline:none;}`
   Files: `knowledge/snippets/Chart-{bar,boxplot,bullet,butterfly-h,butterfly-v,candlestick,combo,donut,histogram,line,pie,scatter,sparkline,stacked-area}.reference.html` (+1 line each). Line, sparkline and stacked-area showed no ring in the sweep because their marks were not hit-testable at that width. They have the same exposure, so they got the same line.

**Keyboard rings kept.** No `:focus-visible` rule was removed. Tabbing still draws the ring on all five sampled parts (renders below).

**Not changed, Dave's call:** the field's own active state. Clicking into a text field still shows the 4px bottom bar and the darker border (`:focus-within`). The Input-fields meta records it as "Aesthetic focus, all users". Under the 14:55 comment that may also count as a focus state. See open question 1.

## 3. The gate

No gate refused `:focus` without `-visible` before this lane. I built one small check inside the existing snippet gate:
- `knowledge/_validate_snippets.py`, check 5b "CLICK RING": refuses a rule whose selector has a bare `:focus` (not `-visible` or `-within`, not inside `:not()`) and whose declarations draw a ring, meaning a non-none outline or box-shadow. It passes on the tree as it stands (137 snippets, 0 failures). Sanity tests were run on seven planted rules.
- `knowledge/_tests/test_gates.py`: a new bite case, "snippet gate bites on a ring on bare :focus". It plants `.zz-planted:focus{outline:…}` and the gate refuses it. Gate self-test: 40 tests, 0 failures.

**Proposed, not built:**
- (a) Refuse a snippet that carries the `data-modality="pointer"` rule but no script setting `data-modality`. That is the Combobox, Multi-select and Tags-input defect. Today it would fail `Template-settings.reference.html`, which is lane TP2's file, so I left it unbuilt and did not touch that file. TP2 should add the four-line listener or drop the rule.
- (b) Promote `click_sweep.py` into a render-based gate, in the same family as `_validate_descender_computed.py`. It is the only check that caught the chart rings, which come from the browser's own styles rather than our CSS.
- (c) Composed pages, such as the dashboard and the templates, get canon's pointer-flag rules but nothing sets the flag. A text field built from canon will therefore show its keyboard ring on click unless the page carries the listener. The banking dashboard showed no click ring in the sweep, because its fields use the bar, not the ring. One shared behaviour file (the `dv-behaviour.js` precedent) would close this for every composed page. Needs a decision.
