## 1 · FINDING 1 — RCA (five whys), then the fix

### The five whys

1. **Why did the console hover render square?** Because the hover fill paints the `<button>`
   (`.seg button:not([aria-pressed="true"]):hover{background:var(--hover)}`) and the button carried
   **no `border-radius` declaration at all**.
2. **Why did the button carry none?** Because when the concentric pair was minted (`s202-D1/D2`) and
   wired (#219), the wiring bound the two boxes that are **painted at rest** — the track (`.seg`) and
   the thumb (`.ind`). The button is `background:transparent` at rest, so it was never in the field of
   view. It only becomes a painted box in a *state*.
3. **Why was "painted at rest" the field of view?** Because every instrument and every review looks at
   a **static render**. A state box exists for nobody until someone hovers it — which is precisely how
   Dave found it and no gate did.
4. **Why did no gate catch it?** Because the whole gate family is **presence-checking**, and this is an
   **absence**. `_validate_radius.py` validates the *form* of `border-radius` declarations that exist
   (must be a var / 50% / 999px / inherit) — it cannot see a box with no declaration.
   `_gate_minted_consumption.py` asks "is this mint READ?" — and the mint **was** read, by `.ind`, so
   it was green. Neither gate can express "these sibling boxes belong to one concentric family".
5. **Why does this keep recurring?** Because **the segmented control's CSS is copy-pasted into twelve
   snippets with no shared partial.** `component-types.json` has exactly two groups —
   `button-family` and `dataviz` — and no `segmented` group. Every segmented repair therefore has to be
   re-applied N times by hand, and any box missed stays missed. The snippets say so themselves: the
   `s227` B6 note now standing in `Chart-line`/`Chart-combo` reads *"the toggle stayed square in every
   rounded theme while its neighbours rounded — repaired by hand in a real page (2026-08-30) before it
   was repaired here, at the source."* Same class, three weeks running.

**ROOT CAUSE (two-part).** (a) The segmented atom has **no PARTIAL**, so its geometry contract is
twelve independent copies rather than one generated block. (b) **No gate expresses concentricity**, so
an omitted radius in any copy — especially on a box that only paints in a state — is invisible.

### Where the fix went, and why that IS the mint path

**The store was already correct.** `--assert-mint` was green *before* this repair: the defect was never
a wrong value, it was an **un-consumed** one. So there was nothing to re-mint.

`gen_canon_components.py`'s own docstring settles where consumption lives: *"The snippets are the
source of truth (they are the final reviewed components); canon regenerates from them."* Editing
`canon.css` would have been the hand-edit; editing the **snippet** and regenerating is the mint path.
No literal was authored anywhere — the button binds the **same scale-selected local the thumb binds**,
so it is concentric by construction and follows the scale classes automatically.

## 2 · FINDING 2 — RCA (five whys), then the fix

### Step 1, as instructed: is there a round variant? **No.**

`knowledge/snippets/Fab.reference.html` has one shape and it is token-bound. Its header says so in as
many words:

> `⛔ CORNERS — the brand stays flat/angular (B-D7); this binds border-radius/control exactly like
> Icon-button (0 in Mono/Legacy, Console forks it through the cascade). A FAB is CONVENTIONALLY
> circular in most systems that ship one; whether Apollo's FAB should DEVIATE from the angular rule
> … is Dave's, flagged not taken.`

The atom: `.fab{ … border-radius:var(--border-radius-control); … }` (line 114), and the manifest binds
`"--border-radius-control": "border-radius/control"`. There is no `.fab.round`, no round variant class,
no second shape anywhere in the file. **So the brief's branch 2 applies and the face adopts the
reference's geometry.**

### The five whys

1. **Why isn't the overlay using the fab component?** `apollo-fab.js:135` hardcoded
   `border-radius:50%` on the face button.
2. **Why was it hardcoded?** Because the overlay is a **self-contained injected-CSS widget** — it
   authors its stylesheet as a JS string array at mount. It never passes through
   `gen_canon_components.py`, so it inherits none of the reference's bindings by construction.
3. **Why did no gate see the divergence?** Because `_validate_radius.py` **explicitly allows `50%`** —
   it is the legal circle idiom for avatars, radios, spinners and dots. The gate read the FAB's circle
   as a valid circle, not as a component ignoring its own token. A gate-legal escape hatch reads as
   intentional.
4. **Why was `50%` ever chosen?** Because a FAB is conventionally circular, and the reference itself
   says so — while **declining to take it**. The overlay took the convention the reference had
   deliberately left on the table.
5. **Why could it be taken silently?** Because `apollo-fab.js` is a component **implementation** with
   **no declared relationship to its component's reference**: it is not a member of any
   `component-types.json` group and carries no `#token-manifest`. Nothing anywhere asserts
   "the overlay's face is the Fab component".

**ROOT CAUSE.** An unregistered second implementation of a gated component, plus a gate-legal literal
that reads as a decision. Nothing in the KB could have contradicted it.

### What changed — 3 edits, `knowledge/_render/apollo-fab.js`

| # | where | change |
|---|---|---|
| 1 | base `.apollo-fab{}` (no-canon leg) | `--af-radius:0` — the reference's **own base value**, not an invention |
| 2 | `.apollo-fab.af-tokens{}` (canon leg) | `--af-radius:var(--border-radius-control,0)` — the reference's binding |
| 3 | `.apollo-fab .af-btn{}` | `border-radius:50%` → `border-radius:var(--af-radius)` |

**Touched only what geometry required.** `--af-size:56px` and the 24 px glyph already matched the
reference and were not moved. **Behaviour is untouched and was re-driven, not assumed** — see §4.

## 7 · Is there a gate that should have caught this? — PRICED, NOT BUILT

**Honest answer: no gate could have.** Both candidates were green and both were *right* to be green:
`_validate_radius.py` validates the form of declarations that **exist**; `_gate_minted_consumption.py`
asks whether a mint is read **at all**, and it was — by `.ind`. Neither can see an **absent**
declaration on a sibling box. That is the gap, and it is real.

### Option A — `_validate_concentric.py`, a CONCENTRIC-FAMILY gate — **recommended first**

A small registry declares concentric families: for `segmented`, container `.seg` / `.dv-toggle-seg`
with inner members `.ind` **and** `button`, and the family's inner local. The gate then asserts: in
every snippet where the container selector appears, **every** declared inner selector carries
`border-radius:var(<the family's local>)`. Absence fails, named, with the file and line.

- **Cost:** ~180–220 lines + a registry file + the ADR-0005 §5 **bite-test** (plant a stripped rule,
  prove it goes red, restore). **S-band, one focused lane.**
- **Catches:** this exact defect in all twelve copies, permanently; and it goes **red today** on the
  four snippets in §6 item 1 — which is a feature, but means it must land *with* a ruling on those.
- **Limitation, stated up front:** it is a text check on the snippet, not rendered geometry. It proves
  the boxes read the same token, not that they are actually coincident. It would not have caught a
  wrong *inset*.

### Option B — a `segmented` PARTIAL group — the structural fix

Make `Segmented-control.reference.html` the source atom, wrap its `.seg` core in `PARTIAL` markers,
register the eleven consumers with per-member `rootSelector` mapping, and let
`gen_component_partials.py --check` hold them byte-identical forever. **The machinery already exists
and is proven** — `button-family/press-physics` runs it across 18 members today.

- **Cost:** registry entries + marker surgery in 12 files + `requires.vars` / `$manifestBinds`
  contracts. **M-band, one lane, wider blast radius.** One real snag: the charts' hover colour is
  `rgba(127,127,127,.14)` while the atom's is `var(--hover)`, so either that unifies (a **visible**
  change needing Dave's eye) or the hover rule sits outside the partial.
- **Payoff:** the class cannot recur. A repair to the atom reaches all twelve by generation, and
  `--check` fails the build the moment one drifts. This is what would have stopped #227's B6 *and*
  today's F1 *and* §6 item 1, all three.

### Option C — for F2, the unregistered-implementation class

`apollo-fab.js` is a component implementation that no instrument connects to its reference. The
partials machinery does not reach it (it is not a snippet). The cheap arm is to require a **named
justification comment** beside any `border-radius:50%` in `_validate_radius.py` (~40 lines) so the next
circle has to argue for itself. The honest arm — a manifest binding the overlay to `Fab.reference.html`
— needs a new mechanism for non-snippet implementations. **Priced as: cheap arm S, honest arm M+,
scope unclear until someone asks how many other non-snippet implementations exist.**

**Recommendation (best practice over convenience): A first — it is cheap, it catches the class
immediately and it moves no pixels. B as the structural follow-on, paired with a ruling on §6 item 1.
Both are Dave's; nothing was built.**
**Permanent-fix owner named: the conductor, to put A (and the §6-item-1 ruling it depends on) to Dave
at the #229 seam. I own the tactical fix only, which is enacted and proven above.**
