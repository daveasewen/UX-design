## THE ANSWER FIRST

**One defect, two reds.** `_gen_chain.build_verdict_line()` printed the denominator of the BUILD VERDICT sentence from the newest ledger record (`v['total']`, the step count THE RUN saw: 146) beside the words "total from `_build_all.py`'s AST". The AST says 148 since R4b. So the chain claimed a provenance its number did not have - a silent gap - and `[121]`'s bite, which re-derives 148 from disk, went red.

**`[13]` is the same bite, one level down.** `_capture_gate.py --selftest` calls `_gen_chain.selftest()` (arm `#70/#71 non-catch`, line ~9455) and fails when it fails. Its survey line only showed the first `❌` in the output, which is a fixture's own `pre-flight:` line - that is why it looked unrelated. Full output, reproduced first try in the clone: `❌ selftest: #70/#71 non-catch: _gen_chain.py --selftest is NOT green`.

**Why it looked flaky - an ordering dependence, not chance.** Both reds exist only while the newest ledger record's `steps_on_disk` differs from disk. `_build_survey.py` APPENDS a record at the end of every run or chunk. In CI, step 5's survey appended a 148 record, so step 6 read `[13]` as 77. In V2's clone, the first chunk (with `[13]`) ran on 146 and every later re-ask ran after a 148 record existed. Driven with the old code: ledger 146 → exit 1, planted 148 → 77, planted 150 → exit 1. The ledger alone decides it; no race, no clock, no temp dir, no network, nothing x64 or arm64.

**The selftest contradicted itself.** One arm asserted the denominator is DISK's (`MATCHES DISK`); the stubbed-ledger arm asserted `"7 of 13 steps GREEN"` against a 146-step build, i.e. that it is THE RUN's. Both could pass only while run and disk agreed.

## THE FIX (one file, `knowledge/_gen_chain.py`, +82 −12)

1. **The denominator is the AST's**, as the sentence already says. Green, fail and could-not-ask stay THE RUN's. When the run's build was a different size, the line SAYS so: `⚠ that run surveyed 146 steps; 148 are on disk now — step(s) 147–148 are newer than the run.` The steps the run never saw are counted into `N step(s) are in NO record — never asked, never green`. A shrunk build is declared too (`K step(s) have gone since…`). A declared gap passes; a silent one fails.
2. **The check compares like with like.** `VERDICT_FIGURE_RE` reads the figure out of the BUILD VERDICT sentence itself. The old bite accepted `" 148 steps"` ANYWHERE in the chain. Measured: the old substring check passes a chain whose verdict says 146 while 148 appears elsewhere, and the new one refuses it.
3. **New bites:** the check is mutated inside the selftest (the verdict figure is moved off disk while the true count stays elsewhere in the file; there is a plant-planted guard). The stub ledger is sized to disk. A same-size run declares nothing. A smaller run keeps disk's total, declares both counts, and counts the new steps as in NO record. A larger run declares the vanished steps.

**Mutation-tested at the seat:** denominator put back to the run's → 3 bites red (`MATCHES DISK`, `SMALLER`, `LARGER`). Denominator `now + 1` → 4 red. Declaration clause dropped → 2 red. The fix → all bites pass.

**Why not the import route.** A survey record committed after a commit is always one sha behind, because committing it makes a new sha. That is exactly why the stale-sha clause already exists. The step-count difference is the same kind of staleness and needs the same declaration. An imported record would only narrow the window, every future `STEPS` change would re-open it, and it would put a survey's writes one step from the mount. So no script was built. The ledger's own age (53 green, from a dirty chunked run at `e31aa34b` on 09-21) is still a real, declared staleness. Refreshing it is a separate job from `[121]`.
