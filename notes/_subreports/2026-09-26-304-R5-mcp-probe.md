## 5a: the catalogue generated from the metas
Files: `gen_catalogue.py` writes `catalogue-all.json` (137 parts), `catalogue-dashboard.json` (18) and `catalogue-report.json`. The generator takes 1.6 s. The shape copies the official basic catalogue: `catalogId`, `components` (each is `allOf[ComponentCommon, CatalogComponentCommon, {component const, props, slots}]`, `unevaluatedProperties:false`) and `$defs.anyComponent/theme`. Apollo's own data sits in an `x-apollo` annotation. That covers level, status, provides/answers/shape/span/priority, when (split into gate and prose), variants, slots with `accepts`, states, the a11y role and SC, the snippet, and the rulings over the part. The rulings are taken from the reader's own `governs_for`/`obeys_for`, not re-implemented. The id is `https://apollo.invalid/…/v0.0.1-probe`, a deliberately reserved domain.

The dashboard's parts were derived by script, not by hand. They are the union of the `$composes` lists on template-dashboard and template-dashboard-bento, plus the worked example's line chart and list, plus the #261 metas: 18 parts in all.

**Validation:** `validate_a2ui.py` runs in the venv. It checks C1 (the document against the 2020-12 metaschema) and then each entry: E0 (the entry is itself a valid schema), E1 (a minimal instance validates), E2 (an unknown property is rejected) and E3 (an `updateComponents` message validates against `server_to_client.json`, with `catalog.json` resolved to our catalogue). Results: 137/137 and 18/18 pass. The harness negatives also bite: an unknown part is refused, and a missing required slot is refused.

The official basic catalogue ran through the same harness as a control: C1 passes, and 13 of 18 entries pass. The five failures come from the probe's minimal-instance builder: it does not synthesise arrays or icon names.

**The harness was mutation-tested** with `validate_mutations.py` (five one-change breaks). The first run found a real hole. The 2020-12 metaschema does not descend into `components`, so an illegal type inside an entry passed C1. The per-entry E0 check was added, and all five breaks are now caught.

**Spec observations:**
- The published basic catalogue is not a valid inline `Catalog`: its `functions` is an object where the schema wants an array, and it has extra top-level keys. Our catalogue has the same one extra-key error in inline form. Reduced to `{catalogId, components}`, it passes as an inline catalogue.
- A2UI cannot say which kind of child a slot accepts. Apollo's `accepts.capability` would have to be enforced by Apollo's own gate.
- `anyComponent` is a `oneOf`, so its failures quote the whole instance. The gate therefore validates each part against its own entry to give readable reasons.

**The levels (from `summarise_catalogue.py`, receipts in `catalogue-summary.json`):**

Three findings from the table matter most:
- **No container.** No part in the dashboard set can hold several children. Layout-utilities declares no slot, and the app shell's `content` slot takes a single child. A dashboard of four parts cannot be expressed as a tree from this catalogue alone.
- **Content is missing.** 45 metas describe how a part looks but not what it says. The button has no label prop, the header no title, and the status indicator no label.
- **Params and slots share names.** 27 metas give a param and a slot the same name (chart `data`/`series`, donut `slices`, KPI `target`). An A2UI property can be only one of them. The probe let the slot win and logged the loss. Across all parts there are 195 loss lines on 63 parts, all in `catalogue-report.json`. Chart data is modelled as child components rather than as a data binding, which is G1's gap 2, still open.

**The thirteen schema errors, and which the catalogue would publish:** `catalogue-report.json` › `schemaErrorPublication` maps each error path to the catalogue fields read from it. **4 of 13 would be published.** All four are the `stateModel` shapes on data-grid, filter-toolbar-bar, kpi-tile and legend, because the catalogue carries a part's states: a live renderer needs ready/loading/empty/error/stale. The other 9 would not be published, because the catalogue never reads those fields: data-grid's six string `with` entries and its `relationships.composes`, and legend's `with/0` and `provenance.source 'hand-authored'`. No schema was touched. That decision is Dave's.

## 5b: a gate that runs in memory
File: `gate_mem.py` (venv). It works in two layers.
- **Surface layer.** Each A2UI message is checked against the spec with our catalogue. Each part is checked against its own entry. The gate also requires one root, unique ids, child references that resolve (the schema cannot see these) and no deprecated part.
- **Accessibility layer.** The page string goes through `check_text()`, an in-memory port of `_validate_a11y.check()`. It uses the same `_a11y_target` engine, and its tiers are read from the disk module at call time.

The page string is made by a stand-in that splices the parts' reference snippets. It is not a renderer; the renderer is PoC step 2.

**Same verdict as the disk gate** (T1). Checked on the 10 dashboard-part snippets (App-shell-top-nav … Kpi-tile): 10/10 identical. On all 137 snippets: 137/137 identical, comparing fails, warns, notes and every control and mark verdict. All 137 pass the disk gate, though, so a dropped fail clause would go unseen. T1b therefore also ran six planted pages through both gates, and all 6/6 were identical, including four FAILs.

**Planted defects** (T2), 14 of 14 as expected. A clean six-part surface passes, and a clean page string passes. Each of these is refused, with a named reason:
- a 16 px button, both alone and planted into the real spliced page (one change flips the verdict)
- an animation with no reduced-motion block
- an unknown ARIA role
- a part not in the catalogue
- a missing required slot
- a dangling child reference
- no root
- duplicate ids
- a deprecated part
- an unknown property
- a state outside the meta's values

**Known misses** come from the disk gate's own design, which the port keeps on purpose:
- K1: the 2.3.3 clause tests the whole string, so an animation added to a page where any other part has a reduced-motion block passes.
- K2: a comment that merely mentions the phrase also satisfies it.
- K3: a control sized only by padding is UNMEASURED, and only the render leg would catch it.

K1 matters for composition. Once parts are spliced onto one page, the motion clause goes blind.

**Timing and no writes** (T3, n=25):
- Warm, per surface: median **61 ms**, max 70 ms. Of that, the accessibility check is 49 ms on a 165 KB spliced page.
- Cold, including building the validator: 71 ms.
- An audit hook recorded **0 writes and 0 file reads** during the warm calls. The cold call read the 2 spec files.

Compare G1's 0.68 s for the static screen gate, which spawns processes and writes records.

## 5c: the when-evaluator
Files: `SPEC-when-evaluator.md` (the spec 5a writes for 5c) and `when_eval.py` (system python). The evaluator:
- parses the gate half of each `when` by the registry's own grammar
- judges each clause with three values: true, false or unknown
- excludes a part only when its gate is false
- ranks the remaining parts by the number of true claims, then priority, then slug

It passes a selftest of 15/15 bites.

**Parse coverage:** 39 metas have a when-rule. They hold 123 clauses: 80 field claims and 43 prose. The resolver counts 78 field claims; the extra 2 are bare ranges the resolver reads as prose (Chart-bullet `span.cols 4–6` and chart-line `series 1–5`). Four gates have no field claim at all (alert, icon-button, popover, view-options), so the evaluator can never pick them on evidence.

## Decisions for Dave, in plain words
1. **The meta schema.** Four of the thirteen errors would ship in a catalogue: the part states on the data grid, filter bar, KPI tile and legend. Either widen the schema to accept those state shapes, or bring the four metas back to it. A live screen needs states either way.
2. **Where a part's words come from.** 45 parts, including the button, the header and the status dot, have no field for their own text. The choice is to add content fields to the metas, or to let the screen borrow A2UI's plain Text parts as children.
3. **A container.** Nothing in the dashboard set can hold several parts. The choice is to give layout-utilities (or the bento template) a children slot, or to import A2UI's own Row and Column into the Apollo catalogue.
4. **Param or slot, when a meta names both the same** (27 parts). Which one wins in the catalogue?
5. **When-rules.** The two chart-line clauses above close both chart misses. Should the chooser also treat a part's own answers and shape as rules (variant B)? And the data grid needs a when-rule plus a new field name for "sort, filter, select or edit".
6. **The motion check on composed pages.** One reduced-motion block anywhere on a page silences the check for every part. Should it be per part before gates run on assembled screens?
7. **Beta parts in the PoC.** Five dashboard parts are beta: the app shell, KPI tile, legend, layout-utilities and footer. Do they ship in the first catalogue?
