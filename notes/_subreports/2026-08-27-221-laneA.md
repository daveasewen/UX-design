```
Scanned **164** … **48** hardcoded foreign-theme colour(s)      ← both
58 lines                                                        ← both
26 lines differ in EACH direction                               ← a pure PERMUTATION
```

**Cause:** `os.walk` yields in filesystem order and the gate never sorted — so the committed
report's row order is a fingerprint of whichever machine wrote it, and no two environments can
ever agree. **A non-deterministic generator is worse than a stale one**, because every comparison
anywhere is noise. L1's "26 rows changed" is, on this evidence, that same permutation — a FALSE
staleness. My first reading of the diff was wrong too (I read a `head -6` of `>` lines as
additions); the counts settled it.

Fixed at cause: `dirs.sort()`, `sorted(files)`, and the result list sorted by
`(area, file, hex)` — belt and braces, so a future change to the walk cannot silently reintroduce
it. **No value moved: 164 scanned and 48 findings before and after.** Proved across both
environments: the working tree and the bare clone now produce a **byte-identical** artefact. A
`--selftest` was added (5 arms, with the control that makes the order assertion falsifiable) and
wired into `test_gates.py`.
