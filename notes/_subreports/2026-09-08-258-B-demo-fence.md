**Leaf vs container rule I applied** (stated so the next lane can agree or overrule): chrome that is a LEAF
(headings, notes, state labels, tier labels, readouts, dials and their scripts) is fenced **in markup**;
chrome that is a **container wrapping component markup** (`.demo-frame`, `.demo-col`, `.demo-box`, `.row-demo`,
`.guide`, `.l-demo`) has its **CSS fenced only** — fencing the element itself would delete the component with it,
which the acceptance test forbids. Deleting those fences leaves a bare unstyled `<div>` around the component.

## 3. `--demo-width`: what moved, what did not

The ruling says demo vars the component reads are **moved to real component defaults**, not fenced. Done in
7 files. One exception, deliberate: **`Links.reference.html` keeps the NAME `--demo-width`** on `.related`,
because it is a declared runtime var (`knowledge/_validate_compose.py:42` `RUNTIME_VARS`) written onto
`#related` at runtime by `knowledge/_render_links.py:32`. Renaming it would silently kill that dial. The rule
still gained a real default (`width:100%; max-width:var(--demo-width,560px)`), so the component renders at
560px with nothing outside the file, and a comment in the file names the contract. `_render_tags.py`'s
`#filterbar` target is `Tags` — lane C, not touched here. `grep -l 'demo-width'` across the 20 lane-B files
returns exactly one file: `Links.reference.html`.
