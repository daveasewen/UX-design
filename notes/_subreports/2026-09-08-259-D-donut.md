## What I could NOT do — first obstacle, named

1. **`dv-004` cannot be evaluated on an engine-drawn donut, and it is BLOCKING.** The static
   dataviz gate reads markup: for a donut it looks for `path.dv-series` with a ≥2px
   surface-coloured stroke, and `_rect_stack_gap` returns `None` ("segments are not measurable
   rects") for arcs, so the fallback demands the stroke. An emptied canvas has **no segments at
   all**, so the gate fails safe on a chart that satisfies the rule by 2.199px of real geometry in
   the browser. This is **[[no-gate-parses-the-artefact]] arriving for the second time in one
   session** — lane A hit exactly this on Chart-bar's stacked canvas (its item 3). RULING-SHAPED.
2. **The DIRECT-LABEL canvas (cd2) stays BAKED.** Two reasons, neither a shortcut: (a) the ruled
   spec has no field for a labelling mode, so "name and value in place, mirrored value ⇄ percent"
   is not expressible in `{type, categories, series, format, unit}`; (b) the page is already 2,971
   bytes over budget and direct labels are the most expensive thing a ring can emit. It keeps the
   snippet's dv-004 story honest for one of the two figures, which is the same trade lane A made.
3. **≥8 categories is not available to this type.** dv-pie-009 caps a ring at six slices, and
   ds-026's solid palette caps it at **five** before that — a sixth slice wraps onto
   `--data-series-1` and a sixth legend swatch would bind a token that does not exist. The
   snippet and the test page therefore carry FIVE, which is the honest maximum, not a shortfall
   against the brief's "≥8 where the type allows".
4. **A re-render does not re-run the sweep or refresh the legend's value cache.** `dv-donut-sweep`
   and `dv-legend` both guard on a `window.__dv*` flag and initialise once; after a filtered
   re-render the arcs are correct but the legend's cached `data-tip-value` map is stale. Not
   re-running the SWEEP is correct (it is an INTRO). The stale legend cache is a real gap and is a
   **core request**, below. I did not touch either file — neither is mine.
5. **`.dv-mk` is moot on this type and was deliberately not emitted.** A radial canvas carries no
   `dv-fit`, so `fitY`/`fitOne` never run on it and no glyph is ever re-scaled; adding `.dv-mk`
   would be a claim about a pass that does not happen.

## Core requests — verbatim, for the core owner (do NOT let a type lane make these)

1. **`dvRender` calls `furniture()` unconditionally and offers no switch.** A radial type has no
   band axis, no value axis, no gridlines and no baseline, so `dv-render-donut` opens with
   `ctx.out.length = 0` to DISCARD furniture the core has already pushed. Requested change,
   verbatim: *"Let a type partial opt out of the cartesian furniture — honour `fn.axis = "none"`
   (or `fn.furniture = false`) in `dvRender` by skipping the `furniture(ctx, …)` call, the way
   `fn.axis`/`fn.domain` are already honoured. Until then a radial type is silently paying for
   gridlines it throws away."*
2. **`dv-legend.rec()` caches `data-tip-value` once and there is no way to invalidate it.**
   Requested change, verbatim: *"After a `dvRender()` re-render the legend's per-series value cache
   (`host.__dv`) describes marks that no longer exist. Either expose an invalidation hook the
   engine can call (`delete host.__dv`, or a `dvLegend.refresh(fig)`), or have the core clear
   `__dv` on the figure's legends before it dispatches the re-fit `resize`. The same argument the
   core already makes for the cached fit fractions applies: they described geometry that is gone."*
3. **`dv-donut-sweep` has no re-entry point.** Requested change, verbatim: *"The sweep's IIFE runs
   once at parse time and `window.__dvDonutSweep` prevents it running again, so a consumer MUST
   inject it after its `dvRender()` bootstrap. Expose `window.dvDonutSweep(figure)` so the order
   dependency is a choice rather than a trap."*

   ruled. Today the partial throws at 7 (dv-pie-009's number) and would silently reuse series-1 at 6.
