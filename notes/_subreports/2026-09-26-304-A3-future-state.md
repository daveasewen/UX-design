## 0. The answer in five lines

Apollo, finished, is a governed engine that composes on-brand, accessible screens from its own parts, knows why each part is right, refuses what breaks the rules before anyone sees it, leaves a record, and can be asked for a live screen by any agent over MCP.
The parts bin, the gates and the graph are built and measured. What is thin is the middle: the judgement that composes well (Dave's "sloppiness" of 2026-09-19 is ungated and unfixed), the evals that prove a run beat the last (hand-scored), and the pack that carries the graph to a consumer (the one Friday's audience holds does not).
Of Friday's claims, the counts are true; the capability slides (knowledge graph at build time, the designer's brain, gates and evals) are PARTLY true in the repo and NOT YET true in the pack that went out in the email bundle; the value slide and the enterprise slide are hypotheses and asks with no measurement behind them yet.
Recommended next milestone: Spider v1.0.14, "the pack the deck describes" — reader and Constitution shipped, the skill rewritten to compose rather than trace, his three observations in the graph, a geometry gate for the sloppiness class, and an automated before/after eval on his CEO Common prompt. Apollo-MCP's catalogue slice runs beside it as a second track, because both need the same when-rules.
Friday's outcome is not in the record (`_HANDOFF-154` "Ask; do not assume"). If the room asked for a pilot, that changes the order; the conductor should ask before the roadmap sets.

## 1. The future state in plain words, stitched from the record

### For a designer
A brief goes in; Apollo asks the few questions that matter, agrees what "done" means before anything is drawn, composes several on-canon answers, shows only the ones that passed the gates, and asks for a twenty-second taste call; the winner's judgement is written back into canon so the next brief starts further on. Receipts: `notes/_VISION-northstar-front-end_2026-07-02.html` ("One screen, one day: judgment spent once, retrieved forever"; six stages brief → contract → register spread → gate report → taste call → promote); `notes/_VISION-iteration-machine_2026-07-03.html` (Input → Shape → Result → Refine, "Regenerate within the curbs"; its line to protect: "the enforcement under Cool/Warm/Hot must stay present even when it's quiet — that's the difference between this and a commodity generator"). Dave on the July mock, via retired memory as quoted by G1: "good expression of where we get to, not a vision yet but close." ADR-0006 (2026-07-03, accepted) makes it one engine with four dials — discovery depth, register, unit (cluster → screen → journey), library growth — and says "own the governance (the standard) beats owning generation (the labour)". The September premise sharpened this: Apollo must compose, not trace. Dave, #288 (2026-09-19, `_HANDOFF-139`:58–63): "what was the point of building the system if it just traces from existing examples??? … this isn't Apollo its a dot-to-dot book", then on the fenced-template probe: "we need to do something about the sloppiness and, its all about alignment spacing and dimensions" (`_HANDOFF-139`:73). Parked designer-facing features in `_FUTURE-STATE.md` (last edited 2026-09-09): edit mode with bounded parameters, a live radius tuner, context-aware responsive strategies, expandable "Other" buckets.

### For an engineer
Apollo is the canonical source, not a mirror of any consumer; codebases are reached by automated adapters, and "handoff is a git pull, not a port" (ADR-0008, 2026-07-20; ADR-0002). Sutherland, the bank's React library, is "a consumer … never the template" (ADR-0008). The gated snippets are already the acceptance fixtures a Sutherland implementation must satisfy (`knowledge/_build_sutherland_fixtures.py` header). Dave's Thursday line that became slide 14's third cell was conditional: "If we can ship near production ready code, this will allow technology to pivot spend on to innovation and away from simple code production." (`notes/_lanes/303/WRAP-BRIEF.md`:255).

### For an agent
Apollo is callable. July: gates-as-a-service, validators exposed as MCP tools so a host agent runs generate → check → fix → re-check (Dave's idea, 2026-07-14, retired memory, per G1 §5). September: the ASK door over the graph (s277-D13; `knowledge/_compose_slice.py` header). Today: the Apollo-MCP proposal v2 (`notes/_PROPOSAL-apollo-mcp-2026-09-26-v2.html`) — speak A2UI and MCP Apps rather than invent a protocol; Apollo owns "knowing when each part is right, gating before anything is drawn, checking what each person may see, and recording every screen". Dave's ask (Sat 2026-09-26 13:29, quoted on the page): "do you think we could create our own MCP-UI -- Apollo-MCP maybe or something that has the same capabilities as Google's A2UI and MCP-UI". And from July: "the KG is a valuable resource and shouldn't be ignored, thats what it is there for" (`_FUTURE-STATE.md`:127 ff., Dave 2026-07-27).

### For the bank
Two things. First, a design operation that delivers more, faster and cheaper under one system: slide 14's six cells, and the strategy's prove → encode → shift → scale roadmap (`digital-experience-transformation/strategy/03_phased-roadmap.md`, draft v0.1, whose Phase 0 metric is "time-to-trustworthy-prototype on the lighthouse journey vs the old hand-built baseline"). Second, a "trust layer for assembled UI": a run-time dashboard where "every element is provably compliant and the user only ever sees what they're entitled to" (`notes/_VISION-contextual-dashboard_2026-06-29.md`), now the Apollo-MCP proof of concept. Slide 15 turns this into an organisational ask: product ownership, funding, a team, pilots, KPIs. Two cautions in the record itself: the strategy folder says of the run-time vehicle "Don't oversell it to leadership as imminent" (`strategy/00_READ-FIRST_strategy-status.md`:19), and the June note's own revisit condition is "The design-time loop is proven on one real HSBC screen" (`_VISION-contextual-dashboard_2026-06-29.md`:84). Neither is a veto; both are premises the roadmap should state rather than skip.
