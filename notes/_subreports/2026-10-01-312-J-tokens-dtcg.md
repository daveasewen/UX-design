## Design notes V should read first

The seam, not 25 hand ports. The brief counted three readers of the token files; the live tree has twenty-five that `json.load` them and walk the old shape (light/dark leaves, `$alias`, `$note`, "16px"). Re-feeding each natively today was neither safe nor provable by 15:00. The precedent is `_dtcg_units.py` (s141-D1 (A)): one module at the read site, every consumer carries on with the data it always had. So `_dtcg_load.load_legacy()` hands each reader the pre-s311 view, computed by the generator's own inverse, and the gate proves on every build that (a) the inverse is exact (forward(inverse(file)) == file, and inverse == the pre-s311 files by parse at landing), (b) the two outputs that matter are byte-equal. The consequence V should test: a token edited in the DTCG files IS seen by every reader (bite 5 of the gate's selftest proves the cache is mtime-keyed, not stale). The consequence Dave should know: readers "think" in the old shape until phase 1 ports them; the file on disk is the standard, the seam is scaffolding with a gate on it.

Alias folding is value-checked, never assumed. An `$alias` became the `$value` reference only when its target resolved, in that mode, to the hex the file already carried (353 of 354 did). The one that did not — `primary/border/hover` dark names `color/red/700` (#BA1110) but holds #D61412 — keeps its literal `$value` and its alias under `$extensions.apollo.alias`, so nothing was re-coloured. Found, not fixed (below).

Where the moved keys live. Every non-standard `$` key on a token or group moved to `$extensions.apollo.<key>` (201 of them: note 83+, contrast 50, darkNote 11, confidence 14, label 6, noteLight 6, siblingSet 2, webStack, metrics, reconstructionNote, provenance, guidance, bands, spanDerivation, roles, name, substitutesFor, condition, rule, whiteTextContrast). Two pre-existing vendor keys are untouched and known by name to the inverse: `com.apollo.sds` (24 uses, s141-D1 (B) + s217-D4 `cssKeyword`) and `apollo.state` (4 uses, ADR-0009). The forward transform REFUSES a collision between a moved key and an existing one (bite 8).

What light means. The base file carries the light value; light is the resolver's default context and adds no sources. The dark context file carries only tokens that had a dark leaf (196). Every group description, deprecation and `$type` stays on the base token; a dark entry is `{$value, $type}` so it is a legal standalone DTCG file too.
