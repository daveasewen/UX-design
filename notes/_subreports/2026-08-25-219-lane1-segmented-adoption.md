## Findings

**1 · The `s202-D1` base-tier SIZE mint never happened, and the generator's own comment says it
did.** `canon/gen_theme_cascade.py:86-88` routes `size/` to `layout.json` with the comment *"size/
segmented-control/* is minted in the BASE layout store (mono is the base theme)"*. Probe, before
the fix: `base_value("size/segmented-control/s", "light")` → **`KeyError: 'size'`**. The radii
(`layout.json`) and paddings (`spacing.json`) both carry a `$reconstructionNote` recording that
*"an accidental `git checkout` in the same session discarded the uncommitted s202-D1 base mint"* —
those two families were reconstructed at #202; **the sizes were not, and nobody noticed for 17
sessions because nothing consumed them.** Closed here by restoring
`layout.json » size/segmented-control/{xs,s,m,l,min-hit-area}` = 24/36/44/48/44 — **Dave's own
tuner-v3 numbers, byte-identical to console's overrides, no new value invented.** Enactment of an
existing ruling, but the conductor should confirm it rather than let it pass silently.

**2 · The `.cn-*` scope does NOT read the theme token at runtime — `gen_theme_cascade` flattens
it.** `canon.css:23085` emits `[data-apollo-theme="console"] .cn-segmented-control{--seg-rad-s:
8px; …}` — a concrete literal at specificity (0,2,0) that short-circuits
`--border-radius-segmented-container-s` completely. Probed by mutation: overriding the token var
changed nothing at all. This is `s200-D1`'s mint-time derivation working exactly as ruled (the
disk carries plain numbers), but it means **"the component consumes the token" is true of the
SOURCE and not of the DELIVERY**, and any future probe that mutates a token var will silently
prove nothing.

**3 · Three token routers disagreed, and two were blind to `size/` and `padding/`.**
`gen_theme_cascade.py::_store_for` knew both; `gen_snippet_tokens.py::resolve` and
`_validate_snippets.py::resolve` did not — a manifest binding to `size/segmented-control/s` would
have fallen through to `semantic-colour.json` and `KeyError`d / returned `None`. This is the
ds-018 silent-lookup class the `gen_snippet_tokens` router is *already annotated about* ("this
router was never taught the store", s121-D1 #121), recurring one and two files over. Both taught
here, with the class named at the site. **⬛ NOT fixed: the class itself.** Three hand-maintained
copies of the same routing table is the defect; a shared `_token_router.py` is the honest fix and
is a refactor, not a repair — priced in the ruling-shaped section.

**4 · The `.seg` mechanism is duplicated across NINE more snippets and they are all still
square.** Each carries its own local copy, none scoped to `.cn-segmented-control`, so this lane's
fix cannot reach them: `Filter-toolbar-bar` (`:151`), `Template-settings` (`:228`), `Chart-donut`
(`:179`), `Chart-line` (`:277`), `Chart-pie` (`:159`), `Chart-bar` (`:257`), `View-options`
(`:27`), `Template-dashboard` (`:357`), `Template-report` (`:239`). The snippet's own header names
this as an "observed duplication — ADR-0013 group-#3 candidate". Not fixed: nine snippets is a
wave, and several of those `.seg` copies are visibly *different* controls (Table's has inter-cell
dividers, Tab-bar's is a 999px lozenge), so a blind sweep would flatten real distinctions.

**5 · `--padding-card-internal` is the SAME CLASS as the finding this lane was sent to fix.**

grep for `var(--padding-card-internal)` outside `reviews/` returns zero files. The card half of

## RULING-SHAPED QUESTIONS

**1 · Which minted corner does the legacy `.lg` borrow?** The two readings agree on `sm→xs` and
`md→s` and disagree only here. **(a) Ordinal** `lg→m` — radius 10px in console, three distinct
corners, a ladder that keeps growing; *this is what is wired today*. **(b) Nearest height**
`lg→s` — radius 8px, because `.lg`'s 36px matches scale `s`'s 36 exactly, so `md` and `lg` end up
looking alike. Both are drawn live and switchable in
`reviews/SEGMENTED-ADOPTION-2026-08-25-v1.html`; console is where the difference is visible.
Recommendation withheld deliberately — it is a curve-matching judgement and `s199-D3` is on record
that the curve match is the whole point.

**2 · Do the minted scales get their own mini-ramp step?** `T-D15` binds 12/14/16 to `sm/md/lg`
only, so `.xs/.s/.m/.l` currently inherit the default control face (14/400 via `.seg button`).
Options: **(a)** extend the ramp with a step per minted scale (a `T-D15` amendment, four new
global bindings in `type.css` plus four `_type-bindings.json` registrations); **(b)** have each
minted scale adopt an existing `.t-cm-ctl-*` composite by class in the markup; **(c)** leave them
on the default face. Not touched — typography is Dave's.

**3 · The label inset on the minted scales — 8/12/16/20, PROPOSED.** Read from the fixed spacing
ramp (`gap/fixed/content/small`, `padding/fixed/{small,medium,large}`), chosen to mirror the
legacy 8/12/16 ladder. **It was never tuned on the corner tuner**, unlike every other number in
this component. Ratify, re-tune, or park.

**4 · `--size-segmented-control-min-hit-area` vs `target/min` — two names, one 44.** Retire the
segmented-specific one, retire `target/min` in its favour, or keep both with the relationship
written down? Finding 7.

**5 · The three-router class (finding 3) — a shared `_token_router.py`?** Three hand-maintained
copies of the same store-routing table, and two of them were already wrong. Priced: one new module
plus three call-site swaps, plus a selftest that asserts all three agree on every namespace.
That is a refactor of the token read path, so it is a promotion decision, not a repair.
