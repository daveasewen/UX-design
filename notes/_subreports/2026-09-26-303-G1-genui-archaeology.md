## The gaps between today's Apollo and a live run-time layer

1. **No declarative UI message format.** Components exist as 139 baked HTML documents, not as addressable, parameterised renderers. The one exception is `dvRender(spec)` for charts. A2UI/MCP-UI-style run time needs a JSON surface description (component id + props + slot children + data binding) that a client renderer turns into canon markup. The metas' props/variants/slots are the raw material for that schema, but slots are declared on only 35 of 138.
2. **No data-binding contract.** Snippets carry mock data; shapes.json names 23 data shapes and slots name `accepts.capability`, but nothing maps a live data source onto a slot. dvRender's spec is the pattern to generalise.
3. **Gates are fast but file-bound and write to disk.** The static screen gate runs in 0.68 s and the selector in 0.82 s — fast enough for run time — but both are CLI scripts over repo files, write records, and the render leg needs Playwright. The KG itself is a 107 s offline build. "Gates-as-a-service" (July 14) was never built: no MCP server, no in-memory entry point, no per-instance verdict object.
4. **Selection is keyword-and-role, not a planner.** `_compose_slice.py` returns a candidate set with governance attached, not a layout; `when` predicates exist on 39 metas as prose-with-grammar, and `priority` on 25. There is no evaluator that takes (intent, shape, span, context) and returns the winning component deterministically. The candlestick in a treasury cash view shows the gap.
5. **Nothing about the user.** Entitlements, user context, consent, audit — the whole "vehicle" half of the June 29 note — has no artefact in the repo. And Jev is ruled out as a run-time dependency, so any run-time judgment must be mechanical or ship its own fallback.
