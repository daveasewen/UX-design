## 1 · PIE — composed, not duplicated. Why, and how it is falsifiable

The brief asked me to reuse rather than duplicate **if the core/partial pattern allows a pie to
consume the donut partial**. It does, and three independent facts say so:

1. `dv-render-donut.js` already ends `window.dvRender.types.pie = function (ctx) { ring(ctx, false); };`
   — the pie is the ring with `ri = 0`, built and driven at #259.
2. `dv-render-donut` is already a registered `$behaviour` whose `$description` reads
   "dv-render TYPE PARTIAL — **donut/pie**". Nothing to add to `$behaviour` at all.
3. ⛔ **The decisive one.** `_validate_dataviz.py`'s `ENGINE_TEST_PAGE` map already contains
   `"Chart-pie.reference.html": "donut.html",   # pie is the ri=0 arm of the same partial`. A
   separate `dv-render-pie.js` would make the **committed driven receipt evidence for code the
   Chart-pie page does not load** — and correcting that needs an edit to a GATE, which this lane is
   fenced from. Composition is the only route that does not require the gate to move.

So Chart-pie's change is `consumes: [dv-behaviour, dv-legend, dv-render, dv-render-donut]`, the two
marker pairs, and the bootstrap. **Zero lines of arc trigonometry were written in this lane.**

**The consequence for the EXTRA in my brief, stated plainly:** with no pie partial there is nowhere
in *my* files to put the two-decimal fix, so the whole of it is filed as a core request — but not as

## 3 · BOXPLOT — the five-number summary IS five series

The type registers `boxplot` and takes **no new spec field**. s249-D4's contract is one value per
category per series, and a box plot is exactly five of those in a fixed ORDER —
`[Minimum, Q1, Median, Q3, Maximum]` — with any further series an **outlier candidate**. Two things
fall out for free:

- the core's own `writeTable` emits precisely the five-number-summary table the snippet used to
  author by hand (`Team | Minimum | Q1 | Median | Q3 | Maximum | Outlier`), driven and confirmed;
- the core's validator already guarantees one finite value per category before the partial runs, so
  the partial only has to check what the core cannot know: that the five do not **decrease**.

Marks are authored in the fit grammar — box `rect data-fx` + `data-fw`, whisker/cap/median
`line data-fx` + `data-fx2`, label `text data-fx`, and the outlier pair inside `g[data-fx][data-x0]`
because dv-behaviour's x pass moves rect/text/line/g and **not a bare circle** (that asymmetry is
boxplot core request 3). No mark carries `data-series-group`: five series are ONE distribution in
ONE colour, and claiming five colour channels would be a lie the §04.3 advisory would believe.

## 4 · BOXPLOT — the exemplar's data moved, and why that was the lesser evil

The original snippet's table carried an *Outliers* column reading `5 · — · 98 · —`. The ruled spec
has no null, so an `Outlier` series must carry a number for every category. My partial's rule — *a
candidate inside `[min, max]` is not an outlier and is not drawn* — is honest **on the chart** and
leaks **on the table**: `writeTable` would print the placeholder under a column headed *Outlier*.

A table that misstates the data is worse than an exemplar whose numbers moved, so Teams B and D
gained genuine low outliers (**8** and **3**, both inside the 0–100 domain), the two `—` cells
became real values, the headline moved from "its **lone** standout" to "the **highest** standout",
and both aria sentences follow. **The "this category has no outlier" case is not lost** — it is
exercised on the committed test page, whose fig-boxplot passes `Outlier: [5, 55, 98, 60]` and draws
exactly two dots. The proper fix is `null` in a values array: **boxplot core request 2**, and it is
spec-shaped, so it wants Dave's word.

## 5 · THE 2.109 DEFECT — cause proven, and the attribution corrected

Lane A's finding was that `n1()` rounds radial path coordinates to one decimal. I patched a SCRATCH
copy of `dv-render-donut.js` (local `n2`, 9 call sites, nothing else) and drove the **committed**
`donut.html` twice through `_drive_chart_engine.py`'s own `drive()`, control and patched, 4 themes ×
2 modes each, into a scratch receipts path:

| figure | control (`n1`) | patched (`n2`) | authored |
|---|---|---|---|
| `fig-donut` — ring, measured at the inner edge ri = 60 | **2.109px** | **2.194px** | 2.2 |
| `fig-pie` — wedge, measured at 0.35·ro = 35 | **2.108px** | **2.134px** | 2.2 |

Identical in all 8 combinations; 0 pageerrors; 5 arcs; filter still 5 → 3.

**The donut defect IS the rounding** — 2.109 → 2.194, residual 0.006px = the remaining two-decimal
budget. **The pie's is not.** A pie has no inner edge, so both the partial (`ctx.GAP / (ri || ro *
0.35)`) and the driver ("the engine's own reference radius for a pie") judge it at a **convention**,
`0.35 · ro`. The honest geometry of two wedges is two rays from one centre: their separation is
`r · gap` and it is **zero at the apex**. There is no radius at which a pie satisfies "2px
everywhere". That is pie core request 2, and it is ruling-shaped, not a lane's.

⛔ The fix is filed against `dv-render-donut.js`, not enacted: that file is not mine to edit, and
the same measurement is the receipt the core owner needs.

### One real defect found by driving, and fixed

**The median line swallowed the tooltip.** `.dv-median` is 2px of ink across the MIDDLE of the box —
exactly where a pointer lands — and dv-behaviour's popover is
`e.target.closest('[data-tip]')`. A bare `<line>` **sibling** of the rect matches nothing, so the tip
went **blank at the box's centre** while working at its edges. `elementFromPoint` at the box centre
returned `line.dv-median`, not the rect. Whiskers, caps and the median now carry
`pointer-events="none"` — they are decoration; the rect is the hit target. The clause is
mutation-tested below, not asserted.

## 12 · RULING-SHAPED — Dave's word, not a lane's

1. **dv-004 on a PIE is judged at a magic `0.35 · ro`, in two files that agree by luck.** A wedge's
   separation is `r · gap` and is ZERO at the apex, so "2px everywhere" is unsatisfiable by
   construction. Either the reference radius becomes a named, written-down contract, or the pie is
   scoped OUT of dv-004 the way boxplot already is. The number the gate records today (2.108px) is
   the convention's number, not the chart's worst separation.
2. **The spec has no way to say "absent".** An outlier list is ragged, a missing month is ragged, a
   category with no reading is ragged — and today each statistical type invents its own sentinel.
   Allowing `null` in a `values` array (~60 code bytes across `validate`, `writeTable`, `autoLabel`)
   is the shape, but it changes the contract Dave ruled at s249-D4. **This one blocked a real
   deliverable in this lane** — it is why Chart-boxplot's exemplar data moved (§4).
3. **dv-bar-009's zero baseline is applied to every type by the core.** The rule says bar-family and
   the static gate scopes it to bar-family; only the engine does not. A distribution or a price
   series pays for a baseline its rule never asked for.
4. **`fitOne` moves rect/text/line/g and not `circle`; `fitY` moves `circle` and not `g`.** Two
   passes, one element, opposite answers. Every point-mark type from here on has to know this, and
   today the only way to learn it is to drive a chart and watch the dots stay put. One sentence in
   the core's grammar comment fixes it; whether the passes should be made symmetric is bigger.
5. **`behaviour.partial` scope is still unsettled from #259 item 4.** I followed the CHART-DONUT
   precedent (list every AUTO-BEHAVIOUR name the snippet carries, dv-legend included) rather than
   chart-bar's, because the schema's own words are "the AUTO-BEHAVIOUR name(s) … that the snippet
   carries". Two members in the library now disagree; that is a one-line ruling, not a lane's.
