## RULING-SHAPED QUESTIONS

1. **The stale PROMOTE join key in `reviews/KG-REVIEW-VERDICTS-2026-08-08-s135-v1.json` — re-key
   it, or make the generator match on something that does not rot?** The verdict
   (`data-grid / hasPart / PROMOTE→selection-controls`) is not in doubt; the exact-`$note` string
   that binds it to the edge is (finding 4). Option (a) re-key the row to the current `use`
   prose: one string edit, generator goes rc=0, cost = a #135 verdict is silently re-asserted
   over text Dave ruled at #258 and never saw in a review, and it rots again on the next prose
   edit. Option (b) match on the part NAME (`note.split(":")[0]`, here `selection-checkbox`),
   which is the stable identity of a `hasPart` edge: one generator change, no review file
   touched, cost = a slightly looser join, and `norm()` is currently the only fuzziness the
   DO-NOT-RULE list allows this script. Option (c) leave it red until the corpus is regenerated
   wholesale under question 2, since the key would be rewritten in that same act anyway.
   **Recommend (b)** — the defect is that a REVIEW ARTEFACT was made to carry a mutable prose
   string as a primary key; re-keying it (a) fixes today and guarantees recurrence, which is the
   conflated-fix shape.

2. **Which authored edges survive a regeneration — i.e. what goes into `DECLARED_EDGE_TYPES`?**
   The generator will delete Filter-toolbar-bar's `$contract`, `composedOf`, `delegatesTo`,
   `drivesConsumer` and Legend's `containedBy` + `governedBy` the moment it runs (finding 5), and
   `s245-D7`'s carry list holds exactly one name. This is the same content as lane C's RSQ 3 but
   a DIFFERENT question: C asks which edge types get a SCHEMA seat; this asks which get a CARRY
   seat, and a type can have one without the other (Legend's `containedBy` and `governedBy` are
   both schema-legal today and would still be deleted). Option (a) widen `DECLARED_EDGE_TYPES` to
   every schema-legal type the generator does not derive — mechanical, and it makes "authored"
   the default for anything the generator has no prose source for. Option (b) name the carried
   types one at a time as Dave rules them. Option (c) invert the generator: never wipe `edges`,
   only add/refresh the derived types — the largest change, and the only one that makes this
   class of loss structurally impossible. **Recommend (a) now, (c) as the real fix** — but do NOT
   run `gen_kg_edges.py` before one of them lands.

3. **Legend's `usedInContext` — is `context:dashboard-rows-of-small-multiples` the id you want?**
   This lane repointed the ref there because it is the only id the repo derives (finding 3), but
   the generated ids in that registry are slugified sentences (`context:chart-panels-figure-dv-
   every-registered-chart-type-already-carries-one` is a real node) and Legend's author clearly
   wanted a short concept id. Option (a) keep the derived id — no further work, and Legend stays
   regeneration-clean on this ref. Option (b) shorten the meta's own `relationships.livesInside`
   string to `"Small multiples"`, which makes BOTH the prose and the derived id short and keeps
   the generator the single source — cost: it edits authored prose. Option (c) rule that context
   ids may be authored short names with the prose kept as the `$note`, which is a change to the
   id grammar (s131-D2 territory) and would need the generator taught. **Recommend (a)** — it is
   already enacted and it costs nothing; but if the sentence-shaped node ids bother you, (b) is
   the cheap correction and it is one string.
