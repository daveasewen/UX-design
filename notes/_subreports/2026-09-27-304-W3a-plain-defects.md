## 1 · Common's bento gutter

**Reproduced.** In the `AUTO-BENTO-ROLE-VARS` block of `canon.css`, `[data-apollo-theme="legacy"]` had no `common` twin. A page saying `common` fell through to `:root`, which is mono (40/4). Of the 420 `legacy` selectors in canon.css, this was the only one without an alias twin; the 419/418 count difference beyond it is a comment.
- Measured on cold-run cand-r3 before the fix: `--bento-dashboard-main` 40px, wall `--bento-gutter` 40px.

**The rulings.**
- s219-D1 (5) sets the dashboard main and sub spacing at 24/40/40/24 and 4/4/4/2, in legacy/mono/console/supercharge order. `_render/_bento_edit_rails.json` agrees (legacy 24/4).
- s227-D8 (1): "data-apollo-theme accepts legacy AND common, common is what new work emits".
- `tokens/themes/_themes.json` declares `attrAliases:["common"]` on apollo-legacy. `gen_theme_cascade.py` already honours it through `theme_attrs()`/`sel_group()`; `gen_bento_role_vars.py` did not.

**Fix (generator).** `knowledge/canon/gen_bento_role_vars.py` now reads the registry's `attrAliases` (it adds `attr_aliases()` and `theme_selector()`). Every theme's rule lists its canonical key first, then its aliases, the same shape as `sel_group`. The selftest gains bite 7: every registry alias shares its theme's rule. Two mutants were caught:
- alias dropped → 7b fires;
- registry alias gone → 7a fires.
- Selftest result: `7 bites OK`.

Regenerated: `[data-apollo-theme="legacy"],\n[data-apollo-theme="common"]{24px;4px}`.

**Proved.** On cand-r3 after the fix, common computes 24/4, legacy 24/4, mono 40/4, console 40/4 and supercharge 24/2. The wall `--bento-gutter` is 24px. The overview is 92px shorter at 1440 (2329 → 2237), and I looked at it in light and dark.

## 2 · Kpi-tile clips its own label descenders

**Reproduced (probe `probe_kpi.py`, 1440).** Every `p.kpi-lbl` computes as follows:
- `text-box-edge:text`, but `text-box-trim:none`;
- `line-height` 14px (`t-cm-caption`, `line-height:1`) against an 18px text box (ascent 15, descent 3);
- `overflow:hidden`.

The label box is 14px, and 2px of every descender is cut ("Card spend", "Pending payments", "Available liquidity").

**Cause.** The ds-005 override (`text-box-edge:text text`) was present, but it acts only on a trimmed box. The leading-trim scaffold's element list (`button,a,label,span,…`) does not include `<p>`, and the label is a `<p>`. So the override was inert. This is a third shape of the #261 crop class, after "missing override" and "cascade-dead override" (#214/#215/#268): an override that wins its cascade but has nothing to act on.

**The ruled pattern.** The ds-005 decision tree (`knowledge/_DS-IMPROVEMENTS.md`:183–187) gives the form for a truncating label: `text-box-edge:text text`, which "keeps overflow:hidden (ellipsis survives) AND stops the descender clip (the box now spans the full glyph)". #261 N4 applied the same repair to the nav labels (11px box → 17px box, 0/336 clipped).

**Fix (source).** In `knowledge/snippets/Kpi-tile.reference.html`, the `.kpi-lbl` rule gains `text-box-trim:trim-both`, so the ruled edge bites. The rule carries a comment naming the cause. canon.css was regenerated by `gen_canon_components.py`.

**Proved.**
- The label box is now 18px, the ink fits, and the ellipsis is kept.
- Geometry gate on the snippet:
  - before: 12 G8 at 1440 and 12 at 390, score 1;
  - after: 0 G8, score 2 at 1440 (the one remaining finding is a pre-existing G6 dead band on the empty-state tile).
- Cold-run cand-r3 overview, with the pack's canon patched:
  - before: 3 G8 at 1440 and 6 at 390, score 1/0;
  - after: 0 at 1440 and 3 at 390, score 3/1. The 390 remainder is tiles clipping spans at phone width, which is not this defect.
- 4x crops LOOKED at, light and dark, for the snippet and cand-r3: g, y, p and q are whole.
- Across all 137 snippets at 1440 after the fix, one G8 remains: `Transaction-row` caption clipped by `table.ldg` (2). That is a different element and not fixed here.

⚠ **Visible consequence, declared.** The label box grows from 14px to 18px. The label ink sits 2px lower, and everything below it in the tile sits 4px lower. This is the ruled pattern's own trade (N4 took 11 → 17). On the as-link tile the chevron stays put, so the label now sits 2px lower relative to it; by eye that reads fine. If Dave wants the tile's lock-up height kept exactly, the alternative is `overflow-x:clip; overflow-y:visible`. That form is not ruled, so I did not choose it.

⚠ **Gate gap.** `_validate_descender_clip.py` passed before the fix and passes after it: it checks that the edge declaration exists, not that the trim is on. Adding a leg for "trimmed-edge declared but trim none" is priced S and not built.

## 3 · The donut centre prints raw floats

**Reproduced.** cand-r3 overview centre: `2990.8999999999996`. Toggling legend items one at a time printed `2565.3999999999996`, `211.20000000000002` and `127.30000000000001` (`probe_legend.py`).

There are two sources:
- `dv-render-donut.js`:135, `String(total)`;
- `dv-legend.js`:97, `String(sum)`, which re-sums on every legend change.

**The convention.** DV-D13 keeps the centre in RAW form, meaning unformatted and without a unit, so it never flips form on a legend click. The engine's own raw branch is `fmt()` in `dv-render.js`:115, `String(Math.round(v * 1000) / 1000)`. Both sites now use exactly that expression. This is still raw form, just without the float noise, so DV-D13 holds.

**The other charts.** Checked every `dv-render-*.js`. Only the donut/pie centre and the legend's centre re-sum print a computed sum. Every other printed number goes through `ctx.fmt`, which already rounds. For example, stacked-area's `total` uses `ctx.fmt(tot)`, and bar's stack sums are never printed.

**Proved on cand-r3, with the page's inlined engine patched identically:**
- centre `2990.9`;
- all ten legend reads clean: 2565.4, 211.2, 127.3 and the rest;
- 4x donut crops LOOKED at in light and dark.

`_BEHAVIOUR-GATE.md` refreshed with `--write`:
- dv-legend 7734 → 7760 code bytes;
- dv-render-donut 3875 → 3901 code bytes;
- page budget worst member Chart-combo 34209 → 34235 of 34 KB (98%, unchanged).

⚠ **Seen, not driven.** dv-legend parses each series value back out of the formatted `data-tip-value` (the last number in it). Under `format:'compact'`, a value shown as "£1.2k" would parse as 1.2. That centre would then flip from 1234 to about 1.2 on the first click. Not reproduced on any page here.
