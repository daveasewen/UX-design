Recall, not re-ranking

What nineteen measured calls to Jev say about where the Memento door actually fails, and what it would cost to test the fix.

“okay this seems like a big job and maybe a dramatic change to the system, given that I have a presentation on Friday any analysis is fine but any chages with impact will need to be made after the presentations and demos.”

Answer first

Re-ranking is flat. Recall is the defect. Jev should be paid at index time, not at query time.

Lane J4 re-ranked fourteen real queries with one live Jev request each and moved MRR 0.173 → 0.187 — measured, and smaller than one query is worth at n = 14.

On four of those fourteen queries the record the session actually fetched was never on the shortlist at all, so no re-ordering could ever have reached it — measured. That is a recall failure, not a ranking failure, and it is the defect worth spending on.

The fix that follows from this is a build-time pass: label every record once, offline, and let the door open a second time on those labels. That moves the cost off the designer's query and onto a batch job nobody is waiting for — and it is the only shape in which a ~920 ms oracle is affordable at all.

J4's fourteen queries, in brief

Measured: MRR 0.173 → 0.187. hits@1 1/14 → 1/14. hits@3 3/14 → 2/14. Four rows improved (one by 13 places, one by 9), four degraded, three were unchanged, and three could not move at all. Absent-from-top-20 was 4 / 14 before and 4 / 14 after — a re-rank cannot add a candidate. A caps-off global baseline was harsher still at 8 / 14 absent.

Three of the shortlist misses were the same target, gm:PRIOR — a haystack section the lexical door never surfaced for three different needle queries. One row, ds-018, is the row worth arguing about: Jev promoted ledger:121-2026-08-07-ds-018-ruled-enacted-s121-d1, the record that says ds-018 was ruled and enacted, over the banner the 2026 session happened to fetch. The metric scored that as a five-place degradation. On at least one of fourteen rows the fixture punishes the re-ranker for possibly being right.

Cost of the whole run, measured: 102,106 input tokens / 4,256 output, 7,293 input per request, 14.0 s of wall time. At the rerank cookbook's declared price of $0.042 per 1M input tokens that is ≈$0.0043 — declared, carried from the vendor's cookbook; the API reports no cost field.

Three lessons, and they are the design constraints

  1. state must be the real artefact, never a description of it. J3 paid for this: the stripped page vouched for a marker that had been removed, and Jev answered the state it was given, correctly. J4 kept the lesson — its candidates were the record text itself — and that is why its ladder did real work instead of collapsing.
  2. Sessions are the users of this search, not Dave. J4's fixture is mined from 357 consult-receipts lines the repo wrote about itself; 63 carry a payload. Every query is one a cold session actually typed. So the thing to optimise is a cold session's first lookup — which is also the one place a ~920 ms tax is least affordable.
  3. A haystack fetch is a recall failure wearing a different hat. When the door cannot surface the needle, the session fetches the big containing section and reads down it. Three of J4's fourteen rows did exactly that. Counting those is how you see the defect; MRR hides it.

Proposal A — a second door for Memento

02

A build-time labelling pass. Nothing at query time. Behind a flag, default off. Not started. After the 25th, if ruled.

Label the index once, offline; open a second door on the labels.

The index holds 2,282 records — measured, knowledge/_memento-index.json, key records. Their kinds are already a closed set of fourteen: ls-archive-section 535, pattern-node 380, gauge-block 275, gm-archive-section 263, context-node 222, brief 206, component-meta 139, ledger-section 86, carries-section 71, runbook-section 57, gm-section 20, dream 13, ls-section 11, lane 4. All measured.

What the pass would ask, per record

  • One Choice — three to five typed topic labels, drawn from a closed label set derived from those fourteen bucket kinds plus the 69 synonyms already in knowledge/_consult-lexicon.json (measured: 69 entries under synonyms). Closed, because an open label set is a vocabulary invented by a model, and this repo closed its edge vocabulary by ruling for exactly that reason.
  • One Score — specificity: is this record a needle (one decision, one ruling, one component) or a haystack section (a whole archive block a reader must scan)? That number is what would let the door prefer the ds-018 ledger record over the banner, and it is the direct answer to the three gm:PRIOR rows.

Where it would sit, and where it would plug in

Output goes to a sidecar JSON beside the index — e.g. knowledge/_memento-labels.json — and never into _memento-index.json itself. The index is a built artefact with its own builder; a model-authored field inside it would be indistinguishable from a measured one at the next rebuild.

The plug point is named, not written: search() in knowledge/_search_core.py (line 94). Today it scores each record with score_record() (line 81) and drops it at line 106 when the score is zero. That line is exactly where recall is lost. A second door would be an optional argument beside the existing decorate hook — a labels lookup consulted only for records that lexical scored at zero, adding them as a separately-headed group. Lexical search is unchanged, the caps are unchanged, totals are unchanged, and --fetch resolves exactly what it resolves today. Absent sidecar, or flag off: today's behaviour, byte for byte.

Working: J4 measured 364.7 input tokens per candidate-question (102,106 ÷ 14 ÷ 20) at a 600-character text cap, and 920.0 ms per 20-question request. At two questions per record that is 4,564 questions ≈ 1,664,000 input tokens — $0.070 at the declared $0.042/1M, across 229 requests, 211 s serial. A one-question variant is $0.035 and 106 s. Cost is not the objection to A. Nothing here is.

The honest caveat on that figure: at a 600-character cap the pass reads 1.37M of the corpus's 40.0M characters — 3.4% (both measured). A record's opening 600 characters is what J4 judged, so this estimate is consistent with the only accuracy evidence that exists — but a fuller window costs more and is untested. A 2,000-character cap is roughly $0.10.

The success measure, fixed in advance

Re-run J4's fourteen-row fixture and count absent-from-top-20 before and after. It is 4 / 14 today, measured. That number is the target — not MRR. MRR is what made the re-rank look like an almost-result; the absent count is what made it a real finding. If A does not move 4 / 14 down, A has failed, and the honest reading of a flat result is the same one J4 gave: do not wire it.

One thing the fixture cannot do, stated now rather than discovered later: two of the misses J4 went looking for — the "trigger index" query and the ds-021 ledger entries — point at records the corpus does not hold or did not index. Those are corpus defects. A cannot fix them either.

Proposal B — edge proposals for two families

Proposal C — audit the ruling-to-ruling edges

04

The cheapest item on the page, and the one with a real ground truth. Not run. After the 25th, if ruled.

Ask, of each judged pair: does the evidence support this edge?

One Noul per pair, state = both rulings' own records plus the evidence line already stored on the edge. The proposition is the edge's own claim. Output is a table sorted by probability ascending, so the weakest edges surface first — and the low end is the useful end.

So “78 calls” is the right budget, and it audits both sides: the 47 edges that were written and the 31 that were deliberately not. What none of this does

05

Published as a CANNOT block, in the house style — so the boundary is read, not discovered.

  • The explorer and its layout are untouched. No node id, edge type, file or family key moves. No baked coordinate moves, because nothing enters the force layout.
  • No dependency is created. No key, no route, no sidecar — every door prints exactly what it prints today and says in one line that the oracle was absent. The oracle rule from knowledge/_jev.py holds: an absence is never a failure.
  • The edge vocabulary stays closed. B and C produce a page for Dave to rule on. Neither writes an edge.
  • No family the metas do not describe can be invented. Jev reads state; it cannot conjure 932 token nodes, 251 photograph rows or a font manifest that does not exist. Every family at zero in #269 is at zero because the payload or the decision is missing, and no oracle supplies either.
  • A cannot fix a corpus defect. If the right record is not indexed, no label reaches it.
  • None of this makes Memento better for Dave. It makes it better for a cold session, which is who actually types these queries.

Risks, stated plainly

06

Four, and the first two are properties of the vendor, not of the design.

  1. Latency has exceeded the declared band on every call so far — 19 of 19, measured. 693.5 / 594.6 / 920.0 ms mean against a declared 70–500 ms. This is survivable for A, B and C precisely because they are batch jobs, and it is the single strongest reason not to put Jev on the query path.
  2. The access is early and the limits move. Two requestable model ids exist; the version in the docs' sample responses is not one you may send. Pricing is a declared figure from a cookbook, not a billed one — the API returns no cost field at all. A run priced at seven cents today could be priced differently tomorrow with no notice to us.
  3. Calibration is unvalidated on this domain, n = 19. No artefact has been asked the same question twice, so answer stability is entirely unmeasured. One Score came back at confidence exactly 1.0 on a rubric it had never seen. A labelling pass that runs once and is trusted thereafter is the worst possible consumer of an uncalibrated instrument — which is why the sidecar must stay a sidecar, rebuildable and discardable, and never merge into the index.
  4. The fixture's ground truth is fetch history. “Correct” means a session wrote in its receipt that it fetched that record. The ds-018 row shows the failure mode directly: the metric scored a five-place loss for an answer that may be better than the fixture's. A success measure built on that fixture inherits the flaw, and 14 rows is too few either way. Before A is trusted, the fixture wants 40+ rows.

Decisions for Dave

Five, each one word, none of them due before the demos.

1
Proposal A — go, after the 25th? A build-time labelling pass over 2,282 records, output to a sidecar beside the index, second door behind a flag that defaults off. Roughly seven cents and three and a half minutes of batch time at the declared price. Success is measured one way only: absent-from-top-20 on J4's fixture, 4 / 14 today. My reading is that this is the cheapest honest test of the actual defect, and that it should be run before anything is wired into the door.
2
Proposal B — are those the right two edge types? The recommendation is providesRole across the closed twelve-role vocabulary (1,656 pairs) and an audit of the 371 usesIcon edges that already exist (371 pairs) — about three cents and ninety seconds together. If you would rather the second one proposed new icon edges than audited existing ones, the price moves to seventeen cents, and the full icon space is $1.41, which is why it is priced here and not recommended.
3
Proposal C — run the audit? Seventy-eight Nouls over the seventy-eight pairs lane E judged in #267 — the 47 that became edges and the 31 you ratified as plain citations. A tenth of a cent. The question is not cost, it is whether a disagreement between Jev and your own #267 ruling would be read as information or as noise.
4
Track the receipts file, and give it a rotation rule? knowledge/_jev-receipts.jsonl holds 19 lines and grew by 14 in one lane. It carries no key material — scanned twice, clean both times. Tracking it means a later session can ask what Jev has already been asked instead of re-deriving it; the cost is that it is append-only, conflicts on every parallel lane, and grows without bound. J2 recommended tracking with a rotation rule and left it to you. Still open. A and B would add thousands of lines, so the rule wants deciding before, not after.
5
Jev as a dev-time instrument only — confirm that as a ruling? This is the stance already being held in practice: _jev.py is an instrument, nothing in _build_all.py calls it, no gate depends on it, and an absent oracle is never a failure. Everything on this page fits inside that stance — A, B and C all run offline and all produce artefacts a human ratifies. Making it an explicit ruling would close the question for every future lane rather than re-litigating it each time.
