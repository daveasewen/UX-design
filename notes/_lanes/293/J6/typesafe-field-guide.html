Answer first

Five pages change what we would build. The largest change is that the proposal's request arithmetic is inverted.

One sentence each, in the order they matter.

  1. Line-by-line search — a single Choice question can carry up to 255 candidate ids at once with a companion Noul asking whether the corpus holds an answer at all, which turns Memento retrieval from a twenty-wide re-rank into a roughly two-hundred-wide joint ranking with an explicit absence signal, and absence is the exact defect lane J4 measured.
  2. Parallel questions — batching many questions about one state is free and provably does not move the answers (declared: 12.2× cheaper, 10.0× faster, run-to-run standard deviation unchanged), which means the saving comes from re-using one state, not from packing many records into one request.
  3. Knowledge graph entity alignment — a three-level Score whose levels are the three available actions (merge, hand to a curator, leave unlinked) removes every fitted threshold from Proposal B and replaces it with wording you can write before you have seen a single number.
  4. Double-checking citations — one Choice over supports / unsupported / contradicted, preceded by an exact-match prefilter done in ordinary code and followed by a confidence flag, is precisely Proposal C's audit, and C's thirty-one recorded human “no”s are a calibration set for the confidence threshold rather than a thing to argue about.
  5. Models — 64k tokens per request (32k for state plus the longest question), 1,200 requests per minute, 250,000 tokens per second, $0.042 per million input tokens with output tokens free, and versioned ids such as jev-1.13.0 accepted whether or not they appear in the model list — which sizes everything above and corrects one of J5's stated risks.

What changes in the standing proposal

The cost conclusion survives. The request count does not.

J5's Recall, not re-ranking priced A, B and C by assuming twenty questions ride in every request, carried over from J4, which put twenty Memento candidates into one shared state. The documentation does not sanction that shape. Classifying RAG passages says it in one line: “Nothing batches passages into one request, because each question is about one pair.” Parallel questions shows the saving comes from sending one document once and asking thirteen things about it — not from putting thirteen documents in one envelope. And jaggedness mode 5 names a state full of material the question does not need as an accuracy cost in its own right.

Recomputed on that basis, every cost falls and every request count rises. Cost falls because a per-record request stops re-sending nineteen other records; requests rise because each record now needs its own envelope. Nothing crosses a tenth of a dollar, and nothing comes close to the declared rate ceiling.

The honest caveat on the whole table: the recomputation assumes the per-question token rate J4 measured carries over to a one-state-per-request shape. It probably does not, exactly — a request that sends one record pays its wrapper and its criteria block once for one record instead of once for twenty, so the per-record figure is more likely to be under-stated than over-stated. Adapter gaps

02

Proposal only. knowledge/_jev.py was read and not touched. Not started. After the 25th, if ruled.

Seven things the adapter would gain to match the documented SDK.

The docstring's own “CANNOT do” list is honest and mostly correct. These are the gaps the documentation opens, in the order a batch job would hit them.

  1. Retries. The docstring calls backoff “a policy decision” that belongs to the caller, which is right — and the caller has nothing to hold it in. A RetryPolicy-shaped argument on ask(), defaulting to off so today's behaviour is unchanged, would let a 2,282-request batch job ask for the documented defaults: two retries, 0.5s doubling to 5.0s, 25% jitter, {408, 429, 500–599}, honouring both retry-after headers. At the declared 1,200 requests per minute, A will meet a 429.
  2. Usage capture in the receipt. Lane J3 read usage off the response and reported 4,023 input tokens; the receipt schema in the docstring lists timestamp, model, questions, answers, latency and request id, and not usage. Adding input_tokens and output_tokens makes every receipt self-pricing at the declared rate, and makes J5's derived token figures checkable against measured ones. Both fields are nullable and must be written as absent, never as zero.
  3. A request-size guard. Nothing in the adapter knows about 64k total or 32k for state plus the longest question. A batch that packs 240 candidate ids into a Choice will silently cross one of those, and the failure will arrive as a 422 with a field path rather than as a clear message. A cheap character-count check before the POST, refusing rather than truncating, would turn that into a caller's problem at build time.
  4. Structured instructions and criteria. Advanced: structure allows objects and arrays in instructions, in Choice option descriptions, in Score levels and in Noul criteria.true/false. Apollo's gate rules and draft principles are already structured; flattening them into a prose string before sending is a loss the adapter does not need to impose. The Score page's own worked example moved confidence from 0.35 to 0.96 purely by adding a relevant examples array to a level.
  5. Record the answering model, not the requested one. The docstring notes that jev-1.13.0 is “echoed, not sent”. Now that pinning is documented as available, the receipt should hold both the id requested and the id that answered, so a disputed answer can be reproduced against the same weights.
  6. A rate-aware batch runner — separate from the adapter. A helper that fires requests concurrently under a 1,200-per-minute and 250,000-token-per-second ceiling is what turns A's 35 minutes serial into roughly 2. It belongs beside _jev.py as its own instrument, not inside ask(), which should stay one POST.
  7. A questions-and-thresholds module. The agent skill page makes this its main review principle: put every question and every threshold constant in one file so a human can review the judgments without reading the plumbing. Apollo has the same problem in a sharper form, because the thing Dave rules on is the question. A knowledge/_jev_questions.py holding A's label set, B's three levels and C's three options, with nothing else in it, is what a ratification page would cite.

One thing the adapter should keep exactly as it is. The oracle rule. Nothing in fifty-nine pages of vendor documentation argues against it, and System One supplies the reason in a sentence: calibration is measured across groups of predictions and “does not guarantee that an individual answer is correct.” An instrument that cannot guarantee one answer must never be allowed to fail a build.
