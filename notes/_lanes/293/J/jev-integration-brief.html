The answer, first

Yes, cheaply, and not where you think.

Can we? Yes. I reached api.typesafe.ai from the Cowork sandbox and it answered with a typed authentication error, and pip install typesafe-sdk pulled 0.7.0 and imported clean — the only missing part is a key, which is early-access and Dave's to request at console.typesafe.ai/keys.

Should we? For a narrow class, yes: judgments Apollo makes many times over, where code can enumerate the options first and a number is more useful than a paragraph — retrieval ranking, ruling-trigger recall, citation checking. For the art-director's eye and for anything with a figure in it, no, and the vendor says so itself (jaggedness).

How? A thin knowledge/_jev.py adapter with a receipts log, called from inside gates that already exist — not an MCP server, because an MCP tool answers into a transcript and Apollo's judgments have to leave a file behind.

What the thing actually is

01

Released 15 September 2026 by TypeSafe AI, in limited early access. Stable at jev-1.13.0.

Jev is not a language model with a schema bolted on. It does not generate text at all: you send a state — a string, a JSON object or an array — together with a map of typed questions, and every question is evaluated against that state in one parallel pass, returning a typed value and a probability distribution (introduction). There are three primitives: Choice picks one option from a set you define and returns the winner, a probability per option and a confidence; Score rates the state against up to ten ordered levels and returns a probability-weighted value, the same per-level distribution and a confidence; Noul asks a yes/no statement and returns a bare probability from 0 to 1, with no confidence attached (API reference). The endpoint is a single POST https://api.typesafe.ai/v1/systemone with a bearer key. TypeSafe prices it at $0.042 per million input tokens with output tokens free, inside a 64k-token request budget of which the state plus the longest single question may use 32k, at 250,000 tokens per second and 1,200 requests per minute — limits the docs warn are "adjusting dynamically" and may change without notice (models). The founder's launch post claims 40–200× faster and, on their own workflow evals, up to 193.6× faster and 444.6× cheaper than frontier models; those numbers are TypeSafe's own, measured on workloads TypeSafe's capabilities team wrote, and the post says so plainly (launch post).

The shape that matters for Apollo is the last line of that paragraph. Jev's answer is a number you threshold on. It does not come with an argument you can disagree with, which is exactly why it suits a gate and does not suit a review.

Three ways in, ranked

All three are real. Only one leaves a receipt.

RANKED FIRST

A knowledge/_jev.py adapter with its own log

What it is. One module, house style: a help_gate docstring naming what it can and cannot see, a single place holding every question and every threshold, and an append-only notes/_JEV-LOG.jsonl recording the state hash, the question, the full distribution, the confidence, the model id the response reports, and the latency.

Prerequisites. An early-access key in the environment, and one ruling from Dave on whether a Jev number may ever appear in a gate's exit code.

Costs. A module to maintain and a network dependency inside scripts that are currently pure and offline.

Cannot do. Nothing for a session that has no key. It also adds 70–500 ms per call to gates that today run in milliseconds.

RANKED SECOND

REST or SDK called directly from inside a gate

What it is. The same calls, but scattered. The Python SDK installs and imports in the sandbox and exports Choice, Score, Noul, TypeSafeClient and AsyncTypeSafeClient; it reads TYPESAFE_API_KEY from the environment and defaults to jev-latest (quickstart).

Prerequisites. Just the key.

Costs. The thing Apollo has spent nine gates learning to avoid — a judgment with no join, questions and thresholds spread across files where no reviewer can find them. TypeSafe's own skill page warns of this and says to keep questions and thresholds in one file (agent skill).

Cannot do. Survive review. This is path one without the discipline, and it is listed only because it is the version that happens by accident.

RANKED THIRD

An MCP server loaded into Claude Code

What it is. jev-mcp exposes jev_classify, jev_score, jev_check, jev_ask and jev_models as MCP tools with full distributions and a confidence-derived act / review / abstain verdict (rahulrajaram/jev-mcp). It installs as a Claude Code plugin with /plugin marketplace add rahulrajaram/jev-mcp then /plugin install jev@jev-mcp, declaring the server inline in .claude-plugin/plugin.json. jev-review is the same idea narrowed to code quality: one tool, seventeen scored dimensions, a local Node process, key never leaving the machine (NiazMorshed2007/jev-review).

Prerequisites. A key, Node 20+, and — this is the blocker — a plugin installed into the Cowork session rather than the sandbox. Cowork loads plugins as bundles of MCP servers and skills through the app; the sandbox shell cannot register one into the running session, so this path is installed by Dave in the client, not by an agent in a lane.

Costs. Low to set up, high in the wrong currency: the answer lands in a transcript.

Cannot do. Leave a file behind. A tool result is visible to the agent that asked and to nobody else afterwards, which is the exact failure Apollo built the rulings store to stop.

ALSO AVAILABLE

TypeSafe's own agent skill

What it is. A drop-in skill teaching an agent the primitives and patterns — claude plugin marketplace add typesafe-ai/skills then claude plugin install typesafe@typesafe-ai, or npx skills add typesafe-ai/skills --skill typesafe-ai for other agents (agent skill).

Why it is not a path. It teaches; it does not call. It costs nothing and belongs alongside path one, so that whoever writes the questions is writing them against the vendor's own guidance rather than against this brief.

The raw skill is readable without installing anything, at raw.githubusercontent.com — reachable from the sandbox, measured today.

Three places it must not go, published so nobody re-derives them.

The stop line in knowledge/_checkin.py is arithmetic over real token counts, and Jev is explicitly not a calculator — the docs say to keep mathematical logic in code and warn that Score levels are "weak in numerical calibration". The spacing and gap conditions P5 to P8 are read from a live DOM in pixels; a probability there would be a downgrade. And scratch hygiene is a file-ownership fact, which needs a stat call, not a judgment.

What could go wrong

02

Each of these is a reason to measure before adopting, not a reason to stay away.

The access is early and the limits move

Jev is in limited early access with a waitlist; the launch post says TypeSafe is "bringing developers off the waitlist as quickly as we can". The models page carries an explicit warning that rate limits "can change without notice". Anything Apollo builds on this is building on a surface that is still moving.

The headline numbers are self-tested

The 193.6× and 444.6× figures come from workflow evals TypeSafe designed, using the average of GPT-6 Astra and Fable 5.1 as the reference answer. The post is candid that the workflows "were made by individuals on our model capabilities team, so some bias could exist". Apollo's own standing rule applies without modification: measured and declared are both published, and these are declared.

Nothing is reproducible from weights

Jev is proprietary and served only from TypeSafe's API. There is no local model, no weights, and no fine-tuning — the docs state the same weights serve every account and that Apollo's domain would be encoded in the state and the criteria, not in a trained artefact. An aliased model can also move underneath a pinned threshold, which is why the response reports the versioned id and why any Apollo use should log it and pin jev-1.13.0 rather than jev-latest.

Calibration is untested on design artefacts

Every calibration claim and every cookbook number is on support tickets, legal passages, SEC filings, patents and beer catalogues. Not one is on a rendered interface or a design ruling. Confidence describes how concentrated a distribution is; it is not a claim that the answer is right, and no number published anywhere says how Jev behaves on Apollo's material. That is the gap the first experiment exists to close.

Design artefacts are exactly the hard input

The jaggedness page names large state full of irrelevant detail as a failure mode, and a .REVIEW.html is 39,137 characters of which the judgment needs perhaps two hundred. It also warns that the model reads hex and RGB worse than colour names. Both cut straight through Apollo's material, and both are handled the same way: build the state in code from the fields the question needs, never from the file you happen to have.

And the governance line does not move

Every use above is advisory. Not one writes to _rulings.json, changes a governs list, flips a gate's exit code, or grades a page. Jev returns a number; a number is evidence. Dave rules.

Typed output guarantees the interface, not the truth. jev-mcp, "When not to reach for this"

The first experiment

03

Small, measurable, reversible. One scratch script, no writes to the tree, cost in pennies.

Re-rank memento search against a retrieval failure we already documented.

Apollo has a named, dated, twice-repeated retrieval defect sitting in its own records. The trigger index README says it outright: ruling ds-021 settled the token unit at session #54; the ruling sits in ten places; #80 re-derived it from scratch twenty-six sessions later and nearly filed it as a discovery, and #81 started down the same path. The README's diagnosis is the sentence to test — searching the archive for the topic returns this week's banners, because retrieval ranks recency above rulings.

So the experiment has a right answer that predates the experiment. Take a small fixture of queries whose correct target ruling is already known. Run the existing lexical search from _search_core.score_record and record where the right ruling lands. Then send the same query plus each shortlisted candidate to Jev as one batched Score request, re-rank inside the bucket without touching bucket membership or caps, and record where the right ruling lands now. Publish both numbers, the per-query distributions, the latency, and the token cost.

It is reversible because it writes only to notes/_lanes/293/J/ — no gate changes, no adapter yet, nothing importable by the tree. It is measurable because rank-of-correct-answer is an integer, before and after. It is small because one batched call carries every candidate for a query, and at $0.042 per million input tokens the whole run costs less than a cent.

The one thing to be honest about in advance

If I write the fixture queries myself from the rulings' own text, the test is circular — I would be writing queries that the ruling's own vocabulary already answers, and lexical search would do suspiciously well. The fixture has to come from Dave, or from real session transcripts where someone searched and missed. The #80 and #81 misses are two such queries with a known right answer, and two is a start but is not a result. Ten real queries would be.

Prerequisite before any of this runs: an early-access key at console.typesafe.ai/keys. The sandbox network reaches the API, PyPI, npm and raw.githubusercontent today — all four measured this session, with commands and output in the filed subreport. The key is the only thing missing.
