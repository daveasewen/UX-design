## The four defects, measured at HEAD before any edit

### 1. Alert — the dismiss × REMOVED NOTHING (severe, user-visible, shipped)

Driven at HEAD: **7 alerts in, 7 alerts out.** The button holding focus was still in the DOM
afterwards. True in light and dark, and at both `prefers-reduced-motion` settings.

Root-causing it took three passes, and **each wrong answer was caught by its own mutation arm**
— which is the argument for arms in one line:

1. *First reading:* `.alert.removing{ max-height:0 !important }` blocked the transition
   (transitionrun fired for opacity/margin/padding and never for max-height). Repaired by
   driving the collapse inline→inline. **The arm restoring the `!important` stayed GREEN** — a
   fallback timer added by the same repair was covering it.
2. *Second reading:* the inline zero is the load-bearing half. **Also green** — restoring the
   `!important` does not re-break it, because the after-change inline value agrees with the
   important one.
3. *Actual root cause,* found only because the arms refused to bite:

```js
n.addEventListener('transitionend', ev=>{ if(ev.propertyName==='max-height') n.remove(); }, {once:true});
```

The element transitions **five** properties. `opacity` finishes at 200ms, `max-height` at
300ms. The 200ms opacity event reached the one-shot listener first, failed the `propertyName`
guard, did nothing — and `{once:true}` had **already unsubscribed it**. The max-height event
100ms later had nothing listening, so `n.remove()` never ran. **`{once:true}` counts
deliveries, not matches:** a guarded one-shot handler on a multi-property transition is a bug
by construction, and the guard is what hides it.

Repaired: a named handler that unsubscribes only on its own property, plus a 600ms fallback so
the control can never be orphaned by an event that does not arrive. Both the `!important` and
the inline drive were left in their cleaned-up state.

⚠ **This class is worth a grep across the library** — see residual R1.

### 2. Alert + Toast — dismissal stranded focus on BODY (WCAG 2.4.3)

Measured on Toast at HEAD: focus the ×, activate it, `document.activeElement` → `BODY`. A
keyboard user is thrown to the top of the document. Same class the Drawer had repaired at #211
lane R3; the two sibling components in the same family never got it.

Repaired: focus moves to the next remaining dismiss in the group; when the last one goes,
Alert lands on `#awrap` (`tabindex="-1"`) and Toast returns to the control that spawned the
toast (captured at spawn time — by dismissal the × is about to be destroyed).

### 3. Popover — the surface did not follow its trigger (severe, user-visible, shipped)

`.pop` is `position:fixed` and was placed **once**, on open, from the trigger's viewport rect.
Measured, same popover, same session:

| | gap to trigger on open | after a 300px scroll |
|---|---|---|
| HEAD | 12px | **108px** |
| repaired | 12px | 12px |

At HEAD the popover stays pinned to the viewport while its trigger scrolls out from under it —
tail pointing at unrelated content, `aria-expanded` still `true`. It is easy to miss because
scrolling *back* restores the 12px exactly.

Repaired: re-place on `scroll` (capture, passive) and `resize` while open, rAF-debounced, with
the listeners **removed on close** — never a page-lifetime listener for a transient surface.

### 4. Skeleton loader — the one piece of real text was the untyped one

The resolved copy arrived as `<p style="margin:0">`: no composite, a hardcoded inline style,
and — the part that matters — **the file pulled no `canon/type.css` at all**. Writing
`.t-ed-body` into it would have been inert decoration: present in the markup, absent from the
rendering. Measured before: `16px / normal` in a fallback face. After: **`16px / 24px` in
Univers Next**.

Repaired: the stylesheet link added, `.t-ed-body` on the resolved copy, margin moved off the
`style=""` attribute. The bones stay untyped — correct, they are `aria-hidden` decoration.

## Decisions for Dave — every judgment call named, NONE decided

1. **Was repairing the right lane output at all?** The brief said *build five*; five already
   existed and four were broken. This lane audited and repaired instead of minting duplicates.
   That is a scope substitution, and it is Dave's to confirm — the alternative reading is that
   lane β should have returned the register finding and stopped, banking nothing.
2. **Toast is very probably not announced at all, and fixing it is an architecture call.**
   `#toastRegion` carries **no `aria-live` and no `role`**. Each spawned toast is created
   detached, given `role="status"`, filled with its content, and only then appended — a live
   region that arrives already populated is the classic shape that screen readers do not
   announce. The file's own header rules "All toasts are `role="status"` (polite)", so moving
   the live region to the container contradicts documented canon, and a belt-and-braces
   both-levels fix risks double announcement. **NOT ENACTED.** It needs a real screen reader,
   which cannot be driven headlessly here. Recommendation if Dave wants one: region-level
   `role="status"` present at load, per-toast roles dropped (the APG shape).
3. **Focus destination when the last alert is dismissed.** Chosen: the group container
   `#awrap`, given `tabindex="-1"`. The alternatives are the page heading or the last
   preceding interactive element; this is a feel call on a keyboard journey.
4. **Toast focus destination.** Chosen: next live toast, else the spawning control. The
   competing reading is "always return to the spawning control".
5. **Static specimen dismiss buttons still do nothing.** The `.x` on Toast's four anatomy
   specimens and Drawer's static specimen have no handler — they are review-pane specimens, the
   established idiom (Drawer's header declares it), and W3 judged the same class as specimens
   rather than phantom controls. Left alone deliberately. If s218-D4 is meant to reach specimen
   rows too, that is a separate sweep and a different ruling.
6. **`<a href="#">` inside Alert and Popover** goes nowhere. Same demo-affordance class W3
   judged and left. Named, not touched.
7. **Popover tracking on scroll is a design behaviour, not only a bug fix.** It now follows the
   trigger and re-flips above/below as room allows. Some systems instead *close* the popover on
   scroll. Both are defensible; the tracking reading was built because it preserves the user's
   surface. Dave's eye.
