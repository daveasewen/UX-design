01

What this is

A claim table is the list a lane leaves behind: each row makes one claim about the work and names the evidence, such as a command, a file or a count. A checker in CI re-reads every row and re-runs some of the commands, so that a claim nobody can check stands out.

The conductor said nine rows "are stale against today's files", meaning the tree moved on after they were written. I tested that against the tree at each table's own commit. It holds for two rows. Of the rest, three are misread by the checker itself, three never named anything a machine could check, and one fails only in CI.

Two things are true of all nine. None of them is a false claim: every row that can be checked was true on the day it was written. And none of them turns CI red. The checker's CI step is allowed to fail, and it has been failing on the same six rows since the day it was wired on 19 August.

04

Testing lane F's premise

Can (a) be built?

  • Yes

    Can the checker learn each table's commit?

    Yes, and it can do it for each row rather than each file. One table had rows added in two separate commits, and git can name the commit behind every line. That works in CI too.

  • Yes

    Are the old files reachable through git?

    Yes. CI's gates job fetches the full history (the fetch-depth: 0 checkout), so any file can be looked up as it was at any commit. I did exactly that for this page.

  • Heavier

    Can it re-run old commands?

    Only by checking out a temporary old copy of the repo for each commit. There are five such commits here. It runs old code, and it still hits "could not ask" in CI wherever files are missing.

  • No

    After (a), could the CI step become blocking?

    No. The checker as it stood on 19 August already flags the same six rows, so (a) cannot clear them. The CI-only row would still say "could not ask". The step would stay red.

  • Not yet

    After (b), could it become blocking?

    Technically yes: all nine clear. But the session 208 wiring table has twelve more rows that expect an exact count or exact text, and they will age the same way. If the step were blocking, an unrelated edit to the build or the CI file could turn CI red. Make it blocking only once (a) is built as well.
