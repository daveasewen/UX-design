Research · design-system ontologies · v2

Ubuntu’s makers publish a design-system ontology. Map to it; don’t swap to it

Canonical, who make Ubuntu, publish an OWL design-system ontology checked by SHACL shapes, and Adobe publishes a relationship schema for Spectrum. Both cover how components are built and styled. Neither covers what Apollo governs. So keep Apollo’s words, map the build half to theirs, and borrow their discipline: every kind of edge defined once, with its ends, its opposite and a check.

Asked by Dave, Tue 29 Sep 2026, 08:43 BST: “I also want some research around design system ontologies, this might help our edge definitions.”

Apollo measured on the repo at 07:53 UTC the same morning. Outside sources read the same day.

Read-only. Nothing in the tree was changed.

v2 answers Dave’s 08:48 challenge (“there are many defined online ubuntu comes to mind too”). v1 is kept unchanged beside it.

The answer

v1 said nobody had published one. That was wrong: Canonical has, and so has Adobe in part. Neither covers Apollo’s governance, so map to them rather than adopt them. Their lesson is the same as the standards’: define each kind of edge once, and have a check read that definition.

Canonical’s Design System Ontology (catalogue below) declares, per relation, its ends, its opposite and whether only one is allowed, and it checks its anatomy with SHACL shapes. OWL, SKOS, SHACL, Dublin Core, Backstage and Wikidata all do the same thing. They write down, once per relation, what may sit at each end, what its opposite is, whether it points both ways, whether it may loop or chain, and how many are allowed. Then a check reads those definitions and reports the edges that break them.

Apollo already has the hard parts: a closed word list, typed ends by prefix, “null, never guessed”, a reading map with force (must, should, is), and polarity nodes that are a textbook way to put a reason on a relation. What it lacks is the per-type definition. It is spread across four files, and the knowledge-graph gate checks that a target exists, not that it is the right kind.

The recommendation is still nine items; items 4, 7 and 9 change in v2. The first is one edge register. Most of the others are fields in it, and the last two are small additions to the vocabulary. Its first run would name some seventy real problems in today’s graph (measured below).

New in v2 · the catalogue of published ontologies

You were right: Ubuntu’s makers have published one

Your sentence, 08:48 BST: “there are many defined online ubuntu comes to mind too”. v1 said nobody had published a design-system ontology worth adopting. That was wrong. I searched by name, not by topic, and read the files themselves. Everything below was read on 29 September 2026.

Canonical’s Design System Ontology (the “ds:” vocabulary)

Canonical publish Ubuntu. Their design team announced the ontology on Ubuntu Discourse on 22 October 2025 (“Canonical’s new design system: towards a design system ontology”, Adrian Villa). It succeeds the Vanilla CSS framework, which has run since 2015. The ontology is now published under LGPL-3.0 in canonical/pragma-core. That repository was created on 28 September 2026 from the now-archived canonical/design-system, anatomy-dsl and design-tokens repositories.

The ontology is written in OWL, as Turtle files, and labelled “Design System Ontology”, version 3.0.0, under the namespace ds.canonical.com. Each relation declares its ends (domain and range), and the key ones declare their opposite and whether only one is allowed (“functional”). It has three companions. A token ontology (“dt:”) sits over the design-tokens standard. An anatomy grammar describes a component’s parts, and its SHACL shapes check them. A code-standards vocabulary describes coding rules. The data behind it covers 139 components, 95 subcomponents, 63 patterns and 16 layouts, as counted from the file tree. It is queried with SPARQL, a CLI and an MCP server.

Its relations, read from the ontology files
  • inheritsFrom ↔ specializedBy, declared opposites: “a Data tooltip inherits from Tooltip”
  • variantOf ↔ hasVariant, declared opposites
  • hasSubcomponent ↔ parentComponent, declared opposites. A subcomponent is its own kind, with a flag for “can stand alone”
  • hasModifierFamily; hasModifier ↔ modifierFamily (only one allowed): the variant axes such as importance and criticality
  • hasProperty, tier (one only), implementsBlock (code → block, one only), library
  • hasTokenBinding → a binding record holding the symbol, the path through the anatomy tree and a fallback rank: an edge made into a node
  • Tokens: aliasOf (one only), refersTo, tokenType; coordinate, resolvesBy, otherwise; contains (declared transitive)
  • Anatomy: hasEdge → Edge → hasRelation (with cardinality and slot name) → edgeTarget. Every parent–child link is a node that carries its own count
  • changeLog entries (timestamp, owner, change type, link); decisionLog is a plain text field
Read against Apollo
  • It covers the build half. By my reading, about 11 of Apollo’s 65 edge types have a counterpart: family, partial, hasPart, containedBy, composedOf, activeVariantOf, renderedBy, bindsToken, setIn, acceptsCapability, capturedFrom.
  • It has nothing for the governance half: no rules, rulings, principles, WCAG criteria, obeys, rests-on, must-not-sit-with, yields-to or groups-with. Decisions are a text log, not a graph. No edge carries a reason.
  • What it has that Apollo lacks:
    • declared opposite pairs
    • “only one” declared per relation
    • SHACL shapes that check the anatomy
    • a subcomponent kind
    • token-to-token aliases
    • themes and modes as coordinates with a fallback
    • a binding that records which part of the anatomy uses a token
  • It is a young, moving target: version 3.0.0, and a repository one day old.

Does it change the nine?

Map, don’t adopt. Keep Apollo’s words, and point the outside column at Canonical and Spectrum first.

No published vocabulary covers what Apollo governs: rules, rulings, principles, criteria and the reasons between them. Canonical’s covers about a sixth of Apollo’s edge types, and it is one day into a new repository. Adopting it outright would drop five-sixths of the graph’s meaning into “relates to”. It does prove items 1 to 3 in practice: an OWL file where every relation states its ends, opposite and count, checked by SHACL shapes. Items 4, 7 and 9 change in the light of it, and they are marked below.

01

What Apollo has today

Good names, typed ends, thin definitions

Every number here was measured on Dave’s repo by running the explorer’s own extract (knowledge/_build_kg_explorer.py, extract() plus extract_extra()) at 2026-09-29 07:53 UTC. Other lanes were writing to the tree that morning, so counts can move by a few.

Where an edge is defined today: four places, none complete

  • knowledge/components/meta.schema.json. The shared edge shape is {ref, $note}, and a ref may point at any of eight kinds, whatever the edge type. Only obeys has its own shape, which the schema split out on purpose “because widening the shared ref pattern would let containedBy point at a rule”.
  • knowledge/_kg_verbs.json is the twelve-verb reading map: which verb reads which storage type, its force, its direction sentence and a count. It is a reading, not a definition of the ends.
  • knowledge/_build_kg_explorer.py gives each type its family, and so whether it is drawn.
  • knowledge/_validate_kg.py checks that every ref matches the id grammar and resolves. A search for domain, range, inverse, symmetric, self-loop or cycle finds nothing in it.

What is already strong

The vocabulary is closed. A new type is a ruling, not a drift. A target that cannot be found is carried as a declared null with its prose, never guessed. obeys requires a reason of at least 40 characters, which is exactly what SHACL’s minLength and Wikidata’s “required qualifier” do. The verbs’ force (must, should, is) is the same three steps as SHACL’s severity (violation, warning, info). And knowledge/brain/polarities.json makes each trade-off a node with typed parties. That is pattern 1 of the W3C note on n-ary relations, the standard way to hang facts off a relation.

Where the definitions are thin — measured

  1. One name, two kinds of target

    governedBy runs from 28 components to a ruling, and from 12 logo lockups to a rule. Those are two different relations under one word. A per-type check on the ends would refuse one of them.

    Measured: ends of governedBy = component→ruling 28, logo→rule 12. The 12 logo lines were hand-written into _logo_nodes.json (builder version note 1.26).

  2. Opposites stored twice and out of step

    A ruling says it governs a component, and the component says it is governedBy the ruling. Both directions are written by hand, in different files. Only 18 of the 28 component-side lines have a matching ruling-side line. containedBy (88) and hasPart (14 between components) are also opposites, and none of the 14 is mirrored.

    Measured. Apollo already has the right rule, for one type: yieldsTo’s schema note says “the inverse is read by traversing the graph, never by writing a second edge into a second meta”.

  3. Edges that point at themselves

    22 edges start and end on the same component. There are 9 family lines, where the note means “this meta covers a family”. There are 7 mustNotNeighbour lines, where the note means “only one on screen at a time”. There are 4 hasPart lines naming sub-parts that are not components, and 2 groupsWith lines. Each one is a different fact squeezed into an edge.

    Measured: self-loops by type, family 9 · mustNotNeighbour 7 · hasPart 4 · groupsWith 2.

  4. A containment loop

    Carousel is contained by cards, and cards is contained by carousel. Containment should never loop.

    Measured: the only two-step cycle in containedBy.

  5. The reason lives on two types, under four names

    Only obeys (168 of 168) and restsOn (75 of 75) carry a reason on the edge. The reason is called $why in the metas and why in the graph. The ruling-to-ruling edges hold evidence in storage. Everything else has only a free $note.

    Measured on the graph. evidence as read from knowledge/_ruling_edges.json.

  6. “Authored” means “drawn solid”, not “written by hand”

    1,648 edges carry no maker flag at all, including all 168 hand-written obeys lines. Meanwhile the 835 bindsToken lines, which a script lands from the metas’ token block, are flagged authored: true.

    Measured: authored flag by type. Provenance of bindsToken from its own note in _kg_verbs.json.

  7. Repeated edges

    29 pairs appear more than once under the same type: 14 under governs, 11 under under and 4 under hasPart, with 60 extra copies in all.

    Measured, one run earlier the same morning.

  8. Two vocabularies for ruling-to-ruling links

    The older _decision-graph.json uses nine types: refines, relates, supersedes, verified-by, bounds, conflicts-with, subsumes, diverges-from and enacted-by. _ruling_edges.json uses ten, spelled differently (enacts against enacted-by). Nothing maps one onto the other.

    Measured: 172 edges in the decision graph; 48 ruling-to-ruling lines in the live graph.

  9. One type read by no verb

    inFamily (145 lines, principle → research family) is in neither the twelve verbs nor the unread list. The verbs file names this gap itself.

    _kg_verbs.json, $measured.$drift; confirmed by comparing the verbs map with the live types.

03

What the outside world does

The general standards, one idea each

These are the general standards the design-system vocabularies above are built on or echo. Canonical’s is written in OWL and checked with SHACL; Spectrum’s is JSON Schema plus graph rules. The ideas worth borrowing are here, stated once each.

OWL 2 · relations carry their own character

A property can be declared the inverse of another, symmetric, asymmetric, transitive, functional (at most one), or irreflexive (never itself). It can also have a domain and a range. Caution: in OWL a domain or range “is not a constraint” but lets a reasoner infer. It fills in facts rather than refusing bad ones.

W3C OWL 2 Primer, Rec. 11 Dec 2012
SHACL · checking is a separate job

Shapes state what a node’s edges must look like: the class at the far end, minimum and maximum count, a text pattern, a minimum length, disjoint properties. Each break carries a severity: violation, warning or info. This is the closed-world check Apollo wants, and its three severities match Apollo’s must, should and is.

W3C SHACL, Rec. 20 Jul 2017
SKOS · a small, plain word set

broader and narrower are opposites. broader is not transitive, but it sits under a transitive broaderTransitive, so you keep the direct link and can still ask for the whole chain. related points both ways and may not be used where a hierarchy exists. It also has mapping words (exactMatch, closeMatch, relatedMatch) for saying “our word, their word”.

W3C SKOS Reference, Rec. 18 Aug 2009
Dublin Core · schema.org · plain opposite pairs

hasPart and isPartOf, replaces and isReplacedBy, requires and isRequiredBy, references and isReferencedBy, conformsTo, source. Schema.org declares its ends softly (“domainIncludes”) and names each property’s opposite.

DCMI Metadata Terms, 2020-01-20 · schema.org/hasPart
Backstage · store one side, emit both

Every relation comes as a declared pair (ownedBy and ownerOf, dependsOn and dependencyOf, partOf and hasPart, providesApi and apiProvidedBy, consumesApi and apiConsumedBy). Only the owner’s field is written. The catalogue emits the opposite automatically. This is Apollo’s own yieldsTo rule, made general.

Backstage docs, well-known relations
Design tokens · aliases that cannot loop

The 2025.10 stable format lets tokens point at tokens ({group.token} or $ref). Tools follow the chain, and circular references “MUST” be detected and reported. A token that aliases another takes the resolved type of its target. Groups can $extends, and tokens can carry $deprecated.

W3C Design Tokens CG, stable 28 Oct 2025; draft read 29 Sep 2026
Figma · aliases and scopes

A variable may reference another variable “of the same type”. Scopes limit which properties a variable may be applied to. That is a range, stated by the designer and enforced by the tool.

Figma Help Centre, variables and collections
WAI-ARIA 1.2 · containment with rules

Roles form a superclass and subclass tree. Some roles have a required context (a listitem must sit in a list) and some have required owned elements (a listbox must own an option or group). Relations like aria-controls and aria-owns are named edges between elements.

W3C WAI-ARIA 1.2, Rec. 6 Jun 2023
UI ontologies · composition models

Paulheim and Probst built a formal UI ontology on DOLCE, with relations such as realizes (a design-time thing to its runtime form), part and adjacent to. Atomic Design is “a mental model”, not a word list. Pattern languages link related patterns. Design-system-as-graph blog posts (McCoy 2021, Singh 2024) publish no schema; Canonical’s ontology does.

SEMAIS 2011 · Frost 2016 · van Welie & van der Veer 2003 · PLML 2003
Design rationale · how decisions relate

Kruchten’s ontology of design decisions has these relations: constrains (if A is dropped, B falls), forbids, enables, subsumes, conflicts with, overrides (a local exception), comprises, is bound to, is an alternative to, and traces to an artefact. Decisions move through states from idea to obsolesced. IBIS links arguments that support or object. ADRs mark a decision superseded, with a pointer to its replacement.

Kruchten 2004 · Kunz & Rittel 1970 · MacLean et al. 1991 · Nygard 2011
Edges that carry a reason

Property graphs (the GQL standard, 2024) let an edge hold its own fields. RDF 1.2 adds triple terms and reifiers, so a statement can be annotated, even with who claimed it and why, without being asserted. Wikidata hangs qualifiers and references on each claim. Its constraints are “hints, not firm restrictions”: they are reported, not enforced, like Apollo’s advisory gates. PROV-O names who made a thing, how, and from what.

ISO/IEC 39075:2024 · RDF 1.2 CR 7 Apr 2026 · Wikidata · PROV-O Rec. 30 Apr 2013
What this adds up to

Each kind of edge gets one definition with the same few facts: its ends, its opposite, its shape, how many, whether it needs a reason, and who made it. A separate check reads that definition and reports by severity. Apollo has none of these definitions in one place. Canonical does exactly this in OWL and SHACL. Apollo already stores edges the modern way, as edges with fields, so it does not need to move to RDF to get the benefit.

06

To rule on

Nine items. Take it, change it or leave it

They build on each other. Item 1 is the foundation, items 2 to 6 are fields in it, item 7 is a column in it, and items 8 and 9 change the vocabulary. Your answers stay in this browser. The button at the foot copies them as plain text.

  1. Write one edge register

    Define every edge type once, in one file, with one row per type: plain word, verb, starting kind, ending kind, opposite, shape, how many, reason rule, maker, and nearest outside term. The meta schema, the verbs map, the explorer and the new check all read it, so none of them holds its own partial copy.

    v2: Canonical’s ontology.ttl is exactly such a register, for its own properties. Why: OWL, SKOS, Backstage and Wikidata all keep these facts on the relation. Today Apollo spreads them over four files, which is how inFamily slipped through with no verb. The register would have 65 rows today (measured). The file name, perhaps knowledge/_edge_register.json, is yours to choose.

  2. Check every edge’s two ends against its row

    Each type names the kinds it may start from and end at. An edge that starts or ends on the wrong kind is reported. Take SHACL’s idea (a closed-world check that refuses) rather than OWL’s (a range that quietly infers). The first case it would catch is the 12 logo lines filed as governedBy that end on a rule. I recommend moving them to obeys, which is what “a logo obeys a rule” means, and keeping governedBy for rulings only.

    v2: Canonical checks its anatomy with SHACL shapes; Spectrum checks shape first, then numbered graph rules. Why: the schema’s own note says one shared ref pattern would “let containedBy point at a rule”. Today only obeys is protected from that.

  3. Store one direction and read the other

    The register names each type’s opposite and says which side is stored. The opposite is read by walking the graph backwards, never written as a second edge. This is Apollo’s own yieldsTo rule applied to every type. Stored side: governs (on the ruling) over governedBy, and containedBy over hasPart. Before switching, run a one-off check of where the two sides disagree today: 10 of 28 governedBy lines have no matching governs.

    v2: Canonical declares four opposite pairs (inheritsFrom/specializedBy, variantOf/hasVariant, hasSubcomponent/parentComponent, hasModifier/modifierFamily). Why: Backstage and Dublin Core both declare pairs and store one side. Two hand-written sides always drift, and here they have.

  4. Say each type’s shape, and move the 22 self-lines to the fields they mean Changed in v2

    For each type, record four things. May it point at itself? May it loop? Does it point both ways (groupsWith, family, tensionWith)? Does it chain (containedBy, under, supersedes)? Then send each self-line to the fact it really states:

    • The 7 “only one on screen at a time” lines become a count on the component, such as at most one per view.
    • The 9 “this meta covers a family” lines become a field.
    • The 4 part-names become a subcomponent kind, as in Canonical’s ontology, where a subcomponent carries a flag for “can stand alone”. Changed in v2
    • The carousel and cards containment loop goes to your eye.

    Why: OWL names these characteristics (irreflexive, symmetric, transitive), and SKOS keeps a direct link while offering the whole chain as a separate word.

  5. One reason field, required by type

    Use one name for the reason everywhere: why. The register says, per type, whether it is required. Require it on every hand-made judgement: obeys and restsOn as now, plus mustNotNeighbour, yieldsTo, groupsWith, composedOf, delegatesTo, drivesConsumer and governedBy. The ruling-to-ruling types already carry evidence that serves. Do not require it on generated structure such as bindsToken, inGroup or usedInContext. Keep the obeys floor of 40 characters.

    Why: only 2 of 65 types carry a reason today, under four different names. A required reason is Wikidata’s “required qualifier” and SHACL’s minimum length.

  6. One maker field on every edge

    Every edge says who made it. There are three values: by hand (and whose), generated (and by which script), or ratified (and by which ruling). This replaces the authored flag, which today means “drawn solid”.

    Why: 1,648 edges carry no maker flag, including every hand-written obeys, while 835 generated bindsToken lines are marked authored. PROV-O has names for all three makers (attributed to, generated by, derived from).

  7. Keep Apollo’s words and write the outside term beside them Changed in v2

    Do not adopt Canonical’s or anyone’s vocabulary outright, and do not move to RDF. Add one column to the register for the nearest outside term, graded exact, close or loose. Point it first at a design-system vocabulary (Canonical’s ds: and dt:, or Spectrum’s) where one covers the type, and at SKOS, Dublin Core or PROV otherwise. Add each component’s Open UI name, the shared cross-system name. Apollo’s storage already works the modern way, as edges with fields, which the GQL standard and RDF 1.2 both now support.

    Why: no published vocabulary covers the governance half. Canonical’s covers about 11 of 65 types, is version 3.0.0, and moved repositories yesterday, so a mapping survives its changes where an adoption would not. You also prefer plain Anglo-Saxon words. The mapping costs one column and lets research, exports and newcomers line Apollo up against the standards.

  8. Fold the two ruling-to-ruling vocabularies into one

    Map the nine types of the older decision graph onto the ten in the ruling-edges file, or retire them. Where no match exists, bring the older type forward as a proposal. The one Apollo lacks is conflicts-with (8 older lines use it; Kruchten names it too). A second one is worth considering later: “depends on”, meaning that if this ruling is retired, the other falls with it (Kruchten’s constrains).

    Why: two spellings of the same idea (enacted-by and enacts) cannot both stay closed and still be read the same way.

  9. Five edges the outside world has and Apollo lacks Changed in v2

    Each is a separate yes or no. You can take this item whole or say which letters you want.

    • a) Token → token alias, with a loop check. Canonical has it as dt:aliasOf, with only one allowed. The design-token standard says circular references must be detected, and Apollo’s token tiers imply alias chains it does not draw.
    • b) Provides capability, the other half of acceptsCapability. The verbs file notes that “no providesCapability is minted”, and Backstage always pairs provides with consumes.
    • c) A theme node kind, so “default for a theme” has something to point at. v2 leans to a node: Canonical models themes and modes as coordinates with a fallback, and Tokens Studio as theme groups and options. Today both defaults are declared nulls.
    • d) Component → ARIA role. ARIA’s own required-context and required-owned rules could then be checked against containedBy and hasPart. Neither Canonical nor Spectrum has this.
    • e) Replaced-by on components and tokens, with the version it happened in. Spectrum carries introduced, deprecatedIn, replacedBy and plannedRemoval on every entity, and the design-token format has $deprecated. Apollo has replacement only between rulings.

    Why: each one closes a gap that a named standard or published design-system vocabulary already covers. None of them is invented here.

07

The check

What the edge check would do, in Apollo’s gate style

A sketch, not code to run. It follows the house pattern: stdlib only, read-only, degrades loudly, advisory first, names every failure.

for edge in graph.edges:
    row = REGISTER[edge.type]          # unknown type → refuse
    start, end = kind(edge.s), kind(edge.t)
    if start not in row.from:          report(row.force, "wrong start")
    if edge.t is None:
        if not row.null_ok or not edge.note:  report("null without its prose")
    elif end not in row.to:            report(row.force, "wrong end")
    if edge.s == edge.t and not row.self_ok:  report("points at itself")
    if row.reason == "required" and len(edge.why or "") < 40:
                                       report("no reason")
    if row.stored == "opposite":       report("opposite written as a second edge")
    if edge.maker not in ("hand", "generated", "ratified"):
                                       report("no maker")

per type:  no_loops → look for cycles · at_most → count per start
           both_ways → one stored copy only · no repeats of the same pair

force from the verb: must → refuse · should → warn · is → note

What its first run would print, from today’s measurement

  • 12 wrong ends: the governedBy lines that end on a rule
  • 22 points-at-itself: family 9, mustNotNeighbour 7, hasPart 4, groupsWith 2
  • 1 containment loop: carousel and cards
  • 29 repeated pairs: governs 14, under 11, hasPart 4
  • 10 governedBy lines with no matching governs (the one-off agreement check in item 3)
  • 1 type with no verb: inFamily
  • Reason and maker: every edge of the types item 5 names, until those fields are filled
