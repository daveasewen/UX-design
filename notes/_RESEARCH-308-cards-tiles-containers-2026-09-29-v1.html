Research · cards, tiles and containers

No standard names exist. Define each type by its job and what it accepts, and the nesting follows

“Card” is fairly settled: content about one thing, usually one of a set. “Tile” is not: it means four different things in four systems. The clearest published line is Canonical’s. A card is one of a series of like records; a tile is a surfaced box for one-off content, the thing a bento is made of.

Asked by Dave, Tue 29 Sep 2026, 17:07 BST: “i think we have to create a definition for cards and tiles … is the question about the hierarchy of containers or clear definitions for different types … is there a standard nomenclature for this?”

Apollo read on the repo that evening; outside sources read the same day. Read-only; nothing in the tree was changed.

The answer

It is both questions, but definitions come first. Once each type says what its job is and what it accepts, the hierarchy is no longer a list to maintain. It is what the rules allow.

There is no standard nomenclature. In Open UI’s survey data, 12 of 27 design systems have a component called Card, only 2 have a Tile, and Carbon has a Tile but says outright that it has no card. Atlassian’s Tile is a small square that holds an emoji or image. Material’s old grid-list tile is a cell holding a picture. Canonical’s Tile is a surfaced container for unlike content in dashboards and bento layouts.

The conductor’s short answer mostly holds, with one correction. The published line that fits Apollo best is not “a card is about one subject, a tile is a grid cell”. It is Canonical’s: a card is one of a series of records that share a structure, and a tile holds content that does not repeat. Canonical’s own example is a single “Total users” number: that belongs in a tile, not a card. Apollo already agrees on the card half. Its own ruling says a record is a card when its container draws a border around each record.

Apollo’s words blur in three places. “Tile” has four meanings in the tree. “Card” names a container, a metric, a record summary and a piece of plastic. The stat card and the KPI tile are the same object, told apart only by whether a trend line is present. Five calls at the foot fix the words and move the check onto “accepts”.

How nesting is governed elsewhere

By type through “accepts”, never by listing pairs

  • HTML gives every element a content model, drawn from shared categories (flow, phrasing, interactive …), plus the contexts it may be used in. One rule covers every pair: an a element may have no interactive content inside it.
  • WAI-ARIA gives roles a required context (a list item sits in a list) and required owned elements (a listbox owns options).
  • Canonical writes each part as an edge carrying a count (media 0..1, content exactly 1) and a slot name, and checks it with SHACL shapes.
  • Figma components have slots and instance swaps with a curated list of preferred components.
  • Apollo already has the same device. A slot declares accepts by tier and capability; the Cards content slot accepts atoms and molecules offering card-body content.

  1. “Tile” means four things

    It names the KPI tile component. It describes the stat card: its purpose reads “the dashboard tile for one headline number”, and roles.json says a headline metric is “the tile a dashboard’s top row is made of”. It names a bento cell: “its tiles are themselves bentos”, and “tiles stay square”. And it names the app tile in the logo guidelines.

    stat-card, kpi-tile and template-dashboard-bento metas · roles.json headline-metric · guidelines/logos.md

  2. “Card” means four things

    Cards is a container family: “a bordered surface” that groups content, and a provider of the arrangement role. Stat card is a metric. Account card is a summary of one record. Payment card visual is the piece of plastic. The Cards meta also lists Carousel among the places it lives.

    cards, stat-card, account-card and payment-card-visual metas

  3. The stat card and the KPI tile are one object

    “A KPI tile with no series is a Stat card.” Both provide headline-metric. So one thing is called a card or a tile depending on whether a sparkline is present, which is the #202 “switch” lesson again.

    kpi-tile meta, citing the ruling that set this; roles.json headline-metric

  4. “Panel” is a role name and a box word

    The chart-panel role (“a charted reading in a panel”), “stat panels” as a place card headers live, and splitter panes all use it. Outside Apollo, “panel” almost always means a region at the side of the screen.

    roles.json chart-panel · card-header-lockup meta · splitter meta

  5. Card and carousel are both “arrangement”; containment is by pair

    roles.json lists Cards (“a bordered surface per item”) and Carousel (“one of a set at a time”) as providers of arrangement, beside the layout utilities. In the edge register, containedBy runs from a component or subcomponent to a component, and nothing checks what a parent accepts. Tonight’s ruling kept one pair, “a carousel holds cards”, explicitly until these definitions land.

    roles.json arrangement · knowledge/_edge_register.json containedBy · the ruling that says a carousel holds cards (17:07 BST)

  6. What already agrees with the outside

    Apollo’s ruling on lists says a record is a card when its container draws a border around each record, which is Canonical’s card. Bentos nest, and the bento’s radius sits on its container while its tiles stay square: the tile is the bento’s cell. This morning’s subcomponent ruling gives Apollo Canonical’s way of naming a card’s parts.

03

Proposed Apollo definitions

Each type: its job in one line, and what it accepts

Every type below gets one of five kinds: layout, holder, record, block or part. Accept rules are written against kinds, not against named components, so a new component inherits the rules the moment it declares its kind. This is how HTML’s content categories work.

Layout · Bento

Job: arranges tiles that together answer one question.

accepts: tile, two or more

A bento may sit in a tile, which is how bentos nest. It paints no ground of its own; the radius sits on its container.

Holder · Tile

Job: one cell of a bento, with its own surface, holding one thing.

accepts: exactly one of block · carousel · layout (a nested bento or a card grid)

Never a tile directly inside a tile (Canonical’s “nested box fatigue”), never a lone button.

Holder · Carousel

Job: shows one, or a few, of a set of like items at a time, in order.

accepts: slides; each slide accepts exactly one record or one image block, and every slide holds the same kind

Lives in a tile, a page section or a hero; never in a card.

Record · Card

Job: one record in a set of records that share a structure.

accepts: its parts only (media 0..1, header 0..1, content 1, footer 0..1); content accepts blocks of atom or molecule size

Never contains a layout, a holder or another record. Always has peers: in a card grid, a card list or a carousel. A lone card is a tile.

Layout · Card grid / card list

Job: lays out a set of like cards.

accepts: record, two or more, all the same kind

This is the list family’s card-list surface (#274), given a name.

Holder · Panel

Job: a region of the screen frame that opens beside or over the page: a side panel, a drawer, a splitter pane.

accepts: layout or block; lives only in the page frame

Not a content box. The chart-panel role is renamed (call 3).

Block · Metric, chart, table, list, image …

Job: carries content: the thing the reader came for.

accepts: parts and atoms only

Sits in a tile, a card’s content, a panel or a slide. The stat card and KPI tile become one block, Metric (call 4).

Part · Subcomponent

Job: a named piece of one component (a card’s header or media), per this morning’s ruling.

accepts: what its parent’s part row says

Canonical’s shape, with a flag for “can stand alone”.

Two words that stop being types

Container becomes the register’s umbrella word for anything that accepts children: layout, holder or record. It is never a component name, except the layout utility’s width container.

Surface becomes a property of a type (ground, border or none), never a type. A tile paints a ground; a card draws a border.

05

How the edge register would enforce it

Check containment by kind through “accepts”, not by listing pairs

A sketch in the existing check’s style, not code to run.

Today the register’s containedBy row says only that a component or subcomponent sits in a component. With 142 components, listing the legal pairs would mean up to about 20,000 lines, and every new component would need its own. Instead, each component declares one kind, and each container kind declares its slots and what they accept. The check then asks one question of every containedBy line: does the parent have a slot that accepts the child’s kind (or a capability the child provides)? The count limits and the “all the same kind” rule are checked per slot.

register  containedBy.accepts = "by slot"      # new field on the row
meta      "kind": "record"                      # one of layout · holder · record · block · part
meta      "slots": { "content": { "accepts": { "kind": ["block"], "tier": ["atom","molecule"] },
                                  "count": "1" } }

for line in containedBy:                     # child → parent
    slot = first slot of parent whose accepts admits kind(child)
           or a capability child provides     # item 9b’s provides-capability
    if not slot:              report "NOT-ACCEPTED"   (must → refuse)
    if count broken:          report "TOO-MANY" / "MISSING"
    if slot.same and kinds differ: report "MIXED-SLOTS"
    if kind(child)=="record" and no peers:  report "LONE-CARD" (should → warn)

The pair line kept tonight, “a carousel holds cards”, then stops being a line to author. It becomes a fact the check derives: the carousel’s slide accepts records, and Cards declares itself a record. The existing Cards content slot, which accepts atoms and molecules, only gains the kind clause.
