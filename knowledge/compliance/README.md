# Compliance knowledge graph

The audit-grade compliance graph: **rule → component → check → success criterion → legal clause**. It links every component to the WCAG success criteria it must satisfy, with an automatable/manual check, severity, and the authoritative sources.

## Conformance basis

Graded against **WCAG 2.2 AA** — the minimum set by **HSBC's digital accessibility framework**, governed by **Group Digital Experience and Accessibility** (mandatory on all HSBC digital projects). See `knowledge/guidelines/digital-accessibility-standards.md` and `knowledge/components/_ACCESSIBILITY-CONFORMANCE.md`.

## Files

```
compliance/
├── rule.schema.json                # contract for a single rule node (one checkable SC)
├── EXAMPLE-contrast-rule.json       # synthetic example (kept for reference)
├── rules/                           # one schema-conformant rule per WCAG SC (31 files)
│   └── wcag-<sc>-<slug>.json
├── graph-index.json                # both-way adjacency: by_sc {SC -> [components]}, by_component {component -> [SCs]}; + verification {SC -> verified_by-or-null}
├── _build_compliance_kg.py         # generator (regenerates rules/ + applies_to index from component metas)
└── _build_verification_edges.py    # generator (layers verified_by onto rules/ + graph-index.json; advisory)
```

## How it's built (reproducible)

`_build_compliance_kg.py` reads every `knowledge/components/*.meta.json` `accessibility.relatedSC` array, parses the leading SC number, and derives the **`applies_to` edges straight from source-of-truth** (so the graph never drifts from the components). It then attaches each SC's metadata (title, level, WCAG versions, check type/threshold, severity, WCAG URL, EN 301 549 clause, internal policy ref) and writes one rule file per SC plus the index. Re-run after editing component metas:

```
python3 knowledge/compliance/_build_compliance_kg.py
```

`_build_verification_edges.py` runs later in `knowledge/_build_all.py` (after the contrast audits and the a11y gate) and layers a second edge type onto the same rule files + index — see **Two edge types** below. It reads evidence, it doesn't generate any; re-run it (or just `knowledge/_build_all.py`) after any of the audits it reads have changed.

## Two edge types: applies_to vs verified_by

`applies_to` is the **claimed** edge — a component meta asserts it satisfies a WCAG SC. It has always been derived straight from source-of-truth (the metas), so it never drifts, but it is still an assertion: nothing runs to check it's true.

`verified_by` is the **verified** edge (design direction ruled 2026-07-10, built 2026-07-14): non-null only where an executable check is wired into the build and its current result is recorded. Today that's **4 of 31 SCs**:

| SC | Mechanism | Granularity |
|---|---|---|
| `1.4.3` Contrast (Minimum) | token-level dark-mode contrast audit, gates the build | token |
| `1.4.11` Non-text Contrast | token-level dark-mode contrast audit, gates the build | token |
| `2.3.3` Animation from Interactions | a11y gate scans every reference snippet for missing `prefers-reduced-motion`, gates the build | component |
| `2.5.8` Target Size (Minimum) | a11y gate measures every interactive control's CSS box against the 24px floor, gates the build | component |

The other 27 stay `verified_by: null` — that's the honest, expected state for a manual or semi-automated check, not a gap in the tooling. See `knowledge/_VERIFICATION-EDGES.md` for the full breakdown (regenerated by `_build_verification_edges.py`).

**Granularity caveat:** `1.4.3`/`1.4.11` verify at **token** granularity (every colour token in the store clears the threshold) not per-component-instance. Getting to true per-component verification for those two needs the token blast-radius join (component → tokens it binds → are those tokens clean) — logged as next work in `_VERIFICATION-EDGES.md`, not built yet. `2.3.3`/`2.5.8` already verify at **component** granularity, since the a11y gate runs per reference snippet (one per component).

**A correction this surfaced:** `2.3.3`'s `check.type` was hand-typed as `manual` in `_build_compliance_kg.py`'s SC lookup table, but the a11y gate has enforced it (gating) since before this change — the metadata just hadn't caught up. Corrected to `semi-automated` (automated detection of the missing escape hatch; the "unless essential" exemption is still a manual judgement call) as part of adding `verified_by`. This is exactly the kind of drift the two-edge-type split is meant to catch.

## Traversing the graph

- **Component → obligations:** `graph-index.json` → `by_component["Modals"]` → `["1.4.3","2.1.2","2.4.3","2.4.11","2.5.8","4.1.2"]` → load `rules/wcag-<sc>-*.json` for the check, severity, threshold, sources, and (if present) `verified_by`.
- **SC → affected components:** `by_sc["2.4.11"]` → `["Modals","Navigations","Search field","Tabs","Tooltip"]`.
- **SC → is this actually enforced:** `graph-index.json` → `verification.by_sc["1.4.3"]` → the `verified_by` object or `null`.
- Each rule carries `sources.wcag_url` (Understanding page), `sources.en301549_clause` (EN 301 549 9.x.x.x; 2.2-only SCs flagged pending alignment), and `sources.internal_policy_ref`.

## Notes / future

- EN 301 549 clauses mirror WCAG SC numbering (9.x.x.x); the three WCAG-2.2-only SCs are flagged "pending EN 301 549 alignment to WCAG 2.2."
- `check.type` is the *gradeability* hint for an automated audit harness (automated / semi-automated / manual). Thresholds are set where machine-checkable (contrast 4.5:1/3:1, non-text 3:1, target 24px, reflow 320px, resize 200%). `verified_by` is the stronger, code-grounded claim — treat `check.type` as intent, `verified_by` as evidence.
- As more components are ingested, re-run the generator — the graph stays in sync with the component metas.
- **Next for the verification layer** (not this pass): (1) import W3C ACT Rules Format 1.1 + axe-core rule metadata for the SC↔rule leg rather than hand-typing the `M` lookup table in `_build_compliance_kg.py`; (2) the token→component join via `tokens/_blast-radius.json` to lift `1.4.3`/`1.4.11` from token to component granularity; (3) extend `verified_by` to the SCs the snippet/dark-surface/icon gates already touch indirectly, once each is confirmed to actually check that specific SC rather than a related concern.
