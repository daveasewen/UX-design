Three follow-up passes the same day (`c33dc97`, `547e7cc`, `dce57a4`) chased down and FULLY RESOLVED two real findings the join surfaced.

**Slice 1 — `verified_by` (`0882b35`):** `applies_to` (claimed) vs `verified_by` (verified — an executable check runs in our build and passes). 4/31 SCs verified. Caught real drift: `2.3.3`'s hand-typed `check.type` said "manual", corrected to "semi-automated" (the a11y gate already gated it).

**Slice 2 — `external_automatable_refs` (`87ebed7`):** imported axe-core v4.12.1 (105 rules, vendored snapshot at `compliance/_vendor/`, no live network at build time) as the "import ACT" half. 15/31 SCs have axe-core coverage: 13 easy-wins (covered, not wired), 2 already wired (`1.4.3`, `2.5.8`), 16 uncovered (2 of which — `1.4.11`, `2.3.3` — we already verify ourselves via bespoke checks). W3C ACT Rules Format checked, NOT ingested — no structured export exists without scraping ~500 pages; deferred with a concrete approach logged in `_vendor/_INGEST-NOTES.md`.

**Slice 3 — component-granularity join (`0b02ee1`):** `1.4.3`/`1.4.11`'s `verified_by` now report per-component pass/fail/not_covered via a join through `tokens/_blast-radius.json` (component → tokens it binds), not just an aggregate token-level result. Real finding at the time: `1.4.3` full coverage (18/18), `1.4.11` only 4/8 (Badge/Cards/Divider/Links not_covered) — logged, not yet fixed.

**Slice 4 — the 1.4.11 classifier fix, and what it actually found (`c33dc97`):** investigated *why* Divider fell through. Root cause: `_build_indicator_contrast_audit.py`'s classifier matched brand/RAG/interactive/status tokens only and explicitly EXCLUDED anything containing "border" — structurally incapable of ever auditing a border token, regardless of validity. WCAG 1.4.11 explicitly covers UI-component boundaries, so this was a real gap in the audit, not correct scoping. Widened the classifier to include border tokens. First full-build run surfaced 19 new gating failures — flagged and checked before committing. 4 were `*/disabled` tokens, which WCAG 1.4.11's own text exempts ("except for inactive components") — excluded. The remaining 15 were genuine dark-mode contrast failures store-wide, left gating on purpose (not allowlisted) pending a decision on how to fix them.

**Slice 5 — the actual token-value fix (`547e7cc`):** Dave: "we created the dark mode tokens so we have free reign on these specific tokens, so lets fix everything we should." All 15 dark-mode border values lifted to clear 3:1 against `#1D1D1D` (range 3.07:1–4.27:1), preserving each token's original relative weight (border/strong stays most prominent, divider break-lines stay subtlest — nothing flattened to one grey). Disabled tokens deliberately left untouched (WCAG-exempt). `primary/border/hover` kept its red hue, just lightened (#BA1110→#D61412). Reviewed via a rendered before/after HTML preview (all tiers + hierarchy check + disabled tokens shown for reference, per Dave's ask) BEFORE landing — Dave: "this all looks fine to me." Bonus catch: `data-vis/border/on-dark/baseline-2`/`gridline` had been reusing the *light-mode* grey/800 value verbatim with zero dark adaptation — now have real dark values (also fixed 2 stray "flat" dark==light entries in the dark-mode audit). Landing the token fix immediately surfaced a downstream consequence: 22 reference snippets hardcode the old hex values in their `[data-theme="dark"]` CSS blocks (separate from the token source), which drifted the snippet gate the moment the token changed — all 22 updated to match. **Result: `knowledge/_build_all.py` fully green, 0 gating failures across all 21 steps.** 1.4.11 join: 6/8 applies_to components covered, all 6 pass (Button, Status indicator, Account card, Cards, Divider, Dropdown). Badge/Links remained not_covered (unrelated to borders — separate open question, resolved in Slice 6 below).

**Slice 6 — Badge/Links resolved via a secondary snippet-contrastPair evidence path (`dce57a4`, same day):** neither Badge nor Links binds a border-category token, so the blast-radius join alone can never cover either — but investigation found this was a FALSE NEGATIVE for Links specifically: its reference snippet (`Links.reference.html`) already declares two `"ui"`-context `contrastPairs` (the arrow, the download icon) that the BLOCKING snippet gate (`_validate_snippets.py`, check 3) has been checking every single build all along — real, currently-passing evidence the compliance graph's `verified_by` join simply wasn't consulting. Badge declared only a `"text"` pair for its number label, with no `"ui"` pair for the fill itself, so a matching pair (`primary/background/default` vs `background/default`) was added to `Badge.reference.html`, mirroring Links' existing pattern — bringing Badge under the same already-enforced gate going forward. `_build_verification_edges.py` gained `snippet_ui_contrast_join()`: for any 1.4.11 component the blast-radius join can't cover, it reads that component's own reference-snippet `contrastPairs` and resolves/computes any `"ui"`/`"icon"`-context entry using the SAME `resolve()` token-walk and the SAME `_contrast_utils` formula the snippet gate itself uses — not a new check, just surfacing evidence that already exists. Only ever upgrades a `not_covered` verdict, never overrides a real blast-radius pass/fail. **Result: 1.4.11 join now 8/8, all pass, 0 not_covered.** Badge's fill: 5.22:1 (light) / 4.02:1 (dark) against the 3:1 floor. Links' arrow: same ratios; its icon: 12.63:1 / 21.0:1 against the 4.5:1 floor (icon-015 promotion). Full build green (`python3 knowledge/_build_all.py` exits 0). Also confirmed in this pass: `_build_verification_edges.py` and `_import_axe_rules.py` ARE properly wired into `_build_all.py`'s `STEPS` list (steps 19–20 of 21) — an earlier device-bridge staging of `_build_all.py` this session had returned a STALE, older copy missing those two steps, which briefly looked like a wiring gap; re-staging fresh from the device confirmed the live file is current and correct. Worth remembering: a staged file's mtime can lag the true device state if staged too early in a session — re-stage immediately before trusting a "gap" finding.
