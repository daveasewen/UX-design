**Standing principle (Dave, 2026-07-14) — mind the capability gap.** Confirmed for recording ("something
to note for sure").

Dave's frame, his words: *"I'm riding a very capable wave that not everyone I serve has access to... in
short order much of what we are doing might be obsolete — maybe for me, and more slowly for the designers
we serve."*

**The rule:** the driver's capability must NEVER be load-bearing for the product's value. My capability
(agents, whole-project context, judgment) can silently SUBSTITUTE for the product's structure and make
Apollo look like it works — but part of "it working" is me, and the designers Dave serves don't have me.
Use capability to DEPOSIT transferable structure (retrieved tokens, gates, runbooks, the library) into the
artifact so it holds for a designer — and for a weaker/cheaper model — WITHOUT us. The externalised
structure isn't scaffolding capability made obsolete; it's the TRANSFER MECHANISM. The gap is *why* the
discipline still matters — it stopped being about my limits and became about theirs.

**The sharpening — DIFFERENTIAL OBSOLESCENCE:** the gap isn't static; things obsolete at DIFFERENT RATES.
Fast for Dave (on the wave); slowly for the designers (their tooling advances slowly). Decision rule for
where to invest:
- **Slow curve — invest here, it compounds:** designer-facing transferable structure — library/canon as
  source of truth, the gates (floor/moat), the criteria/judgment/governance layer.
- **Fast curve — hold loosely, capability will eat it:** orchestration machinery — bespoke harness, heavy
  multi-agent scaffolding, §9 register machinery. (Matches Dave's own instinct: "less infra if possible",
  "trim §9 machinery, keep gates" — [[multi-mode-product-vision]], [[ruling-generation-shape-2026-07-10]].)
  Heuristic: if a thing only serves MY level, treat it as disposable; if it serves THEIRS, it's the asset.

**Reframe (opportunity, not just risk):** the persistent gap IS Dave's value. His durable role is
TRANSLATION / GOVERNANCE — take what he can do on the wave and deposit it into governed structure the
slow-curve users can use. That function doesn't obsolete fast; better models make it MORE needed, not less.
It's where [[digital-experience-transformation]] already points: value moves artifacts → judgment/criteria/governance.
What honestly obsoletes = scaffolding + much orchestration. What survives = criteria (what "good" is), the
library, and gates-as-audit (governance needs externalised proof; never let a model merely *assert* compliance).

**How to apply (every session):**
- Recall is a tell: if I "just know" a value, the user won't — retrieve/gate/write it down, never recall.
- Ask of every deliverable: does this stand up for someone WITHOUT me / on a weaker model?
- Build the floor to transfer; keep the ceiling available (don't dumb down; don't make my capability
  load-bearing for baseline value).
- Test at THEIR capability (designer live-fire + try a cheaper model); NAME the assist when I use capability they lack.
- Weight investment to the slow curve; keep fast-curve machinery thin.
