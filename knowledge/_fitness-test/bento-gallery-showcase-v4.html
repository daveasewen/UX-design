Bento layout, full-scale bento, photography gallery & bento designer — v3

Three layouts the library does not have yet, drawn so you can rule them by eye. The first is a bento — a wall of tiles of deliberately different sizes, where the size itself is the emphasis. The second is a photography gallery, shown both of the two ways a gallery can honestly be built, because which one is right is a judgement about pictures, not about code. The third, new in this version, is a full-scale bento: the same idea at marketing scale, where each tile is a whole statement on a twelve-column grid and the rows alternate 7/5, 5/7, 7/5.

New in this version, section 4: a bento designer. You saw nev.club’s grid and said the thing about it is that it looks designed, not generated. There are two honest routes to that feel and both are here, governed by the same twelve columns. A is an authoring tool — drag on a lattice, and tiles snap to whole columns and whole row units; there is no free-pixel placement anywhere in it. B is a seeded generator whose parameters are the ones that make a wall read as composed rather than computed: at most one hero, a few mediums, many smalls. C is the part that decides whether any of it is usable — one export that turns either route into plain CSS with the spans written out as numbers and no script in it at all.

New in this version: the gallery has a masthead. You said the bento is right for the photo library, so section 2 now opens with one — the same twelve-column composition section 3 uses, scaled down to a two-row band of cropped photographs sitting above the gallery’s own controls. It is the argument that the bento and the gallery are one idea at two scales rather than two components. Which way round the hero sits is not settled; the note under the masthead says so on the page.

This is v4. Nothing was taken away. bento-gallery-showcase-v1.html, -v2.html and -v3.html are untouched on disk and still say exactly what they said; this file is v3 plus the gallery masthead. If the masthead is the wrong idea, v3 is the record of the page without it, v2 the record without section 4, and v1 without section 3 either.

Everything on this page is proposed, not decided. No colour value was authored; every surface, ink, border and corner comes from a canon token, which is why the four theme buttons at the top change the look without anything here changing. The controls are there so you can settle the open questions live rather than from a description — column count, gap, how loud the tiles get, which gallery mode, and what shape a photograph should be forced into.

Two things will look like bugs and are not — they are the trade-off you are being asked to rule on. A staggered masonry gallery reads down its columns, but a screen reader and a keyboard read across the source order, so the picture you tab to next is not the picture beside the one you were on. Turning on dense packing in the bento does the same thing: it back-fills holes with whatever tile happens to fit, so a later tile jumps ahead of an earlier one. Press Show DOM order in the bar above and both sections number themselves in source order — where the numbers stop counting up, the reading order and the visual order have parted. Nothing on this page resolves that; it is shown, deliberately.

The lightbox has no JavaScript in it at all. Clicking a photograph opens it through the browser's own Popover API, triggered by the command / commandfor attributes on the button. There is no :target trick and no hidden checkbox. Escape closes it, clicking outside closes it, and focus returns to the photograph you came from — all from the platform. The badges in the bar report whether the browser you are reading this in actually supports that; the script that fills them in is review chrome and touches nothing in either component.

Technical detail
  • Bento is CSS Grid only. A repeating column track (repeat(var(--bx-cols), minmax(0,1fr))), a fixed row rhythm (grid-auto-rows), and four span utilities — wide (2×1), tall (1×2), big (2×2), hero (3×2) — expressed as data-span attributes. grid-auto-flow: row dense is a toggle, never a default. No flexbox, no absolute positioning, no measurement JavaScript.
  • Responsiveness is a container query, not a viewport query. The stage declares container-type: inline-size, so the bento collapses to two columns at 700px and one at 460px of its own box. That is why the 380px stage-width button collapses the layout on a wide screen — a viewport query could not see it. (Same argument as the l-split case in the #204 layout-utilities page.)
  • Gallery mode (a), masonry, is columns. CSS multi-column with break-inside: avoid on each cell. It preserves every photograph's native ratio and costs the reading order. Mode (b) is a uniform grid with object-fit: cover and an aspect-ratio; it keeps the reading order and costs the crop.
  • Native CSS masonry (Grid Lanes) is deliberately not used. It is not Baseline; the badge in the bar reports CSS.supports('grid-template-rows','masonry') as measured in your browser, and the layout does not depend on it either way.
  • Lightbox mechanism. <button command="show-popover" commandfor="lb-N"> against <div id="lb-N" popover>; the close button is command="hide-popover". Light dismiss, Escape, the top layer, and focus restoration are all the platform's.
  • Token binding. Page-local names (--ink, --surface, --line, --radius…) are bound to canon's own custom properties at the .bgx scope — --text-default, --surface-raised, --surface-subtle, --tertiary-background-default, --border-subtle, --border-strong, --text-secondary, --focus-ring, --border-radius-surface, --border-radius-control, --target-min, --layout-app-gutter. All twelve are defined in canon.css's :root, so none can dangle into a silent black in any theme.
  • Radius is not a decision here. Corners are --border-radius-surface and --border-radius-control as canon ships them per theme. Measured on this page: Console is the only rounded theme — surface 20px, control 8px (s199-D3) — while Mono, Legacy and Supercharge all resolve to 0. Switch themes and the corners move; no radius value was authored here.
  • Type. Zero raw font-size and zero raw font-weight in this file, chrome included. Every text node carries a .t-cm-* or .t-ed-* composite.
  • Images. 14 SVGs generated locally by assets-bento-gallery/_gen-photos.py (deterministic; re-runnable). No external fetch. Their palette is cool-only by construction — no red, no yellow — so nothing can be mistaken for a status signal.

Fourteen photographs of deliberately awkward shapes — two panoramas, four portraits, two squares. A gallery that only ever sees 4:3 landscapes proves nothing.

Six tiles on a 12-column grid, laid out 7/5, then 5/7, then 7/5, so the weight swings side to side down the page. Three things worth knowing before you look. (1) The Tile surface control here is the same open token question section 1 raises, not a second one — surface/raised and tertiary/background/default are identical to background/default in light in all four themes, so a full-scale tile painted with the correct card token is invisible except for its hairline. It starts on Subtle for legibility only; that is not a recommendation. How it collapses, and why it is a container query. Full 7/5 alternation while the stage is wide; 2-up equal below 1000px of the stage; single column below 640px. 4 · Bento designer

Two routes to a grid that looks designed rather than generated, and both of them are governed by the same twelve columns. A is a drawing tool: drag on the lattice and a tile appears, snapped. B is a seeded generator: set the shape of the distribution and it deals a layout, the same layout every time for the same seed. C is the only part that matters downstream — an export that turns either of them into plain CSS with concrete numbers in it.

Two things about what this is. (1) The tool has JavaScript in it and the thing it makes does not. Sections 1–3 still contain no script at all. This one does, because it is an authoring surface and an authoring surface without behaviour is a picture of one. What it emits is a <style> block and some markup with the spans written out as numbers — no script, no randomness, nothing to run. (2) Snap is not a convenience, it is the constraint. Nothing here can be placed at a pixel. Every drag resolves to whole columns and whole row units before it is recorded, which is why the export can be trusted: the tool cannot draw a layout the minted CSS could not reproduce.

A · Snap designer

Drag on an empty part of the lattice to draw a tile. Drag a tile to move it. Drag a corner or an edge handle to resize it. The small button at a tile’s top-left cycles its content through the three kinds this exploration already uses — text, photograph, statistic — and the one at the top-right removes it. New tiles take the next kind in that same cycle, so a drawn wall is never all one thing.

Keyboard, and an honest account of it. Every tile is focusable: Tab to it, then ←↑→↓ moves it one column or one row, Shift + the same arrows resizes it by one column or one row, K cycles its kind and Delete or Backspace removes it. Each of those is announced in the status line above. What is missing, stated rather than glossed: drawing a new tile from the keyboard is not possible — the Start me off and Clear buttons and the parametric generator below are the only keyboard routes to a new tile; there is no keyboard equivalent of drag-to-draw. That is a real gap and it is named, not designed around.

B · Parametric shuffle

Why naive random feels mechanical — this is an explanation, not a ruling. If you pick every tile’s size uniformly at random you get three things at once, and all three read as computed: sizes arrive in roughly equal numbers, so nothing is the biggest thing and the eye has no entry point; the packer leaves holes wherever the next tile does not fit, and a hole in a wall reads as a mistake rather than as air; and because no size dominates, the wall has no rhythm — it is a texture, not a composition. A grid that reads as designed is a skewed distribution: at most one hero, a few mediums, and many smalls, with the hero placed first so everything else arranges itself around it. The controls below are exactly those three quantities, plus an explicit hole policy, so you can watch the difference rather than take it on trust: set the three weights equal, turn the hero off and fill-holes off, and the wall goes mechanical in front of you.

One measured caveat about fill holes, because the obvious claim about it is false. Back-filling does not produce a tighter wall at every seed. The packer is greedy — it drops each tile into the first place it fits — and filling an early gap can leave the last few tiles worse off than they would have been. Measured across eight seeds: mean fill 79.2% with back-fill on against 76.8% off, but at seed 2026 back-fill is actually the looser of the two (72.0% against 79.2%). The v3 probe asserts the average and explicitly does not assert the per-seed case, because the per-seed case is not true. Reroll a few times and you will see both.

Determinism is the whole point of the seed. The generator uses a small fixed-arithmetic pseudo-random function, not Math.random, so the same seed with the same parameters produces the same layout every time this page is opened, in any browser, forever. That is what makes minting safe: the recipe below is a record of a layout somebody chose, and it can be re-derived rather than merely archived.

C · Export — minted, not live

The generator mints concrete values. A component page would ship the minted CSS and never the randomness that produced it. Nothing downstream should ever import a shuffler, call it at page load and get a different wall on every visit — that is not a design, it is a slot machine, and it cannot be reviewed, screenshotted, regression-tested or signed off. The export below is the artefact: spans written out as numbers, colour left to Apollo tokens, zero JavaScript. Paste it into a page and it works with the script on this page deleted.

It round-trips. Export → paste the JSON into the import box → load → export again gives the identical bytes, because the serialiser orders tiles by row then column and writes only integers. That is not a nicety: a recipe that does not round-trip cannot be stored, diffed or reviewed, and would quietly become a one-way export.

What this is FOR, and it is not built here. The use this was drawn for is a minted “related components” bento at the foot of each showroom component page — a small designed wall of the things you would plausibly reach for next, minted once per page rather than shuffled per visit. Which components belong in which related cluster is ALREADY an open question in front of you — it sits in knowledge/_REVIEW-SIGNOFF.md in the component-library row (#215), under related-cluster membership, along with the sixteen usage-group assignments and the status derivation rule. This page does not answer it, does not propose an answer, and does not touch showroom/ at all. It exists so that when you do rule on membership, the thing that renders it is already a settled shape rather than a second open question.

What is open, and who decides it

Everything below is yours. Nothing on this page has been ruled, recommended, or quietly defaulted into place; where a control has a starting position it is a starting position, not a proposal.

  • Bento defaults — column count, gap, row height and which span preset (if any) is the shipped one. The Flat preset is on the page precisely so “no bento” stays an available answer.
  • Dense packing — whether grid-auto-flow: dense is offered at all, given it breaks reading order. It is a toggle here, never a default.
  • The gallery’s mode — masonry or uniform grid as the library’s default, or both as equal siblings. Not settled here.
  • The aspect-ratio default — 1:1, 4:3, 3:2 or free. Every one of them crops something; which crop is acceptable is a judgement about the pictures.
  • The full-scale bento’s split ratio — 7/5, 8/4, or symmetric 6/6. 7/5 is the starting position only because it is the reference’s shape; 6/6 is on the control so that “don’t be asymmetric” stays an answer you can pick rather than one you have to ask for.
  • Whether the illustration alternates sides down the full-scale page, or always sits right. Unlike dense packing in section 1 this costs nothing in reading order — the DOM is text-then-illustration in every tile either way — so it is a pure look decision.
  • Where the full-scale layout should give up its asymmetry — it currently goes 2-up equal at 1000px of the stage and single-column at 640px, and the illustration moves above the text at 520px of the tile. Those three numbers are proposed, measured, and yours to move.
  • Which of the two routes to a bento the library should actually offer — a hand-authored snap designer, a seeded generator, both, or neither. Section 4 builds both so the choice is made by eye rather than by description; it is not a recommendation of either.
  • The generator’s default distribution — the starting weights (hero 3 / medium 3 / small 7, hero on, fill-holes on, eleven tiles, seed 2026) are a starting position chosen to be legible on arrival, not a proposal. Set the three weights equal and turn the hero off to see what the argument on that section’s face is actually about.
  • The tile-size vocabulary the generator deals from — hero 8×2; mediums 6×2, 4×2, 6×1; smalls 3×1, 4×1, 3×2. Those seven shapes are the whole alphabet, and whether they are the right seven is yours. Note they are a different vocabulary from section 1’s four span utilities, on a 12-column grid rather than a 4-column one; whether the library should have one vocabulary or two is open.
  • Whether a minted bento is how “related components” should appear on showroom component pages at all — and, separately, which components belong in which cluster, which is already open in front of you in the component-library row (#215) and is NOT answered here.
  • Whether either of these becomes a gated component at all, or stays an exploration.
  • Which surface token a card paints with — and this one is measured, not felt. surface/raised and tertiary/background/default are both identical to background/default in light in all four themes, so the semantically correct card token renders flush. Fixing that is a token move; the control on the bento only lets you see it.
  • Theme ink and grey tints — surfaced, not touched. Switch themes and watch the tile surface against the page; if any pair reads flat to you, that is a token question, not a layout one, and it belongs to you.

Selections on this page are not persisted. Rulings land in chat and in the ledger, never in a control’s position.
