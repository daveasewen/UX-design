Banner — a dedicated error TEXT ink on the error fill (FLOATED)

What changed from v1. v1 attacked this by moving the fill (overlay direction and strength) under white text. This card follows your direction instead: the fill and its overlay are left exactly as ruled, and only the TEXT ink moves — a new token, separate from #F6604C.
The finding that makes the split necessary. The overlay is declared as a mix of var(--ink), so the overlay always follows the text ink. If a dark error ink were introduced by re-pointing --ink, the overlay would darken with it and every state would drive contrast down: measured that way, even pure #000000 reaches only 4.31:1 pressed and FAILS. A separate text-only token leaves --ink (and therefore the overlay) white, so hover and pressed lighten the fill and contrast rises with state. The two-token split is not stylistic here — it is what makes the fix arithmetically possible.
.banner .actions .abtn:hover{background:color-mix(in srgb, var(--ink) 14%, transparent)}   /* UNCHANGED */
.banner .actions .abtn:active{background:color-mix(in srgb, var(--ink) 22%, transparent)}  /* UNCHANGED */
.banner.err{color: var(--err-text-ink)}   /* PROPOSED new token, name provisional — TEXT only, never the fill, never --ink */

Open question — should a DARK-THEME red text ink exist at all? (FLOATED)

Your stated rule is that red text is used exclusively with the dark ink — i.e. red text appears only in dark-ink (light-surface) contexts. Dark theme inverts that: surfaces are dark and the ink is light. So the rule, taken at its word, implies there may be no dark-theme red text value at all. That is a policy ruling, not a colour pick, so no swatches are offered. It has to be decided before any error-ink token can be defined, because a token with no dark-theme value is a deliberate absence, not an omission.
